# Delegation and model rules

## Delegation

Review every `agent` cue. For each subagent invocation:

- Identify the subagent type, if named. Estimate the prompt size from the surrounding quoted block or described context injection.
- Two independent subagent calls described sequentially → **MUST FIX**; recommend parallel fan-out in a single assistant turn. A parallel fan-out in one turn is good; never flag it.
- Injected context that could be passed as a file path instead (e.g. an inlined file list) → SUGGESTION.
- A scope narrow enough for an inline search or read → SUGGESTION.
- `subagent-reply` (the skill delegates but never bounds the reply) → SUGGESTION: even when the result goes to a file, every closing message lands in the orchestrator's context. Recommend a fixed one-line reply such as `WROTE <path>`.
- Each `RUNTIME_PROMPT <file> <line> <script>`: a subagent reads a prompt that the named script (or `unknown`) writes at runtime, which the skill's own files never show. The lines after it measure the rendered sample of that prompt, kept in the skill's source tree:
  - `RUNTIME_PROMPT_SAMPLE <sample> <tokens>`, the rendered prompt's estimate; `RUNTIME_PROMPT_READ <sample> <path> <tokens>`, each skill file it tells the subagent to read on every run; and `REPLY_BOUNDED <sample> yes|no`. Report each sample in the Scope. Judge the sample as you judge a body, by content: a SUGGESTION only for a prompt that restates its reads or carries text the subagent never acts on, a read whose content the prompt could carry in a line, or a read that sends the subagent on to further files. `REPLY_BOUNDED <sample> no` → SUGGESTION to end the prompt with a fixed one-line reply such as `WROTE <path>`. Otherwise the runtime prompt has no finding on its content.
  - A sample's `CUE <sample> <line> <cue> <text>` lines judge its order and wording; each is a candidate to read in context. Current models weigh the end of a prompt most and overtrigger on emphatic wording.
    - `after-reply`: text follows the reply line that ends the output contract, so the reply is not the last thing the subagent reads → SUGGESTION to move it ahead of the contract; drop it when the text is the prompt's own instructions and holds no data.
    - `untrusted-after-contract`: a block the prompt marks as untrusted data sits after its output contract starts, so untrusted text comes last → **MUST FIX**: move the data ahead of the instructions and the contract, so the prompt ends with its contract, any self-check, and the reply line.
    - `emphasis`: a rule stated in capitals, such as "MUST" or "Do NOT" → SUGGESTION to state it plainly; drop it for a value the prompt quotes, such as a status word.
  - `RUNTIME_PROMPT_UNSAMPLED <file> <line> <reason>`: no sample was found, for the reason given. Never judge the prompt as a small one; report a SUGGESTION to audit what that script renders by hand (its size, any chain of reads it starts, and whether it bounds the reply), naming the reason, and to keep a rendered sample beside the source.
- A subagent call inside a loop over N items with no cap → **MUST FIX** (unbounded fan-out).

### The agents a skill starts

`scan` reads the definition of each subagent type the skill's Markdown names, from the `agents` folder beside its skills folder: `agents/` in a source tree, `~/.claude/agents` for a deployed skill, and the plugin's `agents/` for a plugin's copy, which names each type `<plugin>:<agent>`. The built-in types, general-purpose among them, have no definition.

- `AGENT <type> <definition>`, `AGENT_TOOLS <type> <tools or all>`, `AGENT_MODEL <type> <model or none>`, and `AGENT_CLAUDE_MD <type> omitted|loaded` give what the type is granted: `all` is every tool the session has, `none` a model that follows the session's, and `omitted` a context without the `CLAUDE.md` files. Report them in the Scope. A type granted `all` that reads text the skill does not control → SUGGESTION to list the tools its prompt needs.
- `AGENT_HOOK <type> <event> <matcher> <program> timeout=<seconds or default> on_failure=<value>`: before every call of that type that the matcher matches, the definition starts `<program>` and waits for it, up to the timeout (a command hook's default is 600 seconds). State that per-call cost in the Scope: one start of the program for each matching call while the subagent runs, and, in the plugin form, where the same hook sits in the plugin's `hooks.json`, one for each matching call of every session in which the plugin is enabled. The cost of a guard the subagent's input needs is no finding. SUGGESTION when the matcher matches tools `AGENT_TOOLS` does not grant, or when a hook that guards untrusted input has an `on_failure` other than `block`, so a hook that fails lets the call through.
- `PLUGIN_HOOK <event> <matcher> <program> timeout=<seconds or default> on_failure=<value>`, printed for a plugin's copy: a hook the plugin's `hooks.json` runs, where the plugin build moves each agent's own hooks, since Claude Code ignores a plugin agent's. Before every call the matcher matches, in every session in which the plugin is enabled and whatever skill runs, it starts `<program>` and waits for it, up to the timeout. State that per-call cost in the Scope, for every skill of the plugin. Judge it as an `AGENT_HOOK` of each agent the plugin carries: a guard the agent's input needs is no finding, and an `on_failure` other than `block` on a hook that guards untrusted input is a SUGGESTION.
- `AGENT_UNREADABLE <path> <reason>`: the definition cannot be read; report it in the Scope with its grants unknown.
- `AGENT_UNDEFINED <file> <line> <type>` → **MUST FIX**: no definition provides the type, so every run takes the body's fallback, such as a general-purpose subagent, or fails to start it. Recommend shipping the definition and declaring it in the metadata's `agent_deps`, or naming a built-in type.
- `AGENT_UNDECLARED <file> <line> <type>` → **MUST FIX**: the source tree defines the type, but neither the skill's `agent_deps` nor a dependency's declares it, so a deployment never installs it and the deployed skill meets it undefined. Recommend declaring it.
- `UNGUARDED_SUBAGENT <file> <line> <type>`: the line starts a general-purpose subagent, which has every tool and no hook, where the guarded type named exists → **MUST FIX** when that subagent reads text the skill does not control, such as a pull request, a document, findings, or people's comments; SUGGESTION otherwise. Recommend starting the guarded type, with a general-purpose subagent only as the fallback for a session that has no such type.

## Model

Claude adapter values are `haiku`, `sonnet`, `opus`, or absent. For other runtimes, also inspect any native adapter metadata when present.

- **SUGGESTION** — a Claude skill does purely mechanical work (all shell and file/search operations; no synthesis, no subagent calls requiring reasoning, no natural-language output beyond a fixed template) and has no model set or pins `sonnet`/`opus`. Suggest trying `model: haiku`, and only after comparing real runs before and after: a cheaper model can quietly lower quality, so never make it a MUST FIX or recommend it without that comparison. Also warn that in Claude Code a skill's `model` applies for the rest of the turn that invoked it, not only while the skill runs; the session's model resumes at the user's next prompt. Every subagent started later in that turn without an explicit model runs on the skill's model. Never suggest a cheaper `model` for a skill that is usually followed, in the same turn, by work that starts subagents. When such a skill can run without the conversation's context, suggest `context: fork` with `model` instead, since `model` then sets only the forked subagent's model. For another runtime, suggest its low-cost equivalent only when that runtime supports skill-level model selection, under the same condition.
- **SUGGESTION** — a skill pins `haiku` but includes reasoning-heavy steps (multi-file synthesis, severity judgment, written recommendations). Recommend removing the pin so the caller's default applies.

The same rules hold for each model and effort a subagent starts on, wherever the skill sets it. A role's setting decides the quality of every run that delegates it, and a cheaper model or a lower effort can miss findings with no visible failure, so only a before-and-after comparison of real runs justifies one.

- `SUBAGENT_MODEL <file> <line> <source>` and `SUBAGENT_EFFORT <file> <line> <source>`: the line delegates a role on the model or effort that source gives. `printed <word>` is the value of a line a script prints, such as a review pipeline's per-role model; read the printing script only as far as where it takes the value (a reviewer profile, a manifest, or the configuration) and report each role's source in the Scope. No finding.
- `PINNED_SUBAGENT <file> <line> model|effort <value>`: a subagent starts on that literal model or effort, set by the skill's Markdown, an agent definition it names, a reference's frontmatter (a reviewer profile's), a JSON data file (a manifest or a configuration), or a script, its own or a dependency's. **MUST FIX** for `haiku`, or for `low` or `minimal` effort, and SUGGESTION for any other value, unless the skill or its documentation cites a before-and-after comparison of real runs for that setting: recommend removing the pin so the session's model and effort apply, or running and citing that comparison.
