# Coding Agent Skills Development

This project packages portable Claude Code skills and a guarded deployer. Each rule below is stated once; the section it points at holds how validation, a hook, or CI enforces it.

The deployer is a standard-library Python 3.12.0+ package and supports Windows, macOS, and Linux, WSL included. Configured paths are absolute drive-letter paths on Windows and absolute POSIX paths elsewhere, and rendered Bash and PowerShell are validated with Git Bash on Windows or the first `bash` on `PATH` elsewhere, ShellCheck, and PowerShell. Keep every operating-system-specific behavior in `deployer/platform_support.py` so Unix support is added there without touching the pipeline. The exceptions are the platform values and process mechanics ejryan89-skill-core holds because a skill's script needs them too, which the deployer reads from there, among them `PYTHON`, which every skill renders as `{{PYTHON}}`. A module states a sanctioned exception beside the code it excuses, as a module-level `PLATFORM_ALLOWED = {token: reason}`; "One platform seam" in `docs/design.md` names each exception, what it holds, and what validation refuses outside the seam.

## Architecture

- `skills/<name>/` contains immutable skill templates. Never render configuration into this source tree.
- `agents/<name>.md` holds Claude Code subagent definitions that skills declare in `agent_deps`; the deployer installs them to `~/.claude/agents`.
- `skills/<name>/scripts/` is the only permitted location for a skill's executable files. Keep substantial executable logic out of Markdown.
- `deploy-meta/<name>.json` declares each skill's required variables, shared dependencies, same-source skill dependencies, selection visibility, opt-in status, the external tools it runs, required or optional, and its runtime support on each of Claude Code, Codex, and Copilot CLI, in the one layout "Metadata" in `docs/adding-a-skill.md` gives, which also says how validation holds each runtime-support declaration to what the skill's frontmatter needs.
- Skills may run only standard commands or declared tools. A Python script names the program of every command it starts where validation can read it, or states why beside the code as a module-level `COMMANDS_ALLOWED = {scope: reason}`; see "Commands skills may run" in `docs/adding-a-skill.md`. `deployer/tools.py` is the single catalogue of those tools, the deployment prerequisites, and the runtimes `python deploy.py verify` lists, with their version floors; `python deploy.py check` (`deployer/check.py`) reports them, and `deployer/source_commit.py` records the source commit in the manifest's source entry at each deployment.
- `source.json` may group selectable skills into atomic bundles, and its `renamed` records each renamed skill's old name, whose owned copy the next deployment moves to the new one ("Renaming a skill" in `docs/adding-a-skill.md`); the manifest records requested roots separately from their expanded dependency closure and each skill's deployed `skill_deps`. A skipped or preserved skill keeps its recorded transitive skill dependencies and their shared assets and agents.
- `skills/<asset>` contains shared assets declared in `source.json` as either `owner` or `dependency`.
- `skills/ejryan89-skill-core/` is a hidden skill and the one home of the repository's shared Python: skill scripts, the deployer, and `tools/` all import its modules from `skills/ejryan89-skill-core/scripts`, and nothing copies them. It holds one module per concern, among them `bash_syntax.py`, the one Bash grammar; `console.py`, whose `run_main(main)` is the one call in every entry point's `__main__` block; `frontmatter.py`, the one reader of skill and agent frontmatter, which skill scripts, the deployer, `tools/`, and the tests import as `frontmatter`; `github_client.py` and `git_client.py`, whose `GitHubClient` and `GitClient` every `gh` call and every git call from a skill's Python go through; `bounded_process.py`, the bounded runner under both; `skill_roots.py`, the skills directories a script must not write inside, and `sibling_scripts`, the one lookup of a sibling skill's `scripts`; `executable_locator.py`; `flat_text.py`, the one whitespace flattener for text a script prints on one line; and `xml_reader.py`, the one reader of untrusted XML. "Script results" in `docs/adding-a-skill.md` states the runner's and the clients' contracts.
- A dependent declares `ejryan89-skill-core` in `skill_deps`, puts `../ejryan89-skill-core/scripts` on `sys.path`, and reaches every other sibling it declares through `sibling_scripts`, as the suites under `tests/` and the modules under `tools/` do after their own `sys.path` statement; the deployer's one such statement is in `deployer/__init__.py`. The deployer and ejryan89-skill-core import nothing outside the standard library, the deployer, and ejryan89-skill-core, and ejryan89-skill-core nothing from the deployer or `tools/`; "Validation" in `docs/adding-a-skill.md` gives each of those statements and states every import rule validation holds.
- `deploy.py` is the single command-line entry point. `deployer/cli.py` routes it, and `deployer/arguments.py` declares its `argparse` parsers.
- Every entry point, a module whose `__main__` block calls `run_main`, states its codes in an `Exit status:` docstring table, and each command has a fault driver in `tests/malformed_input/faults_*.py` or a `NOT_RUN` reason; see "Script results" in `docs/adding-a-skill.md`.
- `python deploy.py configure` runs `deployer/configure.py`, which writes a strictly parsed, source-specific configuration under `~/.claude/deployer/config/`. `deployer/config.py` is the single declaration of configured and derived variables.
- Any other `deploy.py` invocation runs `deployer/pipeline.py`: it renders selected skills in memory, validates the result, applies journaled multi-root changes, and records source-scoped ownership in `~/.claude/skills/.deploy-manifest.json`. `pipeline.py` orchestrates a run (the lock, recovery, the journal, and the manifest commit) over `deployer/selection.py`, `deployer/plan.py`, `deployer/report.py`, and `deployer/migrate.py`, and `deployer/context.py` holds a run's options, selection, and manifest state; "Organizing modules" in `.github/CONTRIBUTING.md` says what each part holds. `deployer/kinds.py` describes each kind of item (skills, shared assets, runtime adapters, agents) once, and every pass over them iterates it, except where a kind differs, which its module states beside the code as a module-level `KINDS_ALLOWED = {pass: reason}`; "One table of item kinds" in `docs/design.md` names the exceptions and what validation refuses. Authoritative skills live under `~/.claude/skills`; thin generated runtime adapters live under `~/.agents/skills`.
- Every mutating filesystem operation of `deploy.py` and the deployer goes through `deployer/fsops.py`, whose `fsops.extract_archive` is the one extraction; tests inject failures by replacing those functions. A sanctioned exception, for throwaway files and directories under the system temporary directory only, is stated beside the code as a module-level `FSOPS_ALLOWED = {token: reason}`; "One write point" in `docs/design.md` says what validation counts as a write.
- Never copy a module-level definition or constant between non-test Python files under `skills/`, `deployer/`, `tools/`, `.claude/skills/`, or `tests/validation/`: import one copy, and move a module more than one part of the repository needs to ejryan89-skill-core. A copy that must stay is sanctioned beside the code in every module that holds it, as a module-level `DUPLICATION_ALLOWED = {name: reason}` whose reason names every other file that holds the copy; "Validation" in `docs/adding-a-skill.md` says what counts as a copy.
- `python deploy.py verify` (`deployer/verify.py`) checks, without starting a model, that Codex and Copilot CLI each find every manifest-owned runtime adapter, enabled and not shadowed. `deployer/discovery.py` reads each runtime's skill listing (Copilot's `copilot skill list --json`, Codex's app-server `skills/list` request) and is shared with `tools/runtime_canary.py`.
- `tests/deployer/test_*.py` are the deployer suites; their isolated fixture repositories and homes live in `tests/deployer/harness.py`, which fails a test whose deployment changes anything under its source, and one whose expected refusal changes the home unless the test states why with `changes_home`; "Refusals before mutation, and journaled rollback" in `docs/design.md` says what the two comparisons leave out and what `tests/deployer/test_invariants.py` shows.
- `docs/skills.md` is the skill reference. `tools/skill_reference.py` generates its summary table and the first block of each skill's section, and the "Runtime support" table, from `SKILL.md` frontmatter and metadata; the explanation after each block is hand-written. After changing a skill's frontmatter or metadata, run `python tools/skill_reference.py --write`; validation fails while the reference is stale.
- `tools/runtime_prompts.py` renders, from fixtures and with no model, a sample of each role it names among the prompts a skill's or a repository skill's script writes for a subagent at runtime, into `docs/runtime-prompts/<skill>/<role>.txt`, with the throwaway folder as `<temp>` and the checkout as `<source>`, where `audit-skill` measures it. After changing such a prompt, run `python tools/runtime_prompts.py --write`; validation fails while a sample is stale.
- `tools/plugin_build.py` assembles the Claude Code plugins from `skills/`, `agents/`, and their metadata, each described by its entry in `.claude-plugin/marketplace.json`, into a folder under the temporary directory or reproducible archives, and never into the source tree: a plugin is a build output, never committed, and validation holds each plugin's files to their sources ("Validation" in `docs/adding-a-skill.md`). `tools/plugin_release.py` builds a release's archives from its tag and pins their checksums in the marketplace ("After tagging" in `docs/releasing.md`). `tools/plugin_canary.py` checks them in a throwaway Claude Code configuration ("Before tagging" in `docs/releasing.md`); like the runtime canary it calls a model, so it is a manual gate, never part of validation.
- `tools/runtime_canary.py` deploys this checkout and the fixture source in `tests/fixtures/runtime-canary/` into a throwaway home with `deploy.py --canary-home`, checks that Claude Code, Codex, and Copilot CLI find and run the named skills, and fails where a run disagrees with the skill's declared runtime support. It calls models, so it is a manual pull request gate run through the `runtime-canary` repository skill, never part of validation. Nothing under `tests/fixtures/` ships, which validation enforces.
- `tools/skill_evals.py` runs a skill's fixed scenarios under `tests/fixtures/skill-evals/<skill>/<scenario>/` model by model and judges each run by script, never from the report. It calls models, so it is a manual pull request gate run through the `evaluate-skill` repository skill, never part of validation; "Skill evaluations" in `docs/skill-evaluations.md` describes the scenarios, the runs, and what is recorded.
- The `deployable.yml`, `runtime-command-lines.yml`, and `runtime-changelogs.yml` workflows under `.github/workflows/` run on dispatch and weekly, start no model, and are never a required check. `deployable.yml` deploys onto fresh Windows, Linux, and macOS runners, uninstalls, and deploys again, and the README's fresh-runner column records its last dispatched release run. `runtime-command-lines.yml` starts, signed out, each runtime command line the repository builds, from the function that builds it for real runs, never a copy, so a runtime release that drops or renames a flag fails the job. `runtime-changelogs.yml` is advisory and fails only when the watch cannot run: it lists the runtime changelog entries that mention a term the code uses and each guidance page that moved or is gone. "Before tagging" and "After tagging" in `docs/releasing.md` say what each runs, judges, and reads, how the guidance audit uses the watch, and what validation pins.
- `tools/release_notes.py` writes a release's section of `docs/upgrade-notes.md` from the upgrade notes of the commits since the previous tag, and `tests/validation/upgrade_notes.py` reads the same entries; "Before tagging" in `docs/releasing.md` runs it.
- `tools/worktrees.py` coordinates parallel sessions (creating task worktrees and surveying them), `tools/hub_guard.py` is the hub guard hook declared in `.claude/settings.json`, `tools/new_skill.py` scaffolds a new skill's frontmatter, metadata, and reference section, or, with `--repository`, a repository skill and its shim, and `tools/skill_shims.py` writes and checks the shims; `tests/tools/test_*.py` are the suites for `tools/`.
- `.claude/skills/<name>/` holds this repository's own skills, for working on it rather than for deployment. Each has a shim in `.agents/skills/<name>/` with the same frontmatter for Codex and Copilot; an adapter is what the deployer generates under `~/.agents/skills` for a deployed skill. Keep the two words distinct. Repository skills meet the shipped-skill standard, and a change to one runs `audit-skill` on it ("Validation" in `docs/adding-a-skill.md`). `review-repository` is this repository's own pull request reviewer, which `review-prs` runs once a machine's code-review configuration names it; "The repository skills" in `.github/CONTRIBUTING.md` says what its reviewers read.
- `docs/design.md` owns why the repository is built this way (the trust model, the invariants, and each decision with its reason and date), and a change that bends an invariant or revisits a decision updates it in the same pull request.

A document names what the repository holds or does and never counts it, and states no date or version in guidance; a reader who needs the number takes it from the generated reference or a command, and a "checked on" or "as of" date is replaced by the thing checked. The exceptions are the places that own a date or version as the record: a decision's date in `docs/design.md`, a release's section in `docs/upgrade-notes.md` and its notes, and the README's supported-runtimes table and the date of its fresh-runner run, which "Before tagging" in `docs/releasing.md` maintains.

To add or change a skill, follow the `change-skill` repository skill. It applies `docs/adding-a-skill.md`, the skill contract, one section at a time: read the section each step names before acting on it.

## Safety requirements

- Do not modify installed skills under `~/.claude/skills`, installed agents under `~/.claude/agents`, generated adapters under `~/.agents/skills`, or user-managed Copilot skills under `~/.copilot/skills` while developing or testing this project.
- Use an isolated temporary home for deployment fixtures and canaries: `--canary-home`, or `Paths` built on a temporary directory. `deployer/platform_support.py` takes the home from the Windows profile folder on Windows, so setting `HOME` alone does not isolate a run there.
- Preserve immutable template sources and verify source hashes when testing rendering.
- Never source or execute configuration files; keep parsing restricted to validated `KEY=VALUE` entries.
- Treat tokens used in Bash, PowerShell, JSON, YAML, or other executable/structured contexts according to that context. Universal raw substitution is not sufficient.
- Reject unresolved tokens, unsafe names and paths, ownership collisions, and invalid shared dependencies before mutation.
- Preserve journaled rollback, recovery, locking, manifest ownership, and permanent backup behavior.
- Do not add personal paths, internal organization names, credentials, or generated deployer state.
- Do not change the source ID without an explicit ownership-migration plan.

## Parallel sessions

Several sessions may work in this repository at once, and sessions that share a checkout share a HEAD and a working tree, so one session's branch switch or commit carries another's uncommitted edits. Each task therefore gets its own worktree; see `docs/parallel-sessions.md`.

- The main checkout is the hub. It stays on `main`, stays clean, and is never edited. It is used only to pull `main`, create and retire worktrees, survey, and deploy.
- Start a task with `python tools/worktrees.py new <kind> <name>`, which creates `.claude/worktrees/<kind>-<name>` (gitignored) on branch `<kind>/<name>`. Then move the session into it (in Claude Code, `EnterWorktree` with that path) before editing. `python tools/worktrees.py list` surveys every worktree.
- Integrate through a pull request pushed from the worktree, never through a merge in the hub. After it merges, retire the worktree from a session outside it with `repo-cleanup` on the hub, which also fast-forwards `main`; see "Retiring a worktree" in `docs/parallel-sessions.md`. By hand, also from the hub, run `git worktree remove <path>` and `git branch -D <kind>/<name>`, since `-d` refuses a squash-merged branch.
- Deploy only from the hub on `main`: `deploy.py` refuses to deploy from a linked worktree, and `--canary-home` (a throwaway home under the temporary directory) still works there; "What is shared even across worktrees" in `docs/parallel-sessions.md` says why, and when `--dry-run` refuses there too.
- When one session orchestrates several task sessions, a session in the hub keeps their pull requests merging with the `shepherd-pull-requests` repository skill, one tick at a time; see "An orchestrator and a shepherd" in `docs/parallel-sessions.md`.
- Never pop or drop a stash you did not create: the stash stack is shared by every worktree.
- In a clone that opts in with `git config coding-agent-skills.hubGuard true`, the Claude Code hook in `.claude/settings.json` catches the accidents a session makes in the hub, such as an edit, a git write, or a redirection into it, and is no sandbox: what a program it does not read writes there is left to the check the shepherd tick and `repo-cleanup` run; "The guard's contract" in `docs/parallel-sessions.md` names what it reads, refuses, and does not see. For Codex and Copilot CLI these rules are the guard; "Other runtimes" in `docs/parallel-sessions.md` says what each runs of the hook.
- `.claude/settings.json` is tracked and may hold `$schema`, hooks, and `attribution` only. Its `attribution` keeps Claude Code's commit trailers, pull request footer, and session links off every commit and pull request made here. Permissions and every other setting belong in each developer's user or `settings.local.json` settings, and a `settings.local.json` is never committed; "The guard" in `docs/parallel-sessions.md` says what validation refuses.

## Required validation

The validation command, which CI runs in full on every push and on every pull request that is not documentation-only (a documentation-only pull request runs the subset the runner selects):

```powershell
python -B tests/run_validation.py
```

- Validation is CI's job: the `validate` workflow's required `Validation` check, across every platform's legs and the known-failure job, is the gate, and a pull request merges only when it passes. Locally, before the pull request, run the suites the change touches one at a time, each new regression test with the fix reverted, ruff and mypy on the changed files, and the title and body checks; `--changed` is optional, never required. Run the full suite locally only when the change's reach warrants it, such as a validation policy or the runner, and reproduce a failed CI leg with `--shard <index>/<count>`. A reach no file name or import shows goes in `CHANGE_REACHES` in `tests/validation/job_selection.py`, never in a list a contributor keeps. "Validation" in `docs/implementing-changes.md` is the procedure and says what each run selects and which legs also need `--full`.
- The gates that call a model (`audit-skill` on a changed skill, the `runtime-canary` lines, and the `evaluate-skill` citation) never run in CI and stay with the author. The `Mutation` workflow's `Mutation gate` job is not a required check: its step summary is the record, so read it, kill or name as equivalent each surviving mutant on a changed line that alters behavior a caller relies on, and copy no result into the pull request.
- `tests/run_validation.py` is the single entry point used locally and in CI. A policy goes in its family's module under `tests/validation/` with a fixture test in that module's suite, `tests/validation/test_<module>.py`, showing a violating input failing and a conforming one passing. A policy that reads Python reads it through `ast` and resolves each name through the module's imports, and a policy check swaps no standard stream and changes neither `os.environ` nor the working directory; "The runner" in `.github/CONTRIBUTING.md` says why and describes the pool, the legs and shards, and how a failure or a termination is reported.
- Suites run in parallel and in shards, so every suite isolates its own temporary home and fixtures, and no test depends on another test's order or state. The root `conftest.py` isolates every Python suite's git, as "Validation" in `docs/adding-a-skill.md` says a test reads and configures it, and no `conftest.py` sits below the root.
- Validation requires the tools "Development environment" in `.github/CONTRIBUTING.md` lists and installs, among them the development dependencies `requirements/requirements-dev.in` pins (`ruff`, `mypy`, `pytest`, and `hypothesis` only, for contributors and CI), while the deployer and shipped skills stay standard-library; `docs/dependency-updates.md` owns the pins.
- Python is formatted and linted with ruff at a line length of 120 and type-checked with mypy, with no file or rule exempt. A finding that must stay is suppressed on its line as `# noqa: <code> - <reason>`, and a type error as `# type: ignore[<code>]  # <reason>`. Function complexity (C901) and length (PLR0915) take no `noqa`: split the function, and lower a ceiling, which only goes down, when the split leaves the maximum below it. `mypy_path` lists each `skills/<name>/scripts` directory a module or suite puts on `sys.path`, and each test directory whose suites import a module beside them by its bare name. "Python checks" in `.github/CONTRIBUTING.md` is the full account.
- Every `.ps1` and Markdown PowerShell fence validation reads passes `Invoke-ScriptAnalyzer -Severity Warning,Error`, and every Markdown Bash fence outside `skills/` and `tests/` passes ShellCheck; write a placeholder in a Bash fence quoted, as in `'<file>'`.

Never work around a failing check. Do not mark tests as expected failures or skipped, weaken or disable a gate, or leave TODO or placeholder comments to land partial work; finish the change so every check passes, or keep it uncommitted. A test that cannot run on a platform is skipped by a condition that reads the platform alone, and any other skip that must stay is sanctioned beside the code as a module-level `SKIP_ALLOWED = {scope: reason}`. Never disable or suppress ShellCheck, PSScriptAnalyzer, ruff, or mypy beyond one finding on its line; fix the cause. The only sanctioned suppression of a shell check is the fragment-lint header `deployer/render.py` adds to Markdown command examples it extracts for validation; PowerShell has none, so rewrite a fence or script so the rule holds, keeping a command example the same command. "Validation" in `docs/adding-a-skill.md` and "Python checks" in `.github/CONTRIBUTING.md` name each marker, comment, directive, and settings file validation refuses.

Add regression coverage for every behavior change. When a token appears in executable content, include a rendered execution fixture with representative values containing spaces and other allowed punctuation: a token in Bash or PowerShell sits inside quotes and is covered by a `tests/deployer/` test named `*with_spaces*`, as "Template values" in `docs/adding-a-skill.md` describes.

A regression suite runs only if its name matches `test_*`, `test-*`, `*_test`, `*-test`, or `*.test.*` with a `.py`, `.sh`, or `.ps1` extension. A Python suite defines at least one test and holds no `if __name__ == "__main__":` block, since the runner starts it through pytest. Run one suite or test as the runner does: "Validation" in `.github/CONTRIBUTING.md` gives the command and the environment it sets. "Validation" in `docs/adding-a-skill.md` states what a suite holds.

Every skill with executable files must include an executable regression suite under its `scripts/` directory. Markdown may use executable-language fences only for command examples of five lines or fewer; extract longer programs into tested files under `scripts/`.

Keep `DOCUMENTATION_FILES` and `DOCUMENTATION_DIRECTORIES` in `tests/run_validation.py` to files no suite executes; Markdown under `skills/`, `agents/`, and `.claude/` is skill and agent behavior, not documentation. "Validation" in `docs/implementing-changes.md` says what a documentation-only change runs.

## Issues and pull requests

- The backlog is this repository's GitHub issues. Write every issue body from the matching template in `.github/ISSUE_TEMPLATE/` (enhancement, bug, documentation, or question) and every pull request body from `.github/pull_request_template.md`, keeping their section headings, to a file passed with `gh issue create --body-file` or `gh pr create --body-file`; `--body` bypasses the template.
- Name each issue the change resolves in its own `Closes #N` line when the pull request is opened.
- A pull request's title becomes its squash commit's title, so it opens with a type (`feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`, or `build`), an optional scope in parentheses, a colon, and a space, as in `fix(deployer): ...`, with no `!`; the type agrees with the worktree's branch kind when the kind is one of them. Check it locally with `--pr-title <file>`.
- A change a user who updates meets, every contract change included, states it under `## Upgrade note` in the pull request body, in the shape `docs/upgrade-notes.md` gives, and never in that file; check it locally with `--pr-body <file>`; given alone, `--pr-title` and `--pr-body` run only the pull request checks named below. A pull request that changes a skill's prompt, description, model guidance, or reviewer instructions cites its `evaluate-skill` run and commits the result it wrote to `docs/skill-evaluations.md`, when the skill has scenarios.
- Before `gh pr create`, run `git fetch origin main` and `git rebase origin/main`, not the local `main`, in the worktree. While the pull request is open, merge `origin/main` into it before pushing more commits, and never rebase or force-push it. If a push is rejected, fetch and inspect the remote branch before anything else: the maintainer may have updated it.

"Pull requests" in `docs/implementing-changes.md` says what each title type covers and how the title, closing-line, upgrade-note, forms-considered, silent-revert, and known-failure closing checks read a pull request.

## Maintaining AI Agent Config

This `CLAUDE.md` is the single canonical, hand-authored instruction source for every agent runtime working in this repository.

- `AGENTS.md` is a hand-maintained Codex wrapper that only redirects to this file. Keep it thin; never copy guidance into it or replace it with a generated adapter.
- Keep this file under 32 KiB, Codex's default `project_doc_max_bytes`, as a budget: Codex loads the root `AGENTS.md` and reads this file through its redirect, which that limit does not govern. State each rule in a sentence or two and point, by its quoted heading and its document, at the section that holds how the rule is enforced, moving any enforcement detail there. `tests/tools/test_claude_md.py` holds the size and that each pointer names a section its document has.
- Claude Code, Codex (through `AGENTS.md`), Copilot CLI/app, and Copilot code review on GitHub.com read these instructions directly, so the repository has no generated projections (no `.github/copilot-instructions.md`, `.github/ai-config-manifest.json`, `.github/scripts/ai_config.py`, or `ai-config-parity` workflow), no parity check, and no `init-ai-config` skill that generated them; "Considered and declined" in `docs/design.md` says why, and when a parity check is reconsidered.

## Source authority

This project directory is the authoritative source for templates, metadata, deployment logic, tests, and documentation. Installed files under `~/.claude/skills/` and any legacy copy under `~/.claude/skill-templates/` are not authoritative and must not be edited as the source of a change. Synchronizing or deploying to those locations must be an explicit operation, never an incidental validation step.
