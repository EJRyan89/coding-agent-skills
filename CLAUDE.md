# Coding Agent Skills Development

This project packages portable Claude Code skills and a guarded deployer.

The deployer is a standard-library Python 3.11.4+ package and supports Windows. On Linux the deployer and the whole validation suite run and `deployable.yml` deploys onto a fresh Ubuntu runner, but Linux support is not claimed until the maintainer's runtime canary runs the skills there; macOS is refused. Configured paths are absolute drive-letter paths on Windows and absolute POSIX paths on Linux, and rendered Bash and PowerShell are validated with Git Bash on Windows or the system Bash on Linux, ShellCheck, and PowerShell. Keep every operating-system-specific behavior in `deployer/platform_support.py` so Unix support is added there without touching the pipeline. The exceptions are what skill-core holds because a skill's script needs it too, and the deployer reads from there: the lookup of a program by its command name, `PATH` and then the platform's package-manager link folders, in `executable_locator.py`, so a skill finds the program `check` reports; the command that runs Python, `PYTHON` in `executable_locator.py`, which `platform_support` re-exports and every skill renders as `{{PYTHON}}`; the process tree that ends every process a command starts, but for one that leaves its process group by starting a session or group of its own, in `job_tree.py`; the probe of whether a process runs and when it started, in `process_identity.py`; and the hint a PDF parser's refusal and `check` add after the parser floors, `INSTALL_HINT` in `pdf_tool.py`, which `deployer/tools.py` puts in its catalogue directly. Validation fails when the deployer, `tools/`, `deploy.py`, or the validation runner names a platform-specific attribute, module, operating-system query, signal, process keyword, environment variable, command, or filesystem path outside it, or strips, appends, or compares an extension Windows finds a program by, which `platform_support.program_name` drops. A module states a sanctioned exception beside the code it excuses, as a module-level `PLATFORM_ALLOWED = {token: reason}`.

## Architecture

- `skills/<name>/` contains immutable skill templates. Never render configuration into this source tree.
- `agents/<name>.md` holds Claude Code subagent definitions that skills declare in `agent_deps`; the deployer installs them to `~/.claude/agents`.
- `skills/<name>/scripts/` is the only permitted location for a skill's executable files. Keep substantial executable logic out of Markdown.
- `deploy-meta/<name>.json` declares each skill's required variables, shared dependencies, same-source skill dependencies, selection visibility, opt-in status, the external tools it runs, required or optional, and its runtime support (`full`, `partial`, or `none` for each of Claude Code, Codex, and Copilot CLI, naming the capability a runtime lacks), in one layout that validation holds. `deployer/runtime_support.py` catalogues the runtimes, the capabilities each offers, and the reader of that declaration; validation derives each skill's needs from its frontmatter and holds the declaration to them. Skills may run only standard commands or declared tools; see "Commands skills may run" in `docs/adding-a-skill.md`. Validation reads the program of every command a Python script starts, and fails on one it cannot read unless the module states why beside the code, as a module-level `COMMANDS_ALLOWED = {scope: reason}` keyed by the function's qualified name or a module-level assignment's target. `deployer/tools.py` is the single catalogue of those tools, the deployment prerequisites, and the runtimes `python deploy.py verify` lists, with their version floors; `python deploy.py check` (`deployer/check.py`) reports them, and the source commit `deployer/source_commit.py` records in the manifest's source entry at each deployment.
- `source.json` may group selectable skills into atomic bundles; the manifest records requested roots separately from their expanded dependency closure and each skill's deployed `skill_deps`. A skipped or preserved skill keeps its recorded transitive skill dependencies and their shared assets and agents.
- `skills/<asset>` contains shared assets declared in `source.json` as either `owner` or `dependency`.
- `skills/skill-core/` is a hidden skill and the one home of the repository's shared Python: skill scripts, the deployer, and `tools/` all import its modules from `skills/skill-core/scripts`, and nothing copies them. It holds one module per concern, such as `console.py`, whose `run_main(main)` is the one call in every entry point's `__main__` block (a skill script, `deploy.py`, or a `tools/` module run as a program) and sets UTF-8 output first, lets a `SystemExit` through, and ends any other exception `main` did not handle with a `FAILED <type>: <message>` line and exit 1, and Ctrl+C with `FAILED interrupted` and exit 130, never with a traceback unless the entry point asks, as `deploy.py`'s `--debug` does, `frontmatter.py`, the frontmatter reader, `github_client.py`, whose `GitHubClient` every `gh` call goes through for one failure classifier and one rate-limit backoff, `git_client.py`, whose `GitClient` every git call from a skill's Python goes through for one failure classifier, both over `bounded_process.py`, which runs a command with no stdin but the bytes its caller gives up front, no prompt, none of git's repository-selecting variables, and a time limit, and, when its caller asks, a bound on the output it keeps and an end to every process the command started that has not left its process group, through a process tree the caller supplies, `skill_roots.py`, the skills directories a script must not write inside and the check for a path in one, and `sibling_scripts`, the one lookup of a sibling skill's `scripts` directory, in the checkout and the deployed home alike, `executable_locator.py`, the one lookup of a program by its command name, `flat_text.py`, the one whitespace flattener for text a script prints on one line, `xml_reader.py`, the one reader of untrusted XML into an element tree, which refuses a document carrying a `DOCTYPE` or `ENTITY` declaration before parsing it, and `git_test_base.py`, the test base every suite that runs git inherits. A dependent declares `skill-core` in `skill_deps` and puts `../skill-core/scripts` on `sys.path`, then puts every other sibling it declares there through `sibling_scripts`, as the suites under `tests/` and the modules under `tools/` do after their own statement; validation fails on a `sys.path` entry that names a sibling's `scripts` by a hand-written path, on a skill script, `deploy.py`, or deployer or `tools/` module whose `__main__` block does not start with that call, resolved through its imports, or that reconfigures a stream's encoding itself, on a script that reaches a sibling it does not declare, or a Python script outside skill-core that runs git or gh itself, and it runs each entry point's `__main__` block as written with its `main` failing, holding the `FAILED` line and the exit codes. `deployer/__init__.py` holds the deployer's one statement putting `skills/skill-core/scripts` first on `sys.path`, located from its own file and never through the configured source path, so every deployer module imports skill-core as skill scripts do; a `tools/` module writes the same statement above its skill-core imports, because ruff sorts them above the deployer's. Validation fails on a module outside skill-core named like a skill-core module, on a deployer or `tools/` import of skill-core without that statement before it, on a skill-core module that imports from the deployer or `tools/`, on a deployer or skill-core import outside the standard library, the deployer, and skill-core, and on a shipped skill script's import outside the standard library, skill-core, its own skill's scripts, and those of the skills its `skill_deps` reach, an import by `importlib.import_module` or `__import__` included.
- `deploy.py` is the single command-line entry point. `deployer/cli.py` routes it, and `deployer/arguments.py` declares its `argparse` parsers.
- `python deploy.py configure` runs `deployer/configure.py`, which writes a strictly parsed, source-specific configuration under `~/.claude/deployer/config/`. `deployer/config.py` is the single declaration of configured and derived variables.
- Any other `deploy.py` invocation runs `deployer/pipeline.py`: it renders selected skills in memory, validates the result, applies journaled multi-root changes, and records source-scoped ownership in `~/.claude/skills/.deploy-manifest.json`. `pipeline.py` orchestrates a run (the lock, recovery, the journal, and the manifest commit) over `deployer/selection.py` (the menu, `--all`, and the checks a selection must pass), `deployer/plan.py` (the per-item plan the dry run prints and the deployment carries out, and the ownership checks before rendering), `deployer/report.py` (report lines and their labels, shared with `check` and `verify`), and `deployer/migrate.py` (`--migrate-from`). `deployer/kinds.py` describes each kind of item (skills, shared assets, runtime adapters, agents) once, and every pass over them iterates it, except where a kind differs: `plan.build` plans skills first and names the kinds that depend on them (a skill left in place keeps what it depends on, and a runtime adapter, which the table marks as following its skill, stays and is skipped with it), `render.Staged` holds each kind's rendered content in its own shape, and the journal records by root, which skills and shared assets share, in its on-disk format. Validation fails on a deployer pass that names a kind's manifest key, report label, or journal root by literal, branches on a kind, or lists kinds by hand, unless its module states why beside the code, as a module-level `KINDS_ALLOWED = {pass: reason}` keyed by the function's qualified name or by a module-level assignment's target; `tests/validation/kinds_table.py` holds it. `deployer/context.py` holds a run's options, selection, and manifest state. Authoritative skills live under `~/.claude/skills`; thin generated runtime adapters live under `~/.agents/skills`.
- Every mutating filesystem operation goes through `deployer/fsops.py`; tests inject failures by replacing those functions. Validation fails when `deploy.py` or another deployer module writes to the filesystem directly, which it finds by resolving each call through the module's imports and simple assignment aliases in its lexical scope, so an alias, an `os.open` with a write flag, an `open` mode it cannot read as read-only, an archive's extraction or creation, an archive, compressed file, or database opened with a mode that may write, a callable named by a literal through `getattr`, `importlib.import_module`, `sys.modules`, a module's `__dict__`, or `operator.methodcaller`, and a write callable, or a module that holds one, passed as a value rather than called each count; `fsops.extract_archive` is the deployer's one extraction. An alias is a name bound to a name or an attribute by an assignment, an assignment expression, an item of a literal tuple or list it is unpacked from or loops over, a parameter's default, or a case that captures its whole subject; a callable alias that is rebound or cannot be resolved, and a call of a callable another call returns or a subscript looks up that no literal names, or of an attribute of a module named by anything but a literal, are reported, never guessed. A module states a sanctioned exception beside the code it excuses, as a module-level `FSOPS_ALLOWED = {token: reason}`; only throwaway files and directories under the system temporary directory qualify, and validation fails on an allowed call that may write elsewhere: a `tempfile` call with a positional argument, a `dir`, or a `prefix` or `suffix` that is not a literal free of path separators, or any other write with a destination argument, any argument that may name where it lands, that is not a name the module binds only to a directory `tempfile.mkdtemp` made there, directly or through `pathlib.Path`, `os.fspath`, or `str`, which keep its path, or with no destination argument, as an extraction into the working directory has.
- Validation fails when a module-level function or class of four or more lines, one in a module-level `if`, `try`, or `with` block included, is defined identically in two non-test Python files under `skills/`, `deployer/`, `tools/`, `.claude/skills/`, or `tests/validation/`, and when two such files assign the same module-level value under any names: a string or bytes literal of twelve or more characters, a pattern `re.compile` builds from a literal, with the same flags, or a tuple, list, or set of literals that together hold twelve or more characters, compared by its members in any order. `__all__` and the `*_ALLOWED` sanction dictionaries are not compared. Import one copy instead. A copy that must stay is sanctioned beside the code in every module that holds it, as a module-level `DUPLICATION_ALLOWED = {name: reason}` keyed by that module's own name for the copy, whose reason says why the module cannot import the other copy; validation fails on a reason that does not name, by repository path, every other file that holds the copy. No allowance sanctions a whole module: a module more than one part of the repository needs moves to skill-core. An entry whose definition or value is no longer copied fails.
- `skills/skill-core/scripts/frontmatter.py` is the one reader for skill and agent frontmatter, imported as `frontmatter` by skill scripts, the deployer, `tools/`, and the tests.
- `python deploy.py verify` (`deployer/verify.py`) checks, without starting a model, that Codex and Copilot CLI each find every manifest-owned runtime adapter, enabled and not shadowed. `deployer/discovery.py` reads each runtime's skill listing (Copilot's `copilot skill list --json`, Codex's app-server `skills/list` request) and is shared with `tools/runtime_canary.py`.
- `tests/deployer/test_*.py` are the deployer suites; their isolated fixture repositories and homes live in `tests/deployer/harness.py`, which fails a test whose deployment changes anything under its source, and one whose expected refusal changes the home, unless the test states why with `changes_home`. `tests/deployer/test_invariants.py` shows both comparisons failing and passing, and holds that a permanent backup survives later deployments and the uninstall.
- `docs/skills.md` is the skill reference. `tools/skill_reference.py` generates its summary table and the first block of each skill's section, and the "Runtime support" table, from `SKILL.md` frontmatter and metadata; the explanation after each block is hand-written. After changing a skill's frontmatter or metadata, run `python tools/skill_reference.py --write`; validation fails while the reference is stale.
- `tools/runtime_prompts.py` renders, from fixtures and with no model, each prompt a skill's script writes for a subagent at runtime (the review-prs and review-document reviewer, the review-insights synthesis) into `docs/runtime-prompts/<skill>/<role>.txt`, with the throwaway folder as `<temp>` and the checkout as `<source>`, where `analyze-skill-cost` measures it. After changing such a prompt, run `python tools/runtime_prompts.py --write`; validation fails while a sample is stale.
- `tools/runtime_canary.py` deploys this checkout and the fixture source in `tests/fixtures/runtime-canary/` into a throwaway home with `deploy.py --canary-home`, then checks that Claude Code, Codex, and Copilot CLI find and run the named skills, and compares each run with the skill's declared runtime support, failing on a disagreement. It calls models, so it is a manual pull request gate run through the `runtime-canary` repository skill, never part of validation. Nothing under `tests/fixtures/` ships, which validation enforces.
- `tools/skill_evals.py` judges a skill's runs of fixed scenarios, model by model: each scenario under `tests/fixtures/skill-evals/<skill>/<scenario>/` is a `scenario.json` of expectations over the review record (a finding at a line and severity, nothing above a severity on clean paths, every finding on given lines, the verdict, and a re-review's ledger) beside what the skill reviews: a code-review fixture (a base and a head tree and a `pull.json`, which `prepare --canary --fixture` reviews), or, for a skill started on one document's path such as `review-document`, a document the `scenario.json` names, with an optional base committed before it in a throwaway checkout. A repository reviewer's scenarios, such as `review-repository`'s, name `review-prs` and the reviewer, and each run places the reviewer's files from the checkout in a throwaway copy of the fixture, so the fixtures hold no copy of the skill. It checks the expectations by script, never from the report, printing `PASS` or `FAIL` per expectation and model and a table. It deploys this checkout into a throwaway home per model with `deploy.py --canary-home`, sets that model on the home's reviewer agent, passes that agent to the session with `--agents` with its hook on the home's reviewer guard (a headless session runs no hook of a project agent), runs each scenario through the skill in a headless Claude Code session on the strongest model, and judges the record the run finalized; `--records` judges records written before. Its `MODELS` constant is the one place the models are named. It calls models, so it is a manual pull request gate run through the `evaluate-skill` repository skill, never part of validation, and `--write` replaces the skill's rows in `docs/skill-evaluations.md`, the latest result per skill and model. `tests/tools/test_skill_evals.py` covers it with a stub Claude Code and no model.
- `.github/workflows/deployable.yml` is a check on a fresh `windows-latest` runner and, in its `deployable-linux` job, a fresh `ubuntu-latest` one, that runs on dispatch and weekly, the day after `validate.yml`'s weekly run, on the README's versions and on the latest release of every runtime; a scheduled failure is a signal the maintainer reads, never a required check, and the README's fresh-runner column records the last dispatched release run, not a weekly one. Each run it installs the prerequisites and the runtimes, deploys into the runner's real profile (not `--canary-home`, because Codex on Windows reads the real profile, and `HOME` on Linux), runs `deploy.py verify`, uninstalls, and deploys again; the Linux job is the Windows one in Bash without its Codex settings step, which `tests/validation/workflows.py` holds. `tools/deployable_report.py` judges Codex and Copilot discovery (`PASSED`, `SKIPPED` when it will not list skills without a sign-in, `FAILED`), checks Claude Code's installed version and the deployed file layout (it has no skill listing without a session), names every path the manifest owned or the deployment made, files included, that the uninstall left, and writes the step summary; `tests/tools/test_deployable_report.py` covers it. It starts no model and uses no secret, and validation pins its triggers, its cron, permissions, action pins, runtime versions, each verify report's `--deploy-verify-log` to the `verify-first.log` or `verify-second.log` its own step saves, and, in both jobs, the uninstall between the first deployment's layout check and the step that reports what was left.
- `tools/release_notes.py` writes a release's section of `docs/upgrade-notes.md` from the upgrade notes of the commits since the previous tag, and `tests/validation/upgrade_notes.py` reads the same entries; "Before tagging" in `docs/releasing.md` runs it.
- `tools/worktrees.py` coordinates parallel sessions (creating task worktrees, surveying them, and the hub guard hook declared in `.claude/settings.json`), `tools/new_skill.py` scaffolds a new skill's frontmatter, metadata, and reference section, or, with `--repository`, a repository skill and its shim, and `tools/skill_shims.py` writes and checks the shims; `tests/tools/test_*.py` are the suites for `tools/`.
- `.claude/skills/<name>/` holds this repository's own skills, for working on it rather than for deployment. Each has a shim in `.agents/skills/<name>/` with the same frontmatter for Codex and Copilot, which validation enforces. A shim is written by `tools/skill_shims.py` from its repository skill's frontmatter and points at the skill, and validation compares each shim with what the tool writes; an adapter is what the deployer generates under `~/.agents/skills` for a deployed skill. Keep the two words distinct. Repository skills meet the shipped-skill standard: validation applies the fence-length, output-placeholder, grant, and description policies to them, and a change to one runs `analyze-skill-cost` on it ("Validation" in `docs/adding-a-skill.md`). `review-repository` is this repository's own pull request reviewer: its specialists manifest routes the deployer, the skills and their metadata, the validation policies, the trust-boundary files, and the documents to reviewers briefed on `docs/design.md`, and `review-prs` runs it once a machine's code-review configuration names it.
- `docs/design.md` owns why the repository is built this way (the trust model, the invariants, and each decision with its reason and date), and a change that bends an invariant or revisits a decision updates it in the same pull request.

A document names what the repository holds or does and never counts it, and states no date or version in guidance; a reader who needs the number takes it from the generated reference or a command, and a "checked on" or "as of" date is replaced by the thing checked. The exceptions are the places that own a date or version as the record: a decision's date in `docs/design.md`, a release's section in `docs/upgrade-notes.md` and its notes, and the README's supported-runtimes table and the date of its fresh-runner run, which "Before tagging" in `docs/releasing.md` maintains.

To add or change a skill, follow the `change-skill` repository skill. It applies `docs/adding-a-skill.md`, the skill contract, one section at a time: read the section each step names before acting on it.

## Safety requirements

- Do not modify installed skills under `~/.claude/skills`, installed agents under `~/.claude/agents`, generated adapters under `~/.agents/skills`, or user-managed Copilot skills under `~/.copilot/skills` while developing or testing this project.
- Use an isolated temporary home for deployment fixtures and canaries: `--canary-home`, or `Paths` built on a temporary directory. `deployer/platform_support.py` takes the home from the Windows profile folder on Windows, so setting `HOME` alone does not isolate a run there.
- Preserve immutable template sources and verify source hashes when testing rendering.
- Never source or execute configuration files; keep parsing restricted to validated `KEY=VALUE` entries.
- Treat tokens used in Bash, PowerShell, JSON, YAML, or other executable/structured contexts according to that context. Universal raw substitution is not sufficient.
- Reject unresolved tokens, unsafe names and paths, ownership collisions, and invalid shared dependencies before mutation.
- Preserve journaled rollback, recovery, locking, manifest ownership, and permanent backup behavior.
- Do not add personal paths, internal organization names, credentials, or generated deployer state.
- Do not change the source ID without an explicit ownership-migration plan.

## Parallel sessions

Several sessions may work in this repository at once, and sessions that share a checkout share a HEAD and a working tree, so one session's branch switch or commit carries another's uncommitted edits. Each task therefore gets its own worktree; see `docs/parallel-sessions.md`.

- The main checkout is the hub. It stays on `main`, stays clean, and is never edited. It is used only to pull `main`, create and retire worktrees, survey, and deploy.
- Start a task with `python tools/worktrees.py new <kind> <name>`, which creates `.claude/worktrees/<kind>-<name>` (gitignored) on branch `<kind>/<name>`. Then move the session into it (in Claude Code, `EnterWorktree` with that path) before editing. `python tools/worktrees.py list` surveys every worktree.
- Integrate through a pull request pushed from the worktree, never through a merge in the hub. After it merges, retire the worktree from a session outside it with `repo-cleanup` on the hub, which also fast-forwards `main`; see "Retiring a worktree" in `docs/parallel-sessions.md`. By hand, run `git worktree remove <path>` and `git branch -D <kind>/<name>`. A squash merge leaves the branch looking unmerged, so `-d` refuses.
- Deploy only from the hub on `main`. A deployment records its source path, so `deploy.py` refuses to deploy from a linked worktree; `--dry-run` and `--canary-home` (a throwaway home under the temporary directory) still work there.
- When one session orchestrates several task sessions, a session in the hub keeps their pull requests merging with the `shepherd-pull-requests` repository skill, one tick at a time; see "An orchestrator and a shepherd" in `docs/parallel-sessions.md`.
- Never pop or drop a stash you did not create: the stash stack is shared by every worktree.
- In a clone that opts in with `git config coding-agent-skills.hubGuard true`, the Claude Code hook in `.claude/settings.json` refuses edits to the hub, git commands that would move its HEAD or write its tree, and a git command it cannot place while a hub is guarded; "The guard's contract" in `docs/parallel-sessions.md` names what it reads, refuses, and does not see. Other runtimes do not run the hook, so for them these rules are the guard.
- `.claude/settings.json` is tracked and may hold `$schema`, hooks, and `attribution` only. Its `attribution` turns off Claude Code's commit trailers, pull request footer, and session links, so commits and pull requests made here carry none. Permissions and every other setting belong in each developer's user or `settings.local.json` settings. Validation fails on any other top-level key, a `$schema` other than Claude Code's settings schema, an `attribution` other than `{"commit": "", "pr": "", "sessionUrl": false}`, and a committed `settings.local.json`.

## Required validation

The validation command, which CI runs in full on every push and on every pull request that is not documentation-only (a documentation-only pull request runs the subset the runner selects, below):

```powershell
python -B tests/run_validation.py
```

Validation is CI's job: the `validate` workflow's required `Validation` check is the gate, and a pull request merges only when it passes. It needs every Windows leg and the `Validation on Linux` job, which runs all of it unsharded on `ubuntu-latest`, so a failure on either platform fails it. The workflow adds `--full` on every event but a pull request, so a push runs every suite, and a pull request runs every suite unless every file it changes is documentation, as below. Locally, run `python -B tests/run_validation.py --changed`: from the files changed since `origin/main`, committed, uncommitted, or untracked, it selects the policy checks, the static checks that read the kinds of file changed (the format, lint, and type checks for Python), and the suites the change reaches: a changed suite, a suite that imports a changed module directly or through others, one that names a changed file or such an importer, one in the `scripts/` of the skill a changed file sits in, and the suites `CHANGE_REACHES` in `tests/validation/job_selection.py` adds, such as the deployer's rendering suite for a change under `skills/` and the suites that read the floors for a change to a tool floor. A reach no file name or import shows goes in that table, never in a list a contributor keeps. Run the full suite locally only when the change's reach warrants it, such as a validation policy or the runner, and reproduce a failed CI leg with `--shard <index>/<count>`, the leg's own index and the workflow's leg count, adding `--full` for a push, schedule, or dispatch leg, which the workflow runs with it: the runner deals the legs after it selects, so without `--full` a branch whose changes are all documentation deals a different leg. "Validation" in `docs/implementing-changes.md` is the procedure. The gates that call a model (`analyze-skill-cost` on a changed skill, the `runtime-canary` lines, and the `evaluate-skill` citation) never run in CI and stay with the author.

`tests/run_validation.py` is the single entry point used locally and in CI. The policies it runs live in `tests/validation/`, one module per policy family, beside `job_pool.py` (the pool of workers), `job_selection.py` (what a run selects), and `validation_support.py` (what they share). A policy module holds its policy functions and the checks that apply them to this repository, which the runner loads as the policy checks and runs in its own process. Beside each is its fixture suite, `tests/validation/test_<module>.py`, which shows a violating input failing and a conforming one passing and runs in the pool like any other suite. A new policy goes in its family's module with a fixture test in that suite. A policy that reads Python reads it through `ast` and resolves each name through the module's imports. The runner starts one pool of workers on the static shell checks, the PowerShell analyzer, the Python format, lint, and type checks, and every regression suite under `tests/` (outside `tests/fixtures/`) and each skill's `scripts/`, and runs the repository layout policies in its own process while the pool works, printing their report as one block when they finish. A policy check, the runner's own included, therefore swaps no standard stream and changes neither `os.environ` nor the working directory, which the pool's jobs start from and print to meanwhile: it takes a stream or an environment as a parameter, or moves into a regression suite, and `pool_shared_state_problems` in `tests/validation/suite_discovery.py` holds the rule. A skill is `skills/<name>` holding `SKILL.md`, as `deployer/source.py` finds it, or a repository skill under `.claude/skills/`, whose `scripts/` is found, laid out, linted, and type-checked as a shipped skill's is. A job that raises anything other than a failed check is reported as a failed job with its traceback, in the output and in the CI step summary. A job whose program, Git Bash, PowerShell, ShellCheck, or any other the runner starts, is ended with a termination status (one Windows sets when an exception or another process ends it, or elsewhere the signal that ended it, never the program's own exit code, read by `platform_support.termination_status`) before its first line of output is reported as that program's termination, naming the status in hexadecimal, or the signal by its name, and the command, not as a failed check, and is started once more: the output and the step summary name the retry and its result, and a second termination fails the job. A job that wrote output, or that ran and failed, is never started again. The runner starts Git Bash as a plain shell, not a login one, as every other start of it in the repository does. Pass `-k <pattern>` to run the policies and suites whose name or path matches; a selection that matches neither is refused with exit 2 rather than passing empty, and `-k` does not combine with `--changed`. `--shard <index>/<count>` runs one leg of a run split across CI's runners: `tests/validation/job_selection.py` deals the selected policy checks and suite jobs across the legs, heaviest first onto the lightest, the same way on every leg, so the legs together run each once, and the `validate` workflow runs one leg per entry of its shard matrix. A job weighs the seconds `tests/validation/job_seconds.json` records for it, the median of its seconds across several recent completed `validate` runs on `main`, which `tools/record_job_seconds.py` rewrites at each release, or, when it has no entry, a count of typical tests: a Python suite's test count, or, for an unsplit job (a static check, or a Bash or PowerShell suite, which has no test count the runner reads), the fixed `UNSPLIT_JOB_COST` in `tests/validation/job_selection.py`; validation fails on an entry that names no job. Suites run in parallel, and `tests/run_shard.py` splits each large Python suite into shards run in separate processes, giving a test whose cost `RECORDED_TEST_SECONDS` in `tests/validation/suite_discovery.py` records a shard of its own, so every suite must isolate its own temporary home and fixtures, and no test may depend on another test's order or state. A Python suite that runs git, itself or through a repository module it imports, isolates it from the shell that started it: every test class inherits `git_test_base.GitTestCase` from skill-core, which gives each test and each class fixture its own `HOME` and global configuration with the fixture identity, an empty hooks folder, and git's automatic maintenance off, no system configuration, and none of the shell's other `GIT_*` variables; a `setUpClass` starts with `super().setUpClass()`, and every `setUpModule` starts with `git_test_base.isolate_module()`. `git_isolation_problems` in `tests/validation/suite_discovery.py` fails a suite that does not, and "Validation" in `docs/adding-a-skill.md` states the rule. It requires Python 3.11.4 or newer, Git Bash, ShellCheck, PowerShell 7 (`pwsh`), the PSScriptAnalyzer module, installed from `pwsh` with `Install-Module PSScriptAnalyzer -Scope CurrentUser -Force`, and the development dependencies pinned in `requirements-dev.txt`, installed with `python -m pip install -r requirements-dev.txt`. Those are `ruff` and `mypy` only, for contributors and CI; the deployer and shipped skills stay standard-library. Validation runs `ruff format --check` and `ruff check` at a line length of 120 on `deployer/`, `tools/`, `tests/`, `skills/`, `.claude/skills/`, and `deploy.py`, excluding no file; run `python -m ruff format` to fix what the first names, and fix each finding the second names. `pyproject.toml` holds the lint rule set and exempts no rule or file; a finding that must stay is suppressed on its line as `# noqa: <code> - <reason>`, and validation fails on a `noqa` without its codes and reason. Function complexity (C901) and length (PLR0915) take no `noqa`, and validation fails on one that names either: split the function instead, and lower their ceilings in `pyproject.toml`, which only go down, and the literals `tests/validation/python_checks.py` pins for them when a split leaves the maximum below them. Validation also runs mypy with `pyproject.toml`'s `[tool.mypy]` configuration, once on `deployer/`, `tools/`, `deploy.py`, and `tests/` together and once on each shipped or repository skill's `scripts/` directory from inside it, and fails on any error, regression suites included. An error that must stay is suppressed on its line as `# type: ignore[<code>]  # <reason>`, and validation fails on a `type: ignore` without its codes and reason. `mypy_path` lists each `skills/<name>/scripts` directory a module or suite puts on `sys.path`, and each test directory whose suites import a module beside them by its bare name, which validation enforces. Validation runs `Invoke-ScriptAnalyzer -Severity Warning,Error` on every `.ps1` under `tools/`, `tests/`, `skills/`, and `.claude/skills/` and on every PowerShell fence in Markdown outside `tests/`, and names each finding's file, line, and rule. It runs ShellCheck at warning severity on every Bash fence in Markdown outside `skills/` (rendered and checked at deployment) and `tests/`, each under the fragment-lint header `deployer/render.py` adds, and names each finding's file, line, and code; write a placeholder in a Bash fence quoted, as in `'<file>'`. `docs/dependency-updates.md` owns the pins, and "Python checks" in `CONTRIBUTING.md` is the full account of the format, lint, and type checks.

Never work around a failing check. Do not mark tests as expected failures or skipped, weaken or disable a gate, or leave TODO or placeholder comments to land partial work; finish the change so every check passes, or keep it uncommitted. `tests/validation/workarounds.py` holds the markers and the comments: in the Python under the format roots outside `tests/fixtures/`, validation fails on a unittest or pytest skip or expected-failure marker, resolved through the module's imports, and a `skipTest` call, unless it is a unittest `skipIf` or `skipUnless` whose condition reads the platform alone, or its module sanctions it beside the code as a module-level `SKIP_ALLOWED = {scope: reason}` keyed by the function's or class's qualified name; and on a comment that says `TODO`, `FIXME`, or `XXX`. A test a class body defines under an `if` on the platform is not a skip. Never disable or suppress ShellCheck or PSScriptAnalyzer diagnostics to make validation pass; fix the cause. The only sanctioned suppression is the fragment-lint header `deployer/render.py` adds to Markdown command examples it extracts for validation. PowerShell has no such header: a fence is analyzed as written, so never add a `SuppressMessageAttribute`, a settings file that disables rules, or any other way of silencing a rule; rewrite the fence or script so the rule holds, keeping a command example the same command. Validation fails on a ShellCheck `disable` directive in a Bash file or a Markdown Bash fence, a `SuppressMessageAttribute` in a `.ps1` file or a Markdown PowerShell fence, a `.shellcheckrc` or `PSScriptAnalyzerSettings.psd1` file, a Python comment that turns a check off beyond one finding on its line (mypy's inline `# mypy:` configuration, ruff's file-level `# ruff: noqa` or `# flake8: noqa`, ruff's range `# ruff: disable[...]`, an isort skip, or the formatter's `fmt: off`, `fmt: skip`, or `yapf: disable`), and a `ruff.toml`, `.ruff.toml`, or `pyproject.toml` anywhere but the repository root.

Add regression coverage for every behavior change. When a token appears in executable content, include a rendered execution fixture with representative values containing spaces and other allowed punctuation. For a token in Bash or PowerShell, validation requires it to sit inside quotes and requires a `tests/deployer/` test named `*with_spaces*` that carries the token in a string literal, runs the rendered result with that language's shell through `run_tool`, and asserts the output against a value containing a space.

A regression suite runs only if its name matches `test_*`, `test-*`, `*_test`, `*-test`, or `*.test.*` with a `.py`, `.sh`, or `.ps1` extension, and a Python suite must end with an `if __name__ == "__main__":` block that calls `unittest.main()`; validation fails on a Python suite whose last top-level statement is not that block or whose block does not call it, and "Validation" in `docs/adding-a-skill.md` states these rules, which validation checks it does.

Every skill with executable files must include an executable regression suite under its `scripts/` directory. Markdown may use executable-language fences only for command examples of five lines or fewer; extract longer programs into tested files under `scripts/`.

The runner decides what a documentation-only change needs. When every file changed since `origin/main` (the pull request's base in CI), uncommitted or untracked, is under `docs/` or `.github/ISSUE_TEMPLATE/`, or is the top-level `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CLAUDE.md`, `AGENTS.md`, or `.github/pull_request_template.md`, it runs the policy checks and only the suites that name a changed file, and, when any changed file is Markdown, the PowerShell analyzer and the ShellCheck check of Markdown Bash fences, since those read the fences a documentation change can break. The Python format, lint, and type checks and the shell checks of skill scripts do not run, since no documentation file reaches them. Any other change, or one it cannot determine, runs every suite, and so does `--full`, which the workflow passes on a push. Markdown under `skills/`, `agents/`, and `.claude/` is skill and agent behavior, not documentation. Keep `DOCUMENTATION_FILES` and `DOCUMENTATION_DIRECTORIES` in `tests/run_validation.py` to files no suite executes.

## Issues and pull requests

The backlog is this repository's GitHub issues. Write every issue body from the matching template in `.github/ISSUE_TEMPLATE/` (enhancement, bug, documentation, or question) and every pull request body from `.github/pull_request_template.md`, keeping their section headings. Write the body to a file and pass it with `gh issue create --body-file` or `gh pr create --body-file`: `--body` bypasses the template, and a file avoids shell quoting of backticks and `$`. Name each issue the change resolves in its own `Closes #N` line when the pull request is opened. A pull request's title becomes its squash commit's title, so it opens with a type (`feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`, or `build`), an optional scope in parentheses, a colon, and a space, as in `fix(deployer): ...`, with no `!`; the type agrees with the worktree's branch kind when the kind is one of them. Validation's title check reads it, locally from `--pr-title <file>` and in CI from the event payload; "Pull requests" in `docs/implementing-changes.md` says what each type covers. A change a user who updates meets, every contract change included, states it under `## Upgrade note` in the pull request body, in the shape `docs/upgrade-notes.md` gives, whose `Contract:` field is the one statement of how an entry names a skill's argument, status line, or exit code, and never in that file: the squash merge carries the body into `main`, and `tools/release_notes.py` writes each release's section from the merged commit messages. Validation's upgrade-notes check reads the body (locally from `--pr-body <file>`, otherwise the branch's commit messages) and the commits since the last tag. A pull request that changes a skill's prompt, model guidance, or reviewer instructions cites its `evaluate-skill` run and commits the result it wrote to `docs/skill-evaluations.md`, when the skill has scenarios.

A pull request stays current with `main`. Before `gh pr create`, run `git fetch origin main` and `git rebase origin/main` in the worktree; the branch is unpublished, so the rebase rewrites nothing anyone has. Rebase onto `origin/main`, not the local `main`, which is only as fresh as the hub's last pull. While the pull request is open, merge `origin/main` into it before pushing more commits, and never rebase or force-push it. Bringing the branch current needs no local rerun: CI validates the result. `gh pr update-branch` is one way to merge `origin/main` into an open pull request; it moves the remote branch, so the worktree pulls before its next push. If a push is rejected, fetch and inspect the remote branch before anything else: the maintainer may have updated it.
