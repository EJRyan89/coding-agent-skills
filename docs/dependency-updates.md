# Dependency updates

This document owns every dependency the repository pins or checks against a floor: where each is declared, how it is updated and reviewed, and the check that fails when it drifts. Change a pin or a floor here and in its declaration in the same pull request, then run the complete validation:

```powershell
python -B tests/run_validation.py
```

## Validation tools

`tests/run_validation.py` stops before running any test when one of these tools is missing or older than its floor, and names the tool, the version it found, and the floor. CI's Windows legs and its Linux legs install ShellCheck, PSScriptAnalyzer, ruff, mypy, and pytest at their floors, so each of those floors is exercised on every run on both platforms, and Python at the newest release of its floor's minor version, as the Python row says. Each leg's verify step prints every tool's version and fails unless the ShellCheck validation runs and the PSScriptAnalyzer it loads are the pins.

## Development dependencies

Validation and CI take these Python packages from PyPI, pinned in `requirements-dev.txt`, and no others: `ruff`, the formatter and linter, `mypy`, the type checker, and `pytest`, the test runner, which starts every Python suite, with the packages each of them needs. They are contributor and CI dependencies only. The deployer and every shipped skill stay standard-library, so deploying needs neither. Install them into the interpreter that runs validation:

```powershell
python -m pip install -r requirements-dev.txt
```

`pyproject.toml` configures the tools and installs nothing, so it has no `[project]` table. [Python checks](../CONTRIBUTING.md#python-checks) in the contributing guide states what validation runs with them and how to fix what each check names.

`requirements-dev.in` is the file a person edits: it pins those packages, and nothing else. `requirements-dev.txt` is the lock compiled from it, which pins every package they install, the ones they depend on included, each with the sha256 hash of every file PyPI holds for its version, so one lock installs on Windows and Linux and on each Python CI runs. pip installs a file that holds hashes in hash-checking mode, where it refuses a package the file does not pin and a download whose hash it does not hold, and CI passes `--require-hashes` as well, so two runs on one commit install the same files, and a new release of any package, a dependency's included, reaches CI only through a pull request that changes the lock. CI also passes `--only-binary :all:`, so it installs wheels alone and never builds a source distribution, whose build runs that package's own code, where a Python has no wheel: a pin is raised only to a version with a wheel for every Python and platform CI runs. `hash_install_problems` in `tests/validation/toolchain.py` fails on a `pip install` in `validate.yml` or `mutation.yml` that does not read `--require-hashes --only-binary :all:` followed only by a lock, and `lock_problems` beside it fails on a lock that holds anything but `name==version` with sha256 hashes, or that pins a package its input pins at another version.

### Compiling a lock

A lock is compiled with [pip-tools](https://github.com/jazzband/pip-tools)' `pip-compile`, which is BSD-3-Clause-licensed, maintained in the open, free of charge, and sends nothing anywhere but the package index pip reads, and whose lock files Dependabot updates natively. It is the one tool a contributor needs only to change a pin: neither validation nor CI installs it, so it is not in either lock. Install it into a virtual environment of its own, outside the checkout and apart from the interpreter that runs validation, so it adds nothing there:

```powershell
python -m venv $HOME/.venvs/pip-tools
$HOME/.venvs/pip-tools/Scripts/python -m pip install pip-tools==7.6.2
```

On Linux, the interpreter is `~/.venvs/pip-tools/bin/python`. Then edit the input and compile each lock from the repository root with the command its header names, the development lock first, since the mutation lock reads it:

```powershell
$HOME/.venvs/pip-tools/Scripts/python -m piptools compile --generate-hashes --allow-unsafe --strip-extras --no-emit-index-url requirements-dev.in
$HOME/.venvs/pip-tools/Scripts/python -m piptools compile --generate-hashes --allow-unsafe --strip-extras --no-emit-index-url requirements-mutation.in
```

Compile on Windows: pytest and click need `colorama` there only, and a lock compiled on Linux leaves it out, so the Windows legs would refuse to install. Without `--upgrade`, `pip-compile` keeps every pin the lock already holds that the input still allows, so a change to one pin moves only what that pin needs; `--upgrade-package <name>` moves one dependency on its own. Commit the input and the locks together.

Dependabot (`.github/dependabot.yml`) checks `requirements-dev.in` and its lock weekly, on the same cadence as the actions, and groups the bumps into one pull request, with security updates in their own group. ruff, mypy, and pytest are each MIT-licensed, maintained in the open, free of charge, and sends nothing anywhere, which the repository's rule for a dependency requires. pytest came with the move of the suites onto it ([#1275](https://github.com/EJRyan89/coding-agent-skills/issues/1275)); no parallel or splitting plugin came with it, because the runner's pool already runs the suites side by side in processes of their own, and the runner already deals the legs and a suite's shards by recorded seconds. A new development dependency is a decision recorded here first, and then added to `DEVELOPMENT_PACKAGES` in `tests/validation/toolchain.py`: `test_ci_exercises_each_floor` fails on every line of `requirements-dev.in` that is not a comment, a blank line, or `name==version` for a package that list names, so an unpinned package, another index, an included requirements file, or an install from a repository cannot enter it. A package one of them comes to depend on needs no decision: it enters the lock when the lock is compiled, pinned and hashed, and a pull request shows it.

### After a Dependabot pull request for ruff

Dependabot changes `requirements-dev.in` and recompiles the locks that hold the package; `lock_problems` fails unless both moved together. A ruff bump raises the floor with it. In the same pull request, set `VALIDATION_FLOORS` in `tests/validation/toolchain.py`, the row above, and the pin `test_ci_exercises_each_floor` checks to the new version, then run `python -m ruff format` on the format roots and commit the result on its own, and fix anything `ruff check` newly names in a commit of its own. Run the complete validation before merging.

### After a Dependabot pull request for mypy

Dependabot changes `requirements-dev.in` and recompiles the locks that hold the package; `lock_problems` fails unless both moved together. A mypy bump raises the floor with it. In the same pull request, set `VALIDATION_FLOORS` in `tests/validation/toolchain.py`, the row above, and the pin `test_ci_exercises_each_floor` checks to the new version, then fix each error the type check newly names, one commit per root. Run the complete validation before merging.

### After a Dependabot pull request for pytest

Dependabot changes `requirements-dev.in` and recompiles the locks that hold the package; `lock_problems` fails unless both moved together. A pytest bump raises the floor with it. In the same pull request, set `VALIDATION_FLOORS` in `tests/validation/toolchain.py`, the row above, and the pin `test_ci_exercises_each_floor` checks to the new version, read the release's changelog for changes to collection, fixtures, and the unittest support the suites rely on, and for any new strictness option, which `strict = true` in `pyproject.toml` turns on with the bump, so name it beside the others there and in [Validation](../CONTRIBUTING.md#validation), and fix anything `tests/test_conftest.py` or a suite newly fails on. Run the complete validation before merging.

## Mutation tools

The mutation gate (`tools/mutation_gate.py`, run by `.github/workflows/mutation.yml` on every pull request) takes two more packages from PyPI, pinned in `requirements-mutation.in`, on Linux. That input takes `requirements-dev.in` whole and `requirements-dev.txt` as a constraint, so its lock, `requirements-mutation.txt`, holds the development dependencies at the versions and hashes their own lock holds, and the mutation tools with everything they need; it is the one file that workflow installs, with `--require-hashes --only-binary :all:`, and `lock_problems` holds every package the development lock pins to the same version and hashes in it. [Compiling a lock](#compiling-a-lock) compiles it. They stay out of `requirements-dev.txt` because mutmut refuses to run on Windows, where contributors validate, and the `libcst` it parses with needs a PyYAML wheel that not every Python a contributor runs has; validation never imports either. The gate makes its mutants with mutmut's operators but runs the suites itself (the gate's docstring says why), so it reads mutmut's `create_mutations`, whose `covered_lines` filter keeps the mutants to the changed lines, and checks a canary mutant before every run, made on its line and on no other, which fails the gate rather than quietly making fewer mutants, or mutating whole modules again, after a release changes it.

| Tool | Pin | Declared in | How it is reviewed |
|---|---|---|---|
| mutmut | 3.8.0 | `requirements-mutation.in` | BSD-3-Clause, maintained in the open, free of charge, and sends nothing anywhere. Dependabot proposes new releases with the development dependencies; the gate's run on that pull request is the review, since its canary and its summary show whether the release still makes the mutants. |
| coverage.py | 7.16.2 | `requirements-mutation.in` | Apache-2.0, maintained in the open, free of charge, and sends nothing anywhere. The gate needs the `.pth` file its wheel installs, which starts measuring each process a suite starts from the file `COVERAGE_PROCESS_START` names, and that file's expansion of `PYTEST_CURRENT_TEST` in each process, which names the test that started it. A release that drops either fails the gate visibly, since its measurement canary runs before every reach pass and stops the run with a `FAILED` line when the canary suite's own process or the process its test starts goes unmeasured or unnamed. Raise the pin as Dependabot proposes, after the gate's run on that pull request still measures each suite's reach. |

`MUTATION_PACKAGES` in `tests/validation/toolchain.py` holds the input to these two pins and its two includes, and nothing else, as `DEVELOPMENT_PACKAGES` holds `requirements-dev.in`, and the toolchain policy holds this table to the file.

## Runtime tool floors

`python deploy.py check` reports each tool a skill declares and each runtime `python deploy.py verify` lists, with its version, and marks one older than its floor `OUTDATED`, and one with a floor whose version probe fails or prints no version `UNUSABLE` with the probe's reason, as it marks a `pdftotext` it cannot identify, because a version it cannot read is no evidence that the floor is met. `verify` reports a runtime below its floor as `OUTDATED` instead of listing its skills, and lists one whose version it cannot read, because the listing is its own evidence: a copy the listing does not say is enabled is reported disabled. Feature floors live in `deployer/tools.py` (`SKILL_TOOLS`, `VERIFY_TOOLS` for the runtimes `verify` lists, or `REPORTED_TOOLS` for Claude Code); raise one when a skill, an agent, or `verify` starts using a newer feature, with a comment naming it. The native PDF parser instead has provider-specific maintained-release support floors in `skills/ejryan89-skill-core/scripts/pdf_tool.py`, referenced by that catalogue and enforced by the same probe at extraction time. Review each provider's official release history before raising its floor, record the evidence and limitations in [Design](design.md), and include the upgrade obligation in the pull request body. `tests/deployer/test_check.py` holds this table, the catalogue, and the shared policy to the same floors; the upgrade-notes guard covers both floor locations.

These are supported baselines, not complete vulnerability certifications or assertions that every cited fix is reachable through text extraction. [The design decision](design.md#decisions) records the vendor evidence. The check that holds these floors is that probe, run on each parser ejryan89-skill-core's one locator, `skills/ejryan89-skill-core/scripts/executable_locator.py`, finds, in its search order: every `pdftotext` on `PATH`, then, on Windows, the one in WinGet's Links folder. `check` and every extraction take the first one the probe accepts and name each one they passed over, with what its probe found and where it was found, so a parser `check` accepts is the one an extraction runs in the same environment. Versions are named as each vendor numbers them, with Xpdf's minor version and Poppler's month in two digits, and compared as numbers. When the probe accepts none, `check` reports an identifiable older parser as `OUTDATED`, and an unidentifiable or failed probe as `UNUSABLE`. The floors are not lowered for a distribution's `pdftotext`, which keeps a version below Poppler's floor as it backports fixes, so on Linux `check` and every refusal name the Xpdf command-line tools after the floors. Every extraction repeats the bounded probes on the executables the locator currently finds, before writing document bytes, then executes the accepted absolute path. A Git-bundled parser below its provider's floor, such as the one Git Bash puts ahead of the Windows `PATH`, is passed over rather than upgraded: a supported, user-managed installation anywhere the locator looks is used instead, and deployment never installs or upgrades one.

## GitHub Actions

Every action in `.github/workflows/validate.yml` is pinned to a full commit SHA with its version in a comment beside it. Dependabot (`.github/dependabot.yml`) checks the pins weekly and groups the bumps into one pull request; with Dependabot security updates enabled for the repository, a security advisory opens its own grouped pull request. Review the upstream release notes and the proposed commit before merging, and keep the version comment.

Each Windows leg and each Linux leg installs the same tools, so `actions/cache` keeps ShellCheck and the PSScriptAnalyzer module under a key that names the runner's operating system and the pinned version, and a leg whose key hits installs neither from the network; `setup-python` keeps pip's downloads under a key built from `requirements-dev.txt`, the lock. Raising a pin changes the key, so the next run installs the new release and caches it; nothing else needs clearing. The Linux image already ships PSScriptAnalyzer for all users, and `Install-Module` of a version in use installs nothing, so each Linux leg first asks `Get-Module -ListAvailable` whether the pinned version is there, and restores the cache and installs the module only when it is not; the verify step checks the result either way. `tests/validation/workflows.py` holds each key to the `env` pin its install reads, and the Linux cache and install to that reading.

`.github/workflows/deployable.yml`, `.github/workflows/mutation.yml`, `.github/workflows/runtime-command-lines.yml`, and `.github/workflows/runtime-changelogs.yml` pin their actions the same way, and Dependabot bumps them in the same grouped pull request. `tests/run_validation.py` fails unless every action each shares with `validate.yml` carries the same SHA and version comment, so a Dependabot pull request that touches only one of them cannot merge green. The Claude Code, Codex CLI, and Copilot CLI versions `deployable.yml` installs by default, `claude-version`, `codex-version`, and `copilot-version` and the fallback a scheduled run uses, are the README's fresh-runner column; [Tested runtimes](#tested-runtimes) states the check that holds them.

### After a Dependabot pull request

No file outside the workflows carries these pins, so the pull request needs no follow-up commit. Once its CI passes and the review above is done, merge it.

## Runner image

CI runs on `windows-latest`, with the Linux legs of `validate.yml` and the `deployable` workflow's Linux job on `ubuntu-latest`, which GitHub updates on its own schedule, along with the Bash, PowerShell, and Python patch releases on them. CI runs on every push to `main` and weekly as well as on pull requests, so an image change surfaces within a week even when no pull request is open, and each leg's verify step prints every tool's version for comparison with the last green run. Pin a dated image such as `windows-2025` or `ubuntu-24.04` only to unblock CI, and open an issue to return to the latest one.
