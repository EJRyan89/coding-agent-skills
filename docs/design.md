# Design

This page says why the repository is built the way it is. It owns the reasons; the documents it points at own the rules themselves, and the code and tests own the behavior. [CLAUDE.md](../CLAUDE.md) states what each part is and where it lives, [Adding a skill](adding-a-skill.md) is the skill contract, and the [threat model](code-review-operations-contract.md#threat-model) states the code-review bundle's guarantees test by test. Read this page before a change that bends one of the invariants or revisits a decision below, and change it in the same pull request when a decision changes.

Each reason here comes from the issue, milestone description, or document named beside it. Where the maintainer gave a reason that no issue or document records, the entry says so; where no reason was recorded at all, it says that instead of supplying one.

## Trust model

The suite has one adversary and several boundaries, each placed where something the user did not write can reach something that acts.

| Boundary | What it holds | Why it is there | Where it is stated |
| --- | --- | --- | --- |
| A pull request's author | The author controls everything a pull request carries: its diff, its tree, its file names, its attributes, its instruction files, and any text addressed to a reviewer. The code-review bundle is the one component that reads such input. Configuration, the trusted reviewer commit, the review archive, fixtures, and the session running the review are trusted. | The bundle is the one component that reads input an adversary writes, and through it the author reaches what a reviewer model reads. | [Threat model](code-review-operations-contract.md#threat-model), held row by row by `test_adversarial_inputs.py` and the tests each row names. The `review-repository` reviewer's `trust-boundary` route asks each change to the contract, the guard, the runtime, or the source commands for its row and test. |
| What a skill may run | A skill runs Python and its standard library, Git for Windows and the utilities it bundles, PowerShell, and the tools it declares from the catalogue in `deployer/tools.py`. Its executable logic lives in tested files under its `scripts/`, and it writes working files under the system temporary directory, never inside a deployed skill directory. | Skills run on machines where installing extra utilities may be inconvenient or not allowed. | [Commands skills may run](adding-a-skill.md#commands-skills-may-run) and [Working files](adding-a-skill.md#working-files), held by the command policy in `tests/validation/skill_scripts.py` and, for working files, `skill_roots.py` in skill-core. |
| A grant | `allowed-tools` pre-approves a command pattern for the turn that starts a skill. It restricts nothing, so it is never a boundary: every grant is a scoped pattern for the commands the skill runs, never a bare shell. | A bare `Bash` or `PowerShell` grant would pre-approve every command in that turn. | [Granting tools](adding-a-skill.md#granting-tools), held by `tests/validation/skill_grants.py`. |
| The deployer | The deployer writes into the directories every runtime loads skills from. It renders in memory, parses configuration without executing it, and refuses unresolved tokens, unsafe names and paths, ownership collisions, invalid shared dependencies, a linked worktree, and a second clone of the same source before it changes anything; what it does change, it journals. | An item it writes is a skill every later session runs, and a deployment that proceeds on a wrong assumption removes or replaces skills the user has: a second clone with the same source ID would adopt the first clone's skills and remove the ones it lacked, until the deployer was made to refuse it ([#22](https://github.com/EJRyan89/coding-agent-skills/issues/22)). | The safety requirements in [CLAUDE.md](../CLAUDE.md), the README's safety model, and [Recovery](recovery.md). |
| The reviewer guard | In Claude Code, a `PreToolUse` hook binds each `code-review-reviewer` to one role of one run: it reads only that run and the suite's references, writes only that role's result, and runs only that role's commands. A call it cannot evaluate is denied. The core validates every result and computes the verdict itself, so a persuaded reviewer can omit a finding but cannot clear a coverage gap. | Prompts alone did not hold the run boundary: reviewers told never to read the local checkout searched it, and the whole workspace, anyway. A reviewer reading the wrong code gives a plausible but wrong review, while a failed one is reported and retried. | [Review pipeline](code-review-operations.md#review-pipeline) and the threat model's reviewer rows, held by `test_review_guard.py`. What it does not cover is listed under the threat model's table. |
| The hub guard | In a clone that opts in, a Claude Code hook refuses edits to the hub checkout and git commands that would move its HEAD or write its tree. A hook can only deny; it never grants. | Sessions that share a checkout share its HEAD, index, and working tree, so one session's branch switch or commit carried another's uncommitted edits. This happened here. | [Parallel sessions](parallel-sessions.md#the-guard), held by `tests/tools/test_worktrees.py`. Codex and Copilot CLI run no such hook, so for them the rules in `CLAUDE.md` are the guard. |
| The same user | A process running as the user is trusted: run folders and the guard's claims live in the per-user temporary directory, and authentication tokens stay available to reviewer hosts. | The suite isolates configuration, not credentials. | The threat model's list of what it does not cover, and the Copilot CLI host paragraph under [Safety invariants](code-review-operations-contract.md#safety-invariants). |

## Invariants

Each invariant below gives its reason and names what holds it today. The `review-repository` reviewer also reads each pull request against them: its `deployer` route against the one write point, the platform seam, and refusals before mutation, its `skill-contract` route against tested scripts over prose, and its `upgrade-notes` route against the structured record. A reviewer reads and validation holds, so it is named here beside the guards, never in place of one.

### One write point

Every mutating filesystem operation in the deployer goes through `deployer/fsops.py`, so tests can inject a failure at any write and show that the deployment recovers ([#9](https://github.com/EJRyan89/coding-agent-skills/issues/9) found three writes failure injection could not reach). Held by the filesystem-write policy in `tests/validation/fsops_platform.py`, which resolves each call through the module's imports, with its fixtures in `tests/validation/test_fsops_platform.py`. A sanctioned exception is stated beside its code as `FSOPS_ALLOWED`, and only throwaway files under the system temporary directory qualify.

### One platform seam

Every operating-system-specific behavior lives in `deployer/platform_support.py`, so the macOS and Linux port is added there without touching the pipeline. Without a check the port would multiply the drift that already existed when the rule had none ([#10](https://github.com/EJRyan89/coding-agent-skills/issues/10)). Held by the platform policy in `tests/validation/fsops_platform.py`. The policy sees only code that names a platform token; the Windows behavior it cannot see, such as case-folded path comparison and a rename that refuses to replace, is listed on [#6](https://github.com/EJRyan89/coding-agent-skills/issues/6) for the port and in [#354](https://github.com/EJRyan89/coding-agent-skills/issues/354).

### One home for shared Python

Shared Python lives in the hidden `skill-core` skill, and the deployer, `tools/`, and every skill import it from `skills/skill-core/scripts`; nothing copies it. Decided on 2026-10-07 ([#143](https://github.com/EJRyan89/coding-agent-skills/issues/143)), replacing a byte-identical copy of the frontmatter reader, because the copy rule did not scale: each new shared module, such as the `GitClient` beside `GitHubClient`, would face the same choice to copy or duplicate. The deployer always runs from the checkout, where that directory exists; the pattern of importing a skill's scripts was already in use; and a deployer that depends on a shared library is the ordinary direction. Held by `tests/validation/duplication.py` (the duplication gate, the copy check, and the import-order checks), with fixtures in `tests/validation/test_duplication.py`.

### Tested scripts over prose

A skill's deterministic steps (collecting data, applying rules, parsing output, writing records) are tested scripts under its `scripts/` that print one fact per line; the prose keeps judgment, delegation, and the questions for the user. A Markdown fence holds at most five lines. The rule predates the repository's publication; its reason, recorded by the maintainer then, is that the code-review skills were slow, expensive, and error-prone while the agent read the core modules and improvised glue code for each pull request, and scripting the pipeline fixed that. A skill body is also read on every run, so what the agent does not act on costs every run ([#7](https://github.com/EJRyan89/coding-agent-skills/issues/7)). Stated in the [Design constraints](code-review-operations-contract.md#design-constraints) and [Files](adding-a-skill.md#files) of the skill contract, held by the fence-length policy in `tests/validation/skill_layout.py` and the [Script results](adding-a-skill.md#script-results) contract, and judged per skill by `analyze-skill-cost`.

### The structured record is the contract

What scripts and users depend on is the structured record: review records, flags, tracker state, the ownership manifest, configuration and manifest files, skill names, arguments, and the status lines an agent parses. Prompt wording, review heuristics, and output no script parses are behavior, which may change in any release. JSON is the source of truth and Markdown a projection, and nothing is scraped from a report. The reason is in [Versioning](releasing.md#versioning) (2026-10-04): a version number tells a user what an update asks of them, so the contracts are what scripts and people depend on, ranked by what a break costs the user, and behavior is not among them. Held by `tests/code-review/test_format_contract.py`, which checks each format table against its validator, and by the upgrade-notes guard in `tests/validation/upgrade_notes.py`, which fails while a changed contract value is named by no upgrade note since the last tag.

### Refusals before mutation, and journaled rollback

The deployer finds every reason to stop before it changes a file, and journals each change it then makes, so an interrupted or failed deployment is put right by the next run ([Recovery](recovery.md#interrupted-deployments)). That is the journal's recorded reason. For refusing first, the record holds the second-clone case in [#22](https://github.com/EJRyan89/coding-agent-skills/issues/22), which the trust model cites, and no more general reason. Held by the deployer suites, among them `test_collision_preflight_occurs_before_pending_removals` in `tests/deployer/test_ownership_removal.py`, `test_unknown_token_fails_staging` in `tests/deployer/test_source_validation.py`, and the recovery tests in `tests/deployer/test_recovery_migration.py`. Every refusal a deployer suite expects is held to the home it found: `deploy_fails` in `tests/deployer/harness.py` compares the home, file by file and byte for byte, before and after the refusal, so a check moved after the first change fails the test of that check, and a failure expected after the deployment began, such as a recovery or a lock reclaim, states why with `changes_home`. `tests/deployer/test_invariants.py` shows the comparison failing on a refusal raised after the plan is applied and passing on one raised before it.

| Review records carry no token usage or cost figures. | Repository skills meet the shipped-skill standard: the same validation policies, scoped grants, script over prose, and an `analyze-skill-cost` run before the pull request. | 2026-10-07 | A repository skill loads into every session here as a shipped skill does, and measured repository skills read whole documents every run and declared no grants ([#133](https://github.com/EJRyan89/coding-agent-skills/issues/133)). The maintainer's instruction was that repository skills are held to the same standard as what is shipped. | [#133](https://github.com/EJRyan89/coding-agent-skills/issues/133); [#54](https://github.com/EJRyan89/coding-agent-skills/issues/54) (2026-10-07 comment) | The policies in `tests/validation/` applied to `.claude/skills/`; [Validation](adding-a-skill.md#validation). |
| A skill pins no model, and a reviewer's model or effort setting changes only with a before-and-after comparison of real reviews. | Before publication for the pin; the comparison rule with the evaluation design on 2026-10-05 | In Claude Code a skill's `model` applies for the rest of the turn that invoked it, so reviewers started in the same turn as a skill pinned to Haiku all ran on Haiku and missed a must-fix finding. A cheaper model or lower effort can miss findings without any visible failure, so only a measured comparison can justify one. | The comment on `test_no_skill_pins_a_model`; [#54](https://github.com/EJRyan89/coding-agent-skills/issues/54); [Specialist reviewers](code-review-operations.md#specialist-reviewers) | `test_no_skill_pins_a_model` in `tests/ai-config/test_cross_skill_contracts.py`; the `evaluate-skill` run a pull request that changes model guidance cites. |
| The required `validate` check stays strict, and a pull request that falls behind `main` is brought up to date by hand, with a merge of `main`. | 2026-10-09 | Branch protection is what keeps `main` green by construction, and strictness is the part of it that makes a pull request pass validation against the `main` it merges into ([How main is protected](../CONTRIBUTING.md#how-main-is-protected)); The milestone records the decision, and that no update-branch workflow or token is added, but not the reasons. The maintainer's, given with the decision: failures belong in CI, not on `main`, so strictness is not dropped; and an update-branch workflow needs a fine-grained token that would have to be kept and rotated. | The v0.5.0 milestone description | `tools/branch_protection.py`, which reads the live settings and prints `DRIFTED` when strictness is lost. |
| The repository is audited twice per release: a release audit of the diff since the previous tag, which holds the tag, and a rotation audit of one area read whole after it, which feeds the next milestone. | 2026-10-09 | The v0.4.0 rotation audit found a reviewer-guard hole and ten bugs in code the release had just shipped, which an audit of the diff before the tag would have caught; the two audits read different code, so neither repeats the other. What an audit finds is the drift validation cannot see. | [#260](https://github.com/EJRyan89/coding-agent-skills/issues/260) and its 2026-10-09 comment | The release procedure and the `audit-repository` repository skill that [#260](https://github.com/EJRyan89/coding-agent-skills/issues/260) adds. |
| An upgrade note is written in the pull request body, under `## Upgrade note`, and each release's section of `docs/upgrade-notes.md` is generated from the merged commits' messages; no pull request edits the notes file for its change. | 2026-10-09 | Every contract-changing pull request added its entry at the top of one shared `## Unreleased` section, so any two in flight conflicted there and nowhere else: of nine merge conflicts on 2026-10-09, eight were that section, each needing a merge of `main`, a validation run, and a push, and with the strict required check each merge put the others behind. The repository already squash-merges with the pull request's body as the commit message, so the body reaches `main`'s history without a shared file. The guard's rule is unchanged; only where it reads the entries moved. The `review-repository` reviewer is not given a pull request's body, so its `upgrade-notes` route judges the diff and no longer the entry. | [#329](https://github.com/EJRyan89/coding-agent-skills/issues/329) | `tests/validation/upgrade_notes.py`, which reads the body in CI and the commit messages since the last tag, and fails on a section of the notes file that is not a version's; `tools/release_notes.py`, which writes the section; `tools/branch_protection.py`, which prints `DRIFTED` when the squash commit stops taking the title and the body. |

## Considered and declined

- **A plugin as the distribution route.** Declined on 2026-10-04 and not to be proposed again while its reason holds: the likely users' organizations block plugin installation ([#6](https://github.com/EJRyan89/coding-agent-skills/issues/6)).
- **An update-branch workflow, and a merge queue.** Declined with the strict check on 2026-10-09 (the v0.5.0 milestone). An update-branch workflow needs a fine-grained token to keep and rotate, as the decision above says. No reason for declining a merge queue is recorded.
- **Model pins in skills.** Declined before publication, and a test refuses a new one: a pin outlives the skill for the rest of its turn, and every subagent started later in that turn without an explicit model runs on the pinned one. A pin needs a measured reason and an entry in that test.
- **Generated instruction projections, and the `init-ai-config` skill that produced them.** The skill was retired on 2026-10-06 and removed in v0.2.0 ([#29](https://github.com/EJRyan89/coding-agent-skills/issues/29)). Every runtime this repository supports reads `CLAUDE.md` directly or through the thin redirect in `AGENTS.md`, so a projection pipeline earns its upkeep only where a surface that does not read `CLAUDE.md` is in use, and the generator wrote about 4,200 lines into every repository that adopted it. `CLAUDE.md` names the condition under which a parity check would be reconsidered. `audit-ai-config`, which is read-only, was kept.
- **A copy of shared modules rendered at deployment.** Considered as the alternative to one home for shared Python on 2026-10-07 and declined: `skills/` would no longer be the source of the modules the skill-core suites test ([#143](https://github.com/EJRyan89/coding-agent-skills/issues/143)).
