# Design

This page says why the repository is built the way it is. It owns the reasons; the documents it points at own the rules themselves, and the code and tests own the behavior. [CLAUDE.md](../CLAUDE.md) states what each part is and where it lives, [Adding a skill](adding-a-skill.md) is the skill contract, and the [threat model](code-review-operations-contract.md#threat-model) states the code-review bundle's guarantees test by test. Read this page before a change that bends one of the invariants or revisits a decision below, and change it in the same pull request when a decision changes.

Each reason here comes from the issue, pull request, or document named beside it. Where the maintainer gave a reason that no issue or document records, the entry says so; where no reason was recorded at all, it says that instead of supplying one.

## Trust model

The suite has several boundaries, each placed where something the user did not write can reach something that acts. Author-controlled input includes a pull request's contents and a document supplied for a standalone review; using a developer tool or a fixture does not make those bytes trusted.

| Boundary | What it holds | Why it is there | Where it is stated |
| --- | --- | --- | --- |
| A pull request's or document's author | The author controls everything a pull request carries: its diff, its tree, its file names, its attributes, its instruction files, its description, and any text addressed to a reviewer. A standalone document's author controls its bytes too. Configuration, the trusted reviewer commit, the review archive, fixture infrastructure and metadata, and the session running the review are trusted; a document copied into a fixture is not. A fixture is as trusted as the checkout that holds it, because its manifest names the condition scripts a review runs: one another author proposes by pull request is that author's input until it is read, as the pull request's code is, and `tools/skill_evals.py`, which runs this repository's fixtures in sessions signed in as the user, refuses a checkout that follows another repository's pull request. | Through the code-review bundle, the author reaches what a reviewer model reads and, for a PDF, what an external parser reads. Trusted fixture routing does not make document content an instruction or bypass the snapshot rules. | [Threat model](code-review-operations-contract.md#threat-model), held row by row by `test_adversarial_inputs.py` and the tests each row names. The `review-repository` reviewer's `trust-boundary` route asks each change to the contract, the guard, the runtime, or the source commands for its row and test. The evaluation runner's refusal is stated in [Skill evaluations](skill-evaluations.md#skill-evaluations) and held by `CheckoutTests` in `tests/tools/test_skill_evals.py`. |
| The PDF parser | `pdftotext`, an external program, reads a PDF's author-controlled bytes as the invoking user before any reviewer sees the text it extracts. | The standard library cannot read a PDF, so an outside parser does, and the suite bounds what it accepts from it rather than trusting it; the paragraph below the table says how far that goes. | The threat model's row for Word and PDF bytes and its limits ([Threat model](code-review-operations-contract.md#threat-model)), held by the PDF tests in `test_review_documents.py` and `test_adversarial_inputs.py` that row names. |
| Authored upgrade notes | A pull request's body is author-controlled data. CI reads it from the event's JSON payload into a fixed file for validation, never interpolating it into executable script text. A squash merge carries the approved body into the commit message, and the release-note tool reproduces its entries as authored Markdown. | Structural validation checks fields and contract coverage, not whether the prose, links, or Markdown should be published. The maintainer reviews the body before merging and the generated notes before release. | [Versioning](releasing.md#versioning) and [Before tagging](releasing.md#before-tagging); `.github/workflows/validate.yml`, `tools/release_notes.py`, and `tests/tools/test_release_notes.py` hold the data path and entry generation, not editorial approval. |

Its executable logic lives in tested files under its `scripts/`, and it writes working files under the system temporary directory, never inside a deployed skill directory. | Skills run on machines where installing extra utilities may be inconvenient or not allowed. | [Commands skills may run](adding-a-skill.md#commands-skills-may-run) and [Working files](adding-a-skill.md#working-files), held by the command policy in `tests/validation/skill_scripts.py` and, for working files, `skill_roots.py` in ejryan89-skill-core. |
| A repository a skill examines | The authors of the repository a skill reads control its files. `dotnet-dependencies` reads its solution, project, and props files as data, only inside the examined tree and only so much of each, modelling MSBuild's evaluation rather than running MSBuild, and may ask `dotnet nuget why`, which the .NET SDK answers from the project and its restored assets. `audit-ai-config` reads its configuration as data; only when the user explicitly authorizes it for a trusted repository does it run the repository's generator in read-only mode or handshake each stdio MCP server the repository configures, which starts the command the repository names, inside the repository and with no grant, so the user approves each run. | A skill pointed at a repository reads what its authors wrote, so reading it as data keeps it from acting, and the one step that starts what it configures waits for the user's own trust decision. | `dotnet-dependencies` in [Decisions](#decisions) and `skills/dotnet-dependencies/scripts/`'s suites; "Optional operational validation" in `skills/audit-ai-config/SKILL.md` and the handshake's suite in `skills/audit-ai-config/scripts/`. |
| A grant | `allowed-tools` pre-approves a command pattern for the turn that starts a skill. It restricts nothing, so it is never a boundary: every grant is a scoped pattern for the commands the skill runs, never a bare shell, and names each script it runs, the path ending before any `*`, or the `git` or `gh` subcommand it runs. | A bare `Bash` or `PowerShell` grant would pre-approve every command in that turn, a pattern whose `*` continues a path would pre-approve every installed skill's scripts through `..`, and one that ends at a program, such as `python *`, would pre-approve any code the `*` supplies. | [Granting tools](adding-a-skill.md#granting-tools), held by `tests/validation/skill_grants.py`. |
| The deployer | The deployer writes into the directories every runtime loads skills from. It renders in memory, parses configuration without executing it, and refuses unresolved tokens, unsafe names and paths, ownership collisions, invalid shared dependencies, a linked worktree, and a second clone of the same source before it changes anything; what it does change, it journals. | An item it writes is a skill every later session runs, and a deployment that proceeds on a wrong assumption removes or replaces skills the user has: a second clone with the same source ID would adopt the first clone's skills and remove the ones it lacked, until the deployer was made to refuse it ([#22](https://github.com/EJRyan89/coding-agent-skills/issues/22)). | The safety requirements in [CLAUDE.md](../CLAUDE.md), the README's safety model, and [Recovery](recovery.md). |
| The reviewer guard | In Claude Code, a `PreToolUse` hook binds each `code-review-reviewer`, the `review-insights` synthesis included, to one role of one run: it reads only that run and the suite's references, writes only that role's result, and runs only that role's commands. A call it cannot evaluate is denied. The core validates every result and computes the verdict itself, so a persuaded reviewer can omit a finding but cannot clear a coverage gap. Only Claude Code blocks a call when the hook fails or times out, so reviewers run under it only there: inline under the seal on Copilot CLI, and as native subagents without it on Codex. Installed as a Claude Code plugin, whose agents' own hooks Claude Code ignores, the plugin's hooks file runs the guard on every session's calls, and the guard holds only `<plugin>:code-review-reviewer`'s, passing the main session's and every other agent's and denying a subagent's call that names no agent type. A hook that never ran holds nothing, so on Claude Code a native reviewer's result counts only once the guard claimed its role. | Prompts alone did not hold the run boundary: reviewers told never to read the local checkout searched it, and the whole workspace, anyway. A reviewer reading the wrong code gives a plausible but wrong review, while a failed one is reported and retried. | [Review pipeline](code-review-operations.md#review-pipeline) and the threat model's reviewer rows, held by `test_review_guard.py`, its `PluginScopeTests` for the plugin, and the guard check of `tools/plugin_canary.py`. What it does not cover is listed under the threat model's table. |
| The hub guard | In a clone that opts in, a Claude Code hook refuses edits to the hub checkout and git commands that would move its HEAD or write its tree, and, while a guarded hub is in view, a git command it cannot place. A hook can only deny; it never grants. | Sessions that share a checkout share its HEAD, index, and working tree, so one session's branch switch or commit carried another's uncommitted edits. This happened here. | [Parallel sessions](parallel-sessions.md#the-guard), held by `tests/tools/test_hub_guard.py`. For Codex and Copilot CLI the rules in `CLAUDE.md` are the guard: Codex runs hooks of its own but not this one, and Copilot CLI, which runs it in a folder it trusts, runs it on Windows under PowerShell, where the hook's command exits before the guard starts ([Other runtimes](parallel-sessions.md#other-runtimes)). Claude Code on Windows runs it under PowerShell too when Git Bash is not installed, so the guard does nothing there as well; the repository requires Git for Windows, which carries Git Bash. |
| The merge shepherd | The `shepherd-pull-requests` repository skill arms squash auto-merge, merges `main` into behind branches, and reruns failed checks only for pull requests whose head branch is in this repository. It names every other open pull request, such as one from a fork, as not admitted, and writes nothing for it. | The repository requires no approval to merge, so arming auto-merge decides the merge: a pull request from another repository merges only when the maintainer merges it. | [An orchestrator and a shepherd](parallel-sessions.md#an-orchestrator-and-a-shepherd), held by the admission tests in `.claude/skills/shepherd-pull-requests/scripts/test_shepherd_pull_requests.py`. |
| The same user | A process running as the user is trusted: run folders and the guard's claims live in the per-user temporary directory, and authentication tokens stay available to reviewer hosts. | The suite isolates configuration, not credentials. | The threat model's list of what it does not cover, and the Copilot CLI host paragraph under [Safety invariants](code-review-operations-contract.md#safety-invariants). |

The PDF parser is a separate boundary from the reviewer model: it consumes author-controlled bytes as the invoking user before the reviewer sees extracted text. The shared provider-specific support policy is checked by the tool catalogue and again before each extraction, without giving the probe document bytes. A refused probe leaves a coverage gap; a successful probe identifies the provider and version at the resolved path, which extraction then uses without another `PATH` search. This reduces exposure to unsupported releases but is not a sandbox, binary authentication, or a guarantee of native parser memory safety. Input and output limits and a timeout bound the work the suite accepts and waits for, not everything a vulnerable parser could do. A same-user process could replace the checked executable between the probe and extraction; the execution environment remains part of the user's trust decision. [The threat model's limits](code-review-operations-contract.md#threat-model) state what is not protected.

These are developer tools, not a deployed application service. That affects who can supply input and the likely exposure, but is not itself a severity rating or a claim of isolation: assess a defect by the input that reaches it, the process's privileges, and the demonstrated impact.

## Invariants

Each invariant below gives its reason and names what holds it today. The `review-repository` reviewer also reads each pull request against them: its `deployer` route against the one write point, the platform seam, and refusals before mutation, its `skill-contract` route against tested scripts over prose, and its `upgrade-notes` route against the structured record. A reviewer reads and validation holds, so it is named here beside the guards, never in place of one.

### One write point

Every mutating filesystem operation in the deployer goes through `deployer/fsops.py`, so tests can inject a failure at any write and show that the deployment recovers ([#9](https://github.com/EJRyan89/coding-agent-skills/issues/9) found three writes failure injection could not reach). Held by the filesystem-write policy in `tests/validation/fsops_platform.py`, which resolves each call through the module's imports and simple assignment aliases in its lexical scope, with its fixtures in `tests/validation/test_fsops_platform.py`. An ambiguous or unresolved callable alias is reported rather than hiding a write ([#501](https://github.com/EJRyan89/coding-agent-skills/issues/501)). Extracting or creating an archive, and opening an archive, a compressed file, or a database with a mode that may write, are writes like any other, so the deployer's one extraction is `fsops.extract_archive`. A sanctioned exception is stated beside its code as `FSOPS_ALLOWED`, and only throwaway files under the system temporary directory qualify.

The policy reads `deploy.py` and every other deployer module. Beside a direct write, each of these counts as one: an alias of a write callable; an `os.open` with a write flag; an `open` mode it cannot read as read-only; a callable named by a literal through `getattr`, `importlib.import_module`, `sys.modules`, a module's `__dict__`, or `operator.methodcaller`; and a write callable, or a module that holds one, passed as a value rather than called. An alias is a name bound to a name or an attribute by an assignment, an assignment expression, an item of a literal tuple or list it is unpacked from or loops over, a parameter's default, or a case that captures its whole subject. A callable alias that is rebound or cannot be resolved, a call of a callable another call returns or a subscript looks up that no literal names, and a call of an attribute of a module named by anything but a literal are reported, never guessed. An entry of a module-level `FSOPS_ALLOWED = {token: reason}` fails when its call may write outside the system temporary directory: a `tempfile` call with a positional argument, a `dir`, or a `prefix` or `suffix` that is not a literal free of path separators; any other write with a destination argument, any argument that may name where it lands, that is not a name the module binds only to a directory `tempfile.mkdtemp` made there, directly or through `pathlib.Path`, `os.fspath`, or `str`, which keep its path; and a write with no destination argument, as an extraction into the working directory has.

### One platform seam

Every operating-system-specific behavior lives in `deployer/platform_support.py`, so the macOS and Linux port is added there without touching the pipeline. Without a check the port would multiply the drift that already existed when the rule had none ([#10](https://github.com/EJRyan89/coding-agent-skills/issues/10)). Held by the platform policy in `tests/validation/fsops_platform.py`, which matches an environment name in any case, as Windows reads it. The policy sees only code that names a platform token or strips, appends, or compares an extension Windows finds a program by, which `platform_support.program_name` drops; the Windows behavior it cannot see, such as case-folded path comparison, is listed on [#6](https://github.com/EJRyan89/coding-agent-skills/issues/6) for the port. One lookup is shared with the skills rather than held there: finding a program by its command name, the first on `PATH` and else in a folder the platform's package manager links commands into, is ejryan89-skill-core's `executable_locator.py`, which `platform_support.find_executable` calls, because a skill's script runs without the deployer and must find the program `check` reports ([the decision](#decisions)); it names a link folder on Windows only, as the locator row says. Its `environment_path` is the one reader of a folder or program an environment variable names, there and in `platform_support`'s Git Bash and app execution alias lookups and the memory audit's managed settings, and gives none for a value that is not an absolute path, so nothing is looked up relative to the working directory. Two platform values sit beside it for the same reason: the command that runs Python, `PYTHON` in `executable_locator.py`, which `platform_support` re-exports and every skill renders as `{{PYTHON}}`, so a skill's scripts write the command its fences run; and the hint a PDF parser's refusal and `check` add after the parser floors, `INSTALL_HINT` in `pdf_tool.py`, which `deployer/tools.py` puts in its catalogue directly. The process mechanics the deployer shares with the code-review pipeline live in ejryan89-skill-core for the same reason, and `platform_support` calls them: `job_tree.py` holds a command and every process it starts in one tree, a Windows job object or elsewhere the process group of a session of its own, and `process_identity.py` reads whether a process runs and when it started, which the lock judges a holder by. The Linux side of the deployer core sits behind the seam: `ensure_supported` accepts Linux and refuses every other platform but Windows by name; a configured directory is an absolute POSIX path there, under the same character allowlist as a drive-letter path; the system `bash` and `pwsh` check rendered scripts; the install hints are apt's; the home is `HOME`; a backslash is a character of a name rather than a separator; and the lock reads a holder's start time from `/proc`. A rename that never replaces its destination, which journal finalization, recovery, and the lock reclaim rely on, is not left to Windows: `platform_support.refuse_existing_destination` refuses an existing destination wherever the platform's rename would replace it, and `fsops.move` calls it, held by the move tests in `tests/deployer/test_fsops.py`.

The seam's other ejryan89-skill-core values serve the deployer and the skills alike: `job_tree.py`'s tree ends every process a command starts but one that leaves its process group by starting a session or group of its own; `is_reserved_device_name` in `device_names.py`, the names Windows opens as a device rather than a file, is re-exported by `platform_support` for the deployer's names and read by a review snapshot for each path segment; and `is_link_or_junction` in `link_probe.py`, the test of whether a path is a symbolic link, a junction, or another reparse point, is wrapped by `platform_support` for every link check of the deployer's, judging a missing path no link and raising for one it cannot read. The platform policy reads the deployer, `tools/`, `deploy.py`, and the validation runner, and fails on a platform-specific attribute, module, operating-system query, signal, process keyword, environment variable, command, or filesystem path named outside the seam. A module states a sanctioned exception beside the code it excuses, as a module-level `PLATFORM_ALLOWED = {token: reason}`.

### One home for shared Python

Shared Python lives in the hidden `ejryan89-skill-core` skill, and the deployer, `tools/`, and every skill import it from `skills/ejryan89-skill-core/scripts`; nothing copies it. The home is reached by path, never by name: each dependent locates it from its own file, so no other skill named `ejryan89-skill-core` can stand in for it. It replaced a byte-identical copy of the frontmatter reader ([the decision](#decisions)), because the copy rule did not scale: each new shared module, such as the `GitClient` beside `GitHubClient`, would face the same choice to copy or duplicate. The deployer always runs from the checkout, where that directory exists; the pattern of importing a skill's scripts was already in use; and a deployer that depends on a shared library is the ordinary direction. Held by `tests/validation/duplication.py` (the duplication gate, the copy check, and the import-order checks), with fixtures in `tests/validation/test_duplication.py`.

### Tested scripts over prose

A skill's deterministic steps (collecting data, applying rules, parsing output, writing records) are tested scripts under its `scripts/` that print one fact per line; the prose keeps judgment, delegation, and the questions for the user. A Markdown fence holds at most five lines. The rule predates the repository's publication; its reason, recorded by the maintainer then, is that the code-review skills were slow, expensive, and error-prone while the agent read the core modules and improvised glue code for each pull request, and scripting the pipeline fixed that. A skill body is also read on every run, so what the agent does not act on costs every run ([#7](https://github.com/EJRyan89/coding-agent-skills/issues/7)). Stated in the [Design constraints](code-review-operations-contract.md#design-constraints) and [Files](adding-a-skill.md#files) of the skill contract, held by the fence-length policy in `tests/validation/skill_layout.py` and the [Script results](adding-a-skill.md#script-results) contract, and judged per skill by `audit-skill`.

### The structured record is the contract

What scripts and users depend on is the structured record: review records, flags, tracker state, the ownership manifest, configuration and manifest files, skill names, arguments, and the status lines an agent parses. Prompt wording, review heuristics, and output no script parses are behavior, which may change in any release. JSON is the source of truth and Markdown a projection, and nothing is scraped from a report. The reason is in [Versioning](releasing.md#versioning): a version number tells a user what an update asks of them, so the contracts are what scripts and people depend on, ranked by what a break costs the user, and behavior is not among them. Held by `tests/code-review/test_format_contract.py`, which checks each format table against its validator, and by the upgrade-notes guard in `tests/validation/upgrade_notes.py`, which fails while a changed contract value is named by no upgrade note since the last tag.

### Refusals before mutation, and journaled rollback

The deployer finds every reason to stop before it changes a file, and journals each change it then makes, so an interrupted or failed deployment is put right by the next run ([Recovery](recovery.md#interrupted-deployments)). That is the journal's recorded reason. For refusing first, the record holds the second-clone case in [#22](https://github.com/EJRyan89/coding-agent-skills/issues/22), which the trust model cites, and no more general reason. Held by the deployer suites, among them `test_collision_preflight_occurs_before_pending_removals` in `tests/deployer/test_ownership_removal.py`, `test_unknown_token_fails_staging` in `tests/deployer/test_source_validation.py`, and the recovery tests in `tests/deployer/test_recovery_migration.py`. Every refusal a deployer suite expects is held to the home it found: the shared guard in `tests/deployer/harness.py`, used by `deploy`, `deploy_fails`, `configure`, and `run_cli`, compares the home, file by file and byte for byte, before and after any nonzero exit, including usage errors and cancellation. It also compares the source around every run, so neither CLI routing nor an alternate source or canary home bypasses the invariants. A check moved after the first change fails the test of that check, and a failure expected after the deployment began, such as a recovery or a lock reclaim, states why with `changes_home`; that exception never permits a source change. `tests/deployer/test_invariants.py` shows both comparisons failing on mutations and passing on unchanged refusals through the pipeline and CLI.

### One table of item kinds

The deployer handles four kinds of item, skills, shared assets, runtime adapters, and agents, and `deployer/kinds.py` describes each once, its manifest key, report label, noun, and journal root among the rest; every pass over them iterates that table. The reason recorded when the table was introduced is that the same four-kind blocks recurred in the manifest commit, the ownership checks, migration, the take-over summary, and the manifest reader, and `deployer/pipeline.py` had grown to 1,203 lines ([#117](https://github.com/EJRyan89/coding-agent-skills/pull/117), a step of [#23](https://github.com/EJRyan89/coding-agent-skills/issues/23)). Where a kind truly differs, the code says so: `plan.build` plans skills first and names the kinds that depend on them (a skill left in place keeps what it depends on, and a runtime adapter, which the table marks as following its skill, stays and is skipped with it), `render.Staged` holds each kind's rendered content in its own shape, and the journal records by root, which skills and shared assets share, in its on-disk format. Held by `tests/validation/kinds_table.py`, with its fixtures in `tests/validation/test_kinds_table.py`, added because the invariant had no check ([#354](https://github.com/EJRyan89/coding-agent-skills/issues/354)): it fails on a deployer pass that names a kind's manifest key, report label, or journal root by literal, branches on a kind, or lists kinds by hand, unless its module states why beside the code, as a module-level `KINDS_ALLOWED = {pass: reason}` keyed by the function's qualified name or by a module-level assignment's target.

## Direction

The repository is meant to maintain itself within a bounded budget, through scheduled, bounded runs that keep their state in GitHub rather than agents that run continuously. The maintainer's attention goes to three places:

- labels: `agent-ready` admits an issue to automated work and is the trust gate for an issue an outside contributor files, and `needs-human` escalates one to the maintainer;
- the merge of a risky pull request;
- the tag.

The build order, each step its own change and none of it started by this section:

1. the pull request title and bug-class conventions;
2. `review-repository` running on every pull request, with a check that every trust-boundary module matches a review route;
3. a table mapping each "Validation fails when" claim to the check that enforces it;
4. a dispatch script run by hand;
5. scheduled runs with caps and a digest;
6. auto-merge for a pull request that touches neither a contract file nor an area the [model guidance](implementing-changes.md#model-guidance) names as strongest-model;
7. a release driver.

Validation that runs on Linux is what lets cheap cloud sessions take part, which is why the Linux port and this direction go together. The direction comes from [#585](https://github.com/EJRyan89/coding-agent-skills/issues/585), the Linux port's issue, the same source as the platform decisions above.

## Considered and declined

- **mypy's `warn_unreachable` and its `mutable-override` code.** Declined on 2026-10-24 ([#1660](https://github.com/EJRyan89/coding-agent-skills/issues/1660)), when the other optional codes were adopted. The configuration sets no platform, so each host checks the branches it runs, and a function that returns from an `if sys.platform == "win32":` block reports everything after it as unreachable on Windows. Every finding `warn_unreachable` made was that idiom, or a `yield` after a `raise` that keeps a function a generator, and none was a defect. Almost every finding `mutable-override` made was a library's documented form for an attribute: a `ctypes.Structure`'s `_fields_` list, and `maxDiff = None` on a `unittest.TestCase`. The other was a test fixture subclass that narrows a tuple attribute nothing reassigns. Revisit `warn_unreachable` if the configuration ever sets a platform.
- **A plugin as the only distribution route.** Declined on 2026-10-04: the likely users' organizations block plugin installation ([#6](https://github.com/EJRyan89/coding-agent-skills/issues/6)). That reason still holds for them, so the plugin became a second route beside the deployer on 2026-10-19, as the decision above records, and replacing the deployer with it is not to be proposed while the reason holds.
- **An update-branch workflow, and a merge queue.** Declined with the strict check on 2026-10-09 (the strict-check decision above). An update-branch workflow needs a fine-grained token to keep and rotate, as the decision above says. A merge queue is not available: GitHub offers merge queues only on organization-owned repositories, and this one is owned by a user.
- **Model pins in skills.** Declined before publication, and a test refuses a new one: a pin outlives the skill for the rest of its turn, and every subagent started later in that turn without an explicit model runs on the pinned one. A pin needs a measured reason and an entry in that test.
- **Generated instruction projections, and the `init-ai-config` skill that produced them.** The skill was retired on 2026-10-06 and removed in v0.2.0 ([#29](https://github.com/EJRyan89/coding-agent-skills/issues/29)). Every runtime this repository supports reads `CLAUDE.md` directly or through the thin redirect in `AGENTS.md`, so a projection pipeline earns its upkeep only where a surface that does not read `CLAUDE.md` is in use, and the generator wrote about 4,200 lines into every repository that adopted it. `CLAUDE.md` names the condition under which a parity check would be reconsidered. `audit-ai-config`, which is read-only, was kept.
- **A copy of shared modules rendered at deployment.** Considered as the alternative to one home for shared Python on 2026-10-07 and declined: `skills/` would no longer be the source of the modules the ejryan89-skill-core suites test ([#143](https://github.com/EJRyan89/coding-agent-skills/issues/143)).
- **A source-specific prefix on every skill name.** Declined on 2026-10-10 ([#381](https://github.com/EJRyan89/coding-agent-skills/issues/381)) and again on 2026-10-18 ([#1260](https://github.com/EJRyan89/coding-agent-skills/issues/1260)): a prefix on the visible skills changes every command users type, and Claude Code's plugin namespace already lets two suites coexist for a user who opts into the longer invocation. The hidden cores, which nobody types, took the prefix on 2026-10-18, as the decision above records.
