# Code-review operations

The `code-review-operations` bundle installs five public workflows and the hidden `code-review-core` dependency. Development and tests do not modify installed skills, live review archives, dashboards, or GitHub state. The promises those workflows and their archive keep are listed in the [behavior contract](code-review-operations-contract.md).

## Prerequisites

- GitHub CLI (`gh`) installed and authenticated for every configured repository.
- Python 3.11 or newer.
- A supported local agent runtime: Claude Code, Codex, or GitHub Copilot CLI 1.0.88 or newer. Only Claude Code runs every reviewer path. Codex starts reviewers as native subagents on the session's model, so a reviewer `model` or `effort` setting has no effect: `prepare` prints a `NOTE` for a role that names a model. Copilot CLI runs the generic reviewer and the specialists of a manifest without `agent-delegation` inline, and a repository entrypoint reviewer on its bounded host; a specialists manifest that keeps `agent-delegation` fails there. [Runtime support](skills.md#runtime-support) lists each skill.
- A configuration file, written once before the first skill run as described below.

Missing tools, authentication failures, incomplete pagination, and rate limits fail the affected repository without advancing its watermark.

### First configuration

No skill in the bundle works until its configuration exists. Before starting one:

1. Copy the example under [Configuration](#configuration) to a new file, such as `candidate.json`.
2. Edit it: name your repositories under `repositories` and `repository_sets`, and point `archive_root`, `summary_root`, and `dashboard_file` at absolute paths on your machine.
3. From the clone, write it to `~/.coding-agent-skills/code-review/config.json`:

```powershell
python -B skills/code-review-core/scripts/review_config.py write candidate.json
```

`write` validates the file first and prints `WROTE <config path>`; when the file is invalid it prints `FAILED <reason>`, exits 1, and changes nothing. [Configuration](#configuration) describes every field and how to replace the file later.

## Single-PR review and canary

Generate a durable initial review for exactly one configured pull request with:

```text
/review-prs --pull owner/repository#123
```

Re-review one whose head changed since its last review with `--re-review owner/repository#123 --scope auto|full|incremental` (see "Re-review scope" below). Repeat either selector, or mix them, to review several pull requests in one pass; `update-pr-tracker` does this for the reviews it offers.

These selectors do not enumerate the repository or advance a merged-pull watermark. It writes the validated review pair to the configured archive, using the same trusted reviewer and source-snapshot rules as a batch review.

Use an explicit initial-review canary before enabling a new repository, reviewer manifest, or routing change:

```text
/review-prs --canary owner/repository#123 --canary owner/repository#124
```

Each selector must name a configured open (including draft) or merged pull request. Repeat `--canary` to cover every case the change affects, such as a pull request of each kind a manifest routes to a different specialist, or one on each side of a routing threshold; they are prepared up to four per `prepare` call and reviewed in one pass. Each canary fetches only its pull request, materializes the exact head into an isolated hash-verified source snapshot, and writes the validated JSON/Markdown pair only under its own new temporary canary directory, which `finalize` reports as `CANARY <selector> <root>` followed by a `SHA256` line per file and the `STATS` lines of "Snapshot size and reads" below. One canary failing leaves the others' directories in place and reported. A canary never reads or writes configured archives, mirrors, state, dashboards, flags, watermarks, or GitHub review state. Inspect the retained output before deleting it.

### Fixture canaries

A canary can also review a fixture directory in place of a pull request, with no GitHub state at all; skill evaluations (`tools/skill_evals.py`) run `review-prs` this way. It takes one fixture and no other selector:

```text
/review-prs --canary --fixture <directory>
/review-prs --canary --fixture <directory> --re-review --prior <record>
```

The directory holds the change as two trees, `base/` and `head/`, and the pull request around it in `pull.json` ("Fixture pull request" in the [contract](code-review-operations-contract.md#fixture-pull-request) states its fields). `prepare` reads nothing from GitHub. It commits both trees, byte for byte, to a throwaway repository, takes the base and head commits and the diff from it, and snapshots the head from it by the same path a checkout's head takes, with every exclusion; the throwaway repository is gone when `prepare` returns. The suite's generic reviewer reviews a fixture, unless its `pull.json` names a `manifest_path`: a reviewer manifest in the `base/` tree, which `prepare` reads from the base commit as it reads a configured repository's `manifest_path`, so a fixture can exercise specialists, and its `body` is the description reviewers are given. The fixture's repository need not be configured, though the configuration still supplies the runtime, the verdict policy, and model names. `run.json` records the fixture under `fixture`. A fixture is trusted input; see "Threat model" in the contract.

- **Initial review**: `--canary --fixture <directory>` records a first review, version 1, under a new canary root.
- **Re-review**: `--re-review --prior <record>` adds a review record of the same pull request, its first review, such as one an initial fixture canary wrote. The re-review carries that record's open findings and ledger as a real re-review carries the archive's and covers the full scope. `finalize` archives the prior record in the new canary root first and records the re-review as version 2 on top of it, so the record has a real re-review's dispositions, ledger, and `repeats` links.

Both are canaries in every other way: nothing configured or in a flag store is read or written, and `check`, `finalize`, and the result contract are those of every review.

### Document reviews

`review-document <path>` reviews one document that is not in a pull request, such as a draft on disk or a document in a checkout with uncommitted edits, as a fixture canary. Its script, `review-document/scripts/review_document.py`, builds a one-file fixture and `review-document` runs `prepare --canary --fixture`, the reviewer, `check`, and `finalize` on it as `review-prs` does, so the reviewer guard, the inline path, result validation, and the record are those of every fixture canary, and nothing new is trusted. It reads nothing from GitHub and writes nothing to the checkout.

- **Head**: the file as it is on disk.
- **Base**: when the file lies in a git checkout and is committed at `HEAD`, its committed version, so the review covers only the uncommitted change; otherwise, or with `--base none`, no file, so the whole document is reviewed. Both sides have their line endings read as LF, so a checkout that converts them on checkout does not make every line a change. The fixture's `pull.json` records the base used as `base_ref`, `committed <commit>` or `none`, and its title says which; the record keeps both, and the report's **Branch** row shows `working tree` → the base.
- **Path**: the file's path in its checkout, or its file name outside one. The fixture's repository is `review-document.local/<checkout folder>`, or `review-document.local/document` for a file outside a checkout: no GitHub account name holds a dot, so the pull request URL the record must carry names nobody's repository.
- **Reviewer**: a file whose suffix is `.md`, `.markdown`, `.txt`, `.rst`, or `.adoc`, ignoring case, goes to the [design-review specialist](#design-documents) through a specialists manifest the script writes at `.review-document/specialists.json` in both trees, so the manifest is never part of the change. The manifest routes exactly the document's path to `suite:design-review` with the design finding categories and leaves `agent-delegation` out of `required_capabilities`, so a runtime that cannot start subagents reviews it inline. Any other text file has no manifest and gets the generic reviewer.
- **Refused**: a file that is empty, binary (a NUL byte in its first 8,000 bytes, git's test, which refuses a `.docx` or PDF until text extraction exists), or committed with no change and no `--base none`; `--base committed` for a file outside a checkout or never committed; and a path under `.review-document/`.

The fixture goes in `<output>/fixture`, where `<output>` is `--output` or a new `review-document-*` temporary directory; an `--output` inside a skills directory, or one that already holds a fixture, is refused before anything is read. After `finalize`, `review_document.py report` copies the Markdown report to `<output>/report.md` and prints `REPORT <copy>` and `RECORD <record>`. The record stays under the new `code-review-canary-*` root `finalize` names, like every canary's, where `tools/skill_evals.py --records` and `review-insights` can read it. Every file is left for inspection.

## Posting findings

`review-prs` never posts to GitHub. If you then ask the agent to post findings, it should post only the ones you
choose, as one review whose payload a JSON serializer builds and `gh api --input <file>` sends, never `--field`
arguments or a shell heredoc. The payload omits `event` entirely, so no review state (approve, request changes, or
comment) is submitted, and comment bodies are plain text without internal finding IDs or labels. The skill keeps
only the rule against sending an `event`; Codex and Copilot CLI also get the rest through the runtime compatibility
contract every adapter carries.

## Review pipeline

`code-review-core/scripts/review_pipeline.py` runs every deterministic step of `review-prs`, so the orchestrating agent only runs its commands and starts reviewer subagents, or, in an inline review, works each reviewer role itself. It follows [Script results](adding-a-skill.md#script-results): every line goes to stdout, exit 0 is a result (including `RUNNING`, a state to poll again), exit 1 is findings to act on or an expected failure printed as a `FAILED <reason>` line, and exit 2 is only a usage error before any work.

| Command | What it does |
| --- | --- |
| `enumerate [--output FILE]` | Lists each selected repository's open non-draft pull requests and those merged since its watermark, minus already-reviewed heads, into a batch file, and prints `BATCH <file>`. A repository with a watermark lists its open pull requests, then its closed ones from the most recently updated, stopping at the first page whose last one was updated before the watermark; one without a watermark lists its whole history once. Only the pull requests that listing keeps (non-draft, and open or merged on or after the watermark) are looked up in the archive. For each repository listed, it prints `LISTED <repository> scan=<full|watermark> pages=<n> pulls=<n> read=<n> candidates=<n>`: the pages and pull requests listed, the pull requests looked up in the archive, and the `PULL` lines that follow. Without `--output` the file is `batch.json` in a new `review-prs-batch-*` temporary directory. A `--output` inside a skills directory (the one the script runs from, `~/.claude/skills`, or `~/.agents/skills`) is refused with `FAILED` before anything is read, because a file left there makes the deployer skip that skill. A repository whose listing fails, or whose watermark cannot be read, prints `REPOSITORY_FAILED <repository> <error>` and keeps its watermark; the other repositories are still listed and the batch still written, and the command then exits 1, as `collect` does. |
| `prepare [--pull owner/repo#N ...] [--re-review owner/repo#N ... --scope auto\|full\|incremental] [--force] [--canary [--fixture DIR [--re-review --prior RECORD]]] [--host claude-code\|codex\|copilot-cli] [--inline]` | Takes up to four pull requests in all (with `--canary`, only `--pull` and no `--force`), each prepared on its own: `--pull` for an initial review and `--re-review` for a re-review, so one call can mix them. `--scope` is required with `--re-review`, applies to every re-review in the call, and is refused without one. It refuses a pull request named twice, since two runs of it would race to record the same review version. For each, it fetches the pull request, skips an already-reviewed head, times its phases (see "Snapshot size and reads"), writes GitHub's diff and the unresolved review threads a person started, snapshots the head (from `checkout_path`, fetching `refs/pull/N/head` only when the commit is not already local, else from GitHub's tarball), loads the reviewer from its trusted commit, writes the request, and plans one prompt per reviewer role. A re-review carries the open and unverified entries of the finding ledger (see "Finding ledger") and plans its roles for its scope; a pull request with only a migrated legacy review gets an initial review. `--host` names the runtime the orchestrating session runs in, and `review-prs` always passes it (see `runtime` under configuration). `--inline` has the orchestrating session work every role itself, and a runtime that cannot start subagents gets the same for the generic reviewer and specialists (see "Inline reviews"); such a run prints `INLINE <run directory>` in place of its `ROLE` lines. With `--fixture`, it prepares one fixture canary instead, an initial review or, with a bare `--re-review` and `--prior`, a full re-review, and reads nothing from GitHub (see "Fixture canaries"); a failure prints `FAILED <directory> <reason>`. |
| `dispatch --run DIR` | Starts the Copilot CLI host, for the `copilot-cli` runtime only, as a process detached from the command, and prints `STARTED <run directory>` at once, so no runtime's command time limit can stop the review. It records the host's PID and start time in `copilot-host.json` and refuses, with `FAILED <reviewer>: <reason>` and exit 1, while that host is still starting or running, so one reviewer never runs twice. Each attempt keeps the host's own output in `copilot-host-N.log`, Copilot's in `copilot-diagnostic-N.jsonl`, and the host's outcome in `copilot-outcome-N.json`. Copilot writes its result to `copilot-result-N.json`, and the host renames it to the reviewer's result file only when it is a JSON object and the role has not been set aside since `dispatch`, so nothing reads a partial result and a late host never fills a role already set aside. |
| `next-role --run DIR` | For an inline run only, and refused for any other: checks that no sealed file of the run changed, seals every result written so far, and prints `INLINE_ROLE <selector> <id> <prompt file>` for the first role without a result, starting that role's clock the first time it hands it out, or `INLINE_DONE <selector>` once every role has one. A changed or missing sealed file prints `FAILED <selector>: run files changed during the inline review: <paths>` and exits 1. |
| `wait --run DIR --timeout SECONDS` | Waits at most `SECONDS` (1 to 300) for that host and prints one line: `DISPATCHED <result file>` when it finished, `RUNNING <seconds>s` with exit code 0 when it is still going after the timeout, or `FAILED <reviewer>: <reason>` with exit code 1 when it failed, ended without a result, ran past its 30-minute limit, or was never dispatched. `review-prs` repeats `wait --timeout 90` until it stops printing `RUNNING`; `check` then offers a failed reviewer its one rerun, which is another `dispatch`. |
| `workflow --run DIR [--run ...]` | Writes a Claude Code Workflow script, kept in the first run's directory, that starts every reviewer role of the given runs at once with the same task the native path uses, and prints `WORKFLOW <script> roles=<n>`. It refuses a `copilot-cli` run and an inline run. |
| `wait-reviewers --run DIR [--run ...] --timeout SECONDS` | Waits at most `SECONDS` (1 to 300) until no role of the given runs is still running, and returns as soon as none is. It prints `READY <selector>` for a run whose roles all have a valid result. For each other role, it prints `RUNNING <selector> <id> <seconds>s` or `OVERDUE <selector> <id> <seconds>s` once the role has gone an hour since `workflow` handed it out without a valid result. The hour is counted from `workflow`, not from when the role started, so a role queued behind the Workflow tool's concurrency limit is not cut short. Both are states, not failures, so they exit 0; only a `FAILED <run> <reason>` line exits 1. Like `validate-result`, it only reads: an invalid result may be one its reviewer is still fixing, so it counts as running and is left for `check`. It refuses a Copilot CLI host run, which `wait` follows, and an inline run, which `next-role` hands out. |
| `check --run DIR [--run ...]` | Validates each run's reviewer results. An invalid or missing result is renamed `*.rejected-N` and its role is offered for one fresh rerun; a second failure fails the pull request. A run whose Copilot CLI host is still starting or running prints `RUNNING <selector> <reviewer> <seconds>s`, and its role is left as it is. It exits 1 when it prints any `RETRY` or `FAILED` line, and 0 otherwise, including when `RUNNING` lines are all that remain. An inline run is checked against its seal first: a changed or missing sealed file prints `FAILED <run> <reason>` and sets nothing aside. A result set aside is unsealed, so `next-role` hands its role out again. |
| `validate-result --run DIR --role ID` | Run by a reviewer, not the orchestrator: prints `VALID`, or `INVALID <reason>` with exit code 1, using exactly the checks `check` applies to that role. It changes nothing, so it neither sets the result aside nor counts a retry. Every reviewer prompt a native subagent runs names this command and asks the reviewer to fix its result and rerun it, at most twice, before replying. The Copilot CLI host denies shell commands, so its reviewer relies on `check` and `dispatch` alone. |
| `finalize --run DIR [--run ...]` | For each run, assembles the result, assigns finding IDs and the verdict, commits the record pair (or a canary pair under a new temporary root), and removes the run directory. `prepare` records the archive's latest version and the hash of its finding ledger in `run.json`, and `finalize` commits only on top of that same version, so dispositions judged against one version are never applied on top of another: when the archive moved, it prints `FAILED <run> The archive moved since prepare: ...`, naming both versions, and leaves the archive untouched. A failed run directory is kept for inspection. A canary also prints its `STATS` lines before its `RECORDED` line. When another process, such as antivirus, still holds a file in a recorded run, `finalize` retries for a few seconds, then leaves the directory marked recorded and says so in a `NOTE` line. An inline run whose seal no longer holds fails without recording. |
| `unfinalized --run DIR [--run ...]` | Prints `UNFINALIZED <selector> <run directory>` for each given run that still holds a prepared run, and exits 1 if there is any. Otherwise it prints `ALL_FINALIZED`. A run that `check` failed, and one that nobody finalized, both count. A directory that no longer exists counts as recorded, because `finalize` is the only step that removes a prepared run, and so does one `finalize` marked recorded because it could not remove it. Any other existing directory that is not a prepared run prints `FAILED <run> <reason>`. |
| `advance --batch FILE` | Moves each fully enumerated repository's watermark past the merged pull requests whose head now has a review. |

Every `prepare`, `check`, and `finalize` line names its pull request, and one pull request's failure never stops the others in the same call; the command exits 1 if any failed. `review-prs` works in groups of four, so each group costs three pipeline calls however many pull requests it holds, and the group size bounds how many reviewers run at once.

When the Workflow tool is available (Claude Code), every mode (a batch, `--pull` and `--re-review`, and `--canary`) instead prepares every pull request, runs one Workflow from `workflow`, then checks and finalizes every run in one call each. `workflow` prints the script between `BEGIN_WORKFLOW_SCRIPT` and `END_WORKFLOW_SCRIPT`, and the orchestrator passes it inline as `script`. The Workflow tool refuses a `scriptPath` that it didn't return itself and that isn't under the session's working directory, which includes the script `workflow` saves in the run folder under the system temp directory. The script stays compact (each role is its ID, its prompt path relative to the run folder, and its model) because the orchestrator copies it. If the tool still refuses, the roles start as native subagents. No pull request waits for another group's slowest reviewer, the Workflow tool's own concurrency limit bounds the reviewers, and their replies never reach the orchestrating session. A Workflow can only start agents, so `prepare`, `check`, retries of `RETRY` roles (as native subagents), and `finalize` stay with the orchestrator, and `check` still records every rejected result and retry. Codex and Copilot keep the grouped steps.

The Workflow tool returns as soon as it starts the reviewers and reports its completion later as a notification. `review-prs` grants its pipeline commands through `allowed-tools`, and Claude Code applies those grants only in the turn that invoked the skill. A session that ended its turn, or scheduled a wakeup, to wait for the notification had `check` and `finalize` denied in the later turn. A headless session has nobody to approve them, so nothing was recorded, and the session still exited with success. A skill cannot extend its grants, and re-invoking it in the later turn would depend on the same model following an instruction it had already ignored. So the orchestrator never leaves the invoking turn. It repeats `wait-reviewers --timeout 90` until no role is running, or until the Workflow reports it finished, and then checks and finalizes. The `OVERDUE` limit ends the wait even if that notification never reaches the session mid-turn.

In every mode, `review-prs` runs `unfinalized` on every run `prepare` started before it reports. Each `UNFINALIZED` line is reported as that pull request's failure. If any pipeline command is denied, every pull request without a `RECORDED` line is reported as failed. A skill cannot change a headless session's exit status, so the failure is in the report itself.

`prepare` works on a call's pull requests concurrently, and `enumerate` lists repositories concurrently, four at a time to stay clear of GitHub's secondary rate limits. Output keeps the order the pull requests or repositories were given in. Fetches into one checkout still run one at a time, because concurrent fetches contend for its `FETCH_HEAD` and ref locks, and a pull request whose commit another one just fetched skips its own fetch.

A pull request's diff is untrusted bytes, and a file saved in a legacy code page such as Windows-1252 puts bytes in it that are not UTF-8; one stopped `prepare` with a traceback. Every `gh` output is now decoded without failing: the runner keeps each undecodable byte, and the GitHub client replaces each one with U+FFFD before anything reads, writes, fingerprints, or prints it, so `diff.patch` is always valid UTF-8 and reviewers in every runtime see the same text. When it replaced any, `prepare` prints `NOTE <selector> <n> undecodable bytes replaced in the diff`, and `finalize` repeats it. Replacing rather than escaping the bytes loses nothing the review needs: `diff.patch` was never byte-exact, since `gh` output is read as text with its line endings normalized, and nothing applies it as a patch. `finalize`, the specialist planner, and the source snapshot's coverage check all read `diff.patch` through one function that also replaces, so a run prepared before this agrees with one prepared after. Any other `UnicodeError` the pipeline raises ends as `FAILED <selector> <reason>`, never a traceback.

A repository reviewer's trusted files, unlike the diff, are read from git as their exact committed bytes, because their hashes are recorded. Reading them as text once turned CRLF line endings into LF, so the materialized file and its recorded SHA-256 differed from the repository without any warning, and on Windows a byte that is not UTF-8 ended `prepare` in a traceback. The git runner now captures bytes and decodes them itself, keeping every byte and every line ending, so resources, guidelines, entrypoints, and condition scripts saved with CRLF or in a legacy code page materialize unchanged. A file the pipeline has to read as text (the manifest, a review skill, or a specialist profile) that is not UTF-8 ends as `FAILED <selector> <reason>` naming it. A repository path that is not UTF-8 is left out of the file listing used to resolve a review skill's references, since no manifest or skill can name it.

The generic reviewer is planned like a specialist: it gets the same fixed prompt, numbered diff, and line-anchoring checks, with no trusted repository guidance.

In Claude Code, every reviewer runs as the `code-review-reviewer` subagent, which deploys to `~/.claude/agents` with `code-review-core`. It has its own short system prompt, only the tools a role needs (`Read`, `Grep`, `Glob`, `Write`, `Edit`, `Bash`), and `omitClaudeMd: true`, so the session's `CLAUDE.md` files and their imports stay out of its context. A profiled general-purpose reviewer carried about 20,000 tokens of system prompt and tool definitions on every turn, plus about 11,000 tokens of the session's instruction files. A session started before the agent was deployed may not have the type, so `review-prs` falls back to a general-purpose subagent, which runs without the guard below. The Workflow script never does: a role whose guarded reviewer fails is left unfinished, and `check` hands it back as a `RETRY` for a fresh `code-review-reviewer`. A `PreToolUse` hook in the agent definition runs `review_guard.py`, which enforces the run boundary that prompts alone did not: reviewers told never to read the local checkout searched it, and the whole workspace, anyway. A reviewer's first call must be a Read of a role's prompt file, as `run.json` names it, and that read binds the reviewer to that role and run. Parallel reviewers share a session, so the guard tells them apart by the `agent_id` Claude Code puts in a subagent's hook event, and keeps each agent's binding in its own file under the system temporary directory, which no reviewer can write. Nothing is readable before the prompt, so content in a pull request cannot choose the role, and a retry is a fresh agent that binds to the same role. After that, Read, Grep, and Glob must name a path inside the bound `code-review-run-*` folder or `code-review-core`'s `references`, and the guard logs each allowed read of a snapshot file to count it (see "Snapshot size and reads"). Grep and Glob must name it explicitly, since their default is the session's working directory. Write and Edit may touch only the bound role's result file, so a reviewer cannot overwrite another role's result or another pull request's, and Bash may run only that role's self-check command, exactly as the pipeline writes it, and, for a lazy snapshot, that role's `source-file` and `source-search` commands with the one path or pattern the reviewer fills in (see "Source snapshots"). A call the guard cannot evaluate is denied, a call without an agent ID included: a reviewer reading the wrong code gives a plausible but wrong review, while a failed one is reported and retried. Claude Code runs the hook in Git Bash, or in PowerShell when it finds no Git Bash, and Git Bash takes `$HOME` from `HOME`, which need not be the profile folder the guard is installed in. So the hook has Python find the guard with `os.path.expanduser`, which on Windows reads the profile folder in either shell. It runs Python in isolated mode (`-I`), so modules in the session's working directory cannot stand in for the standard library.

### Inline reviews

Where the orchestrating session cannot start subagents, it works the reviewer roles itself. `prepare` dispatches a run this way for the generic reviewer and a specialists manifest when the runtime offers no `agent-delegation` (Copilot CLI today), and for any reviewer when `--inline` is given. `review-prs` passes `--inline` when its session cannot start subagents, such as a review started from inside a subagent, or when the user asks for an inline review. A Copilot CLI entrypoint reviewer still runs on the bounded host. The run prints `INLINE <run directory>` instead of `ROLE` lines, and the session runs `next-role` for one role at a time, follows that role's prompt (the same file a subagent reads, with the same snapshot exclusions, the same self-check, and, for a lazy snapshot, the same source commands), writes its result, and asks again until `INLINE_DONE`. `check`, its retries, and `finalize` are unchanged, so each result is validated exactly as a subagent's is. `run.json` records the run's `dispatch`, and the record's `review.dispatch` and the report's **Review Details** show it: `inline`, `subagents`, or `copilot-host`.

An inline reviewer runs in the orchestrating session, without the `code-review-reviewer` agent's tool list and without its `PreToolUse` guard. Three things stand in for them. The prompt carries the same boundary as a subagent's. The run is sealed: `prepare` records the SHA-256 of every file it wrote in the run except `run.json`, the source snapshot, and the reviewers' results, `next-role` seals each result it moves past, and `next-role`, `check`, and `finalize` fail the pull request, recording nothing and retrying nothing, when a sealed file changed or is gone. And the core validates every result and computes the verdict, as in every mode. So a later role cannot quietly rewrite an earlier role's result, clear a coverage gap or a prior finding from the request, or change the next role's prompt. That is not the guard's equivalent: the session keeps its own tools, permissions, and instruction files, nothing confines what it reads or runs, later roles see the earlier ones in context, a deliberate rewrite of the digests in `run.json` defeats the seal, and the snapshot is not hashed again between roles, which would take minutes on a large one. The [threat model](code-review-operations-contract.md#threat-model) states both. Run inline reviews from a directory outside the checkout, in a session allowed nothing beyond what the pipeline's commands need.

Every inline role runs on the session's model at the session's effort: `prepare` prints a `NOTE` for each role whose manifest or profile names a model, in place of its `MODEL` line. Each role's time starts when `next-role` first hands it out. No guard logs what an inline role reads, so its record gives its `files_read` and `bytes_read` as null, unknown rather than zero. A specialists manifest's `required_capabilities` decides whether its specialists may run inline: listing `agent-delegation` keeps them to subagents, so that manifest fails on Copilot CLI and with `--inline`, and a manifest without it runs either way.

In Claude Code an inline role runs its prompt's commands under `review-prs`'s grant, `python -B "${CLAUDE_SKILL_DIR}/../code-review-core/scripts/*` for Bash and for PowerShell. Claude Code fills in the skill's directory and then compares the command's text, quotes and all, normalizing no path, so the resolved path of the same script, without the `..`, never matches. `prepare` therefore writes each role's self-check and source commands with the script path spelled exactly as the session started `prepare`, which is the spelling the grant matched. The variable itself cannot go in a prompt: Claude Code fills it in only in `SKILL.md` and its grants, and does not set it in the shell. A subagent's prompt gets the same spelling, which the reviewer guard resolves to the known script. A `prepare` started through a relative path, or a path a quoted command cannot hold, gets the resolved path, and each of those commands then asks for approval. Writing a role's result is not granted, because the run lives under the system temporary directory, and a skill's grant can name neither that directory nor an environment variable. So Claude Code asks before it writes each role's result. A headless session cannot ask. It needs an `Edit` allow rule in its own permission settings, written as Claude Code writes an absolute path, such as `Edit(//c/<temporary directory>/code-review-run-*/work/*.result.json)` on Windows, or the write is denied and `check` fails that role.

## Tracker pipeline

`update-pr-tracker/scripts/tracker_pipeline.py` runs every deterministic step of `update-pr-tracker`. Like the review pipeline, it follows [Script results](adding-a-skill.md#script-results): each command prints one fact per line on stdout and exits 0 with its result, prints `FAILED <reason>` and exits 1 for an expected failure, and exits 2 only for a usage error.

| Command | What it does |
| --- | --- |
| `collect [--output FILE] [--repository owner/repo ... \| --repository-set NAME]` | Resolves the scope with `operation_repository_sets.update-pr-tracker`, reads each repository's open pull requests with one paginated GraphQL query per page of 50 (author and display name, requested reviewers, participants, draft state, base branch, head, update time, review decision, and the configured user's latest submitted review and its commit), joins each pull request's reviewed head, coverage, verdict, counts, finding-ledger summary (for a review recorded before ledgers, of the ledger the pull request's records compute; for a migrated legacy review, its report's counts as open findings, with `addressed` and `version` null), flagged open findings, what moved since the configured user's last review, and report from the archive and the flag store, validates the result, and writes the tracker input. Prints `REPOSITORY <repo> pulls=<n>` or `REPOSITORY_FAILED <repo> <error>` per repository, then `INPUT <file>` when every repository succeeded, or else `FAILED <n> of <m> …` without writing an input, exiting 1, as `enumerate` does. Without `--output` the file is `input.json` in a new `update-pr-tracker-input-*` temporary directory; a `--output` inside a skills directory is refused with `FAILED` before anything is read, as for `enumerate`. |
| `update --input FILE [--remove owner/repo#N ...] [--candidates]` | Renders the owned dashboard section, taking the dashboard path, login (`github_login`, else the account `gh` is authenticated as), markers, status overrides, author names, short-link repositories (the default set), and configuration link from the configuration. Compares commits four at a time (see "Dashboard markers" for what it compares). Prints `UPDATED <dashboard> rows=<n>`, then `GITHUB_CALLS <n>`, the GitHub requests the update made (retries included), and, with `--candidates`, `CANDIDATE missing\|stale owner/repo#N`. When a GitHub call a comparison needs fails, it prints `PULL_FAILED owner/repo#N <error>` for each pull request whose comparison failed, then `FAILED <n> of <m> …`, and exits 1 without writing the dashboard, as `collect` does for a failed repository (see "Dashboard markers"). |
| `override [--set owner/repo#N=STATUS ...] [--clear owner/repo#N ...]` | Lists, sets, or clears `dashboard.status_overrides` without reading GitHub. Alone it prints `OVERRIDE owner/repo#N <status>` for each override, keyed and trimmed as `update` matches it, then `OVERRIDES <n>`. With `--set` or `--clear` (each repeatable) it applies every change in one write, printing `SET owner/repo#N <status>` or `CLEARED owner/repo#N` per change, then `WROTE <configuration>`. Every other value is kept as written, with no default filled in, and the file is validated as `review_config.py write` validates it, before and after it is serialized. The layout is normalized as that command writes it, with keys sorted and two-space indentation, so a hand-formatted file comes back reformatted. A malformed key or `--set` value, an empty or computed status, a pull request named twice, or clearing one with no override fails with `FAILED` and writes nothing. It never checks that the pull request is open, so a closed one's override clears like any other. |

The **Findings** cell reads the latest review's finding ledger (see "Finding ledger" below), and every row uses one grammar: the remaining work, then the progress. It starts with open findings by severity, using the column's `M`, `H`, and `S` letters, and how many of them have a flag in the flag store (`1M 1S open (1 flagged)`, or `none open`). Then comes what moved since the configured user's last GitHub review of the pull request: `· 1 new, 1 addressed since your review`, or `· unchanged since your review`. Its baseline is the latest review version whose head is the user's review commit, or failing that, the latest one GitHub's compare API places before it (`identical` or `ahead`). An exact head match needs no API call. When every version comes after that commit the baseline is version 0. New entries were raised after the baseline and are still open; addressed entries were raised by the baseline and closed as `addressed` after it, so no entry counts as both. Without a review by the user, or when GitHub no longer has one of the commits (a force-push can remove one), the cell counts the ledger's entries closed as `addressed` instead, such as `1H 3S open · 2 addressed` or `none open · 5 addressed`, and shows the open findings alone when there are none, such as `2M open`. No version number appears in the cell; the report link's file name (`review-v<n>.md`) carries it. A review recorded before ledgers is summarized from the ledger its pull request's records compute, never from its own counts: such a re-review counted only the findings it raised, not a prior one it judged still present, so it renders like any other. A migrated legacy review's findings were never converted, so it shows its report's counts as open findings alone (`1H 2S open`), or `-` when the report is unreadable. One legend line inside the tracker block, above the first section, reads `Findings: M must fix, H should fix, S suggestion; flagged means you flagged it with flag-review-finding.`; a tracker with no rows has none.

`collect` writes its input only when every repository succeeded. Rendering from a partial collection would silently drop the failed repositories' rows, so a repository failure fails the update closed and the dashboard keeps its previous rows. Repositories are collected four at a time. Missing GitHub CLI, authentication failures, and rate limits stop the collection immediately: queries not yet started are cancelled, and nothing is written. A pull request with more than 100 review requests or participants, or whose configured user's active review has no commit, fails its repository rather than being tracked from incomplete data. Team review requests are ignored, because a team never matches the configured login.

## Review insights

`review-insights/scripts/review_insights.py` reads the configured archive and summary root. A report reads only validated review records and names every record file and payload hash it analyzed. A `summary_root` inside a skills directory (this suite's own, `~/.claude/skills`, or `~/.agents/skills`) is refused before a report writes anything, because a file left there makes the deployer see a skill as modified. Each command that writes a report (`report`, `synthesize`, `decide`, and `decide-custom`) holds a lock in the report's directory, `.locks/insights.lock`, from reading the report to writing it, so two runs at once never lose each other's decisions. A report, and the synthesis context beside it, is at most 64 MiB: a write that would exceed it is refused before anything is written, and a read of a larger file is refused, so the script never writes a report it cannot read back.

| Command | What it does |
| --- | --- |
| `scope` | Prints `CURRENT_REPOSITORY <repo> set=<name or none>` when the working directory is inside a configured repository's `checkout_path`, or inside a worktree whose main checkout is (the innermost when checkouts nest), and otherwise `NO_CURRENT_REPOSITORY`; then `DEFAULT_SET <name> <repos>`, the set a report uses when none is named. `set=` names a configured set whose only member is that repository, the default set first, so the skill can report it under that set and keep its decision history; with none, the skill passes `--repository`. The skill asks the user which to analyze only when it printed `CURRENT_REPOSITORY`. |
| `report --start DATE --end DATE [--repository owner/repo ... \| --repository-set NAME]` | Analyzes validated review records reviewed in the inclusive range, resolving the scope with `operation_repository_sets.review-insights`. Writes `<summary_root>/<set>/<start>--<end>/insights.json` and `insights.md`; an explicit repository list uses `repositories-<digest>` as its set name. Prints `REPORT <json>`, `MARKDOWN <md>`, one `RECOMMENDATION <id> <category> findings=<n> decision=<d> flags=<ids or none>` per category (with a recorded synthesis, followed by its `TOPIC <id> <n> <topic>`, `ASSESSMENT <id> <text>`, `ADDRESSED_BY <id> <ids or none>`, and, for a category of five findings or fewer, `FINDING <id> <finding> <assessment>` lines), one `ANALYZER <id> coverage=<c> tool=<t> rule=<r> findings=<n> repositories=<repos> decision=<d> flags=<ids or none>` per `available` or `known` analyzer rule, followed by up to three `EXAMPLE <id> <repo>#<pull> v<version> <finding> <title or path:line>` lines, and last one `CUSTOM_CANDIDATES rules=<n> findings=<n> decision=<d or mixed> flags=<ids or none>` line for every `custom-candidate` rule together (with a recorded synthesis, followed by its `PATTERN <n> rules=<n> <pattern>`, `PATTERN_ASSESSMENT <n> <text>`, and `PATTERN_ADDRESSED_BY <n> <ids or none>` lines). Each custom-candidate rule is still its own recommendation in the report and its Markdown. Each recommendation line is followed by its `REVIEWER <id> <reviewer> model=<m> findings=<n> flagged=<n> addressed=<n> still_present=<n>` lines. Before them come the synthesis lines (see "Synthesis" below): `SYNTHESIS_PROMPT <prompt>` and `SYNTHESIS_RESULT <result>` while it is pending, `SYNTHESIS recorded <time>` and the synthesized recommendations' lines once it is recorded, or `SYNTHESIS skipped`. A category, tool, or rule is printed screened, as `decide` takes it inside double quotes: whitespace becomes one space, and a double quote, backtick, `$`, backslash, or control character becomes `?`; the report keeps the recorded value. Regenerating a report keeps each subject's ID, decision, and history; a new subject gets an ID no earlier version of the report gave, even to a subject a later regeneration dropped. |
| `synthesize --report FILE --result FILE [--check]` | Records the synthesis result the report named, or with `--check` only checks it. Fails without changes, after one `PROBLEM <text>` line per problem found (at most 20), unless the result is the file the report named, the input and context still match the hash the report sealed them with, and the result passes every check below. Prints `VALID <result>` for a check; otherwise `MARKDOWN <md>`, `SYNTHESIS recorded <time>`, then per synthesized recommendation, highest priority first, `SYNTHESIZED <id> type=<t> priority=<p> decision=<d> flags=<ids or none>`, `TITLE <id> <title>`, `TARGET <id> <repository:file or analyzer coverage tool rule>`, `CHANGE <id> <text>`, `RATIONALE <id> <text>`, and up to three `EXAMPLE <id> <finding>` lines, and last `SYNTHESIZED_COUNT <n>`. A report whose synthesis is recorded refuses another until its input changes, and `--check` refuses it too. |
| `decide-custom --report FILE --flags IDS\|none accepted\|rejected\|deferred [--note TEXT]` | Records one decision for every custom-candidate analyzer recommendation, as the user was asked about them in one question. Fails without changes unless the report has custom-candidate recommendations and the union of their linked flags is exactly the flags the user was shown. Accepting resolves those flags that are still open, after the decision is written, as `decide` does. Prints `FLAG_RESOLVED <flag>`, `FLAG_ALREADY_RESOLVED <flag>`, and `DECIDED custom-candidates rules=<n> <decision>`. |
| `decide --report FILE <id> (--category NAME \| --analyzer COVERAGE TOOL RULE \| --synthesized TITLE) --flags IDS\|none accepted\|rejected\|deferred [--note TEXT]` | Fails without changes unless `<id>` still names that category, analyzer rule (tool and rule match without regard to case), or synthesized title (matched without regard to case), named as the report printed it or as recorded, and links exactly the flags the user was shown, so a flag linked by a later regeneration is never resolved without reconfirmation. Appends a timestamped entry to the recommendation's `decision_history` and sets its current decision. Accepting resolves the recommendation's linked flags that are still open through the locked flag API, after the decision is written, so a resolved flag always names a decision the report holds. When the flag store fails partway, the decision entry is rewritten to list only the flags it resolved and the command fails, naming the flags left open; running the same command again resolves them. Prints `FLAG_RESOLVED <flag>`, `FLAG_ALREADY_RESOLVED <flag>`, and `DECIDED <id> <decision>`. |

Analyzer recommendations come from the optional `analyzer` coverage reviewers give a finding (see "Analyzer coverage" below). Findings are grouped by coverage, tool, and rule, and ranked cheapest first: `available` rules (in an analyzer the repository already has, so enforcing the rule stops the finding recurring), then `known` rules (adopting an analyzer, which must clear the dependency rules on license, cost, and telemetry), then `custom-candidate` patterns (a custom rule would have to be written). Each lists the repositories its findings came from and every finding it covers as `evidence`. A finding with coverage belongs to both its category's recommendation and its rule's, so accepting either resolves its flag, and accepting the other then reports `FLAG_ALREADY_RESOLVED`. Report schema version 5 adds each recommendation's `kind`; every recommendation in an earlier report is a category one.

A finding is counted once across the reviews that carry it, by its ledger entry (see "Finding ledger" below): a finding a re-review linked as a repeat counts with the finding it repeats, from the earliest review in the range that carries either. Each `REVIEWER` row also counts how many of its findings a later review judged `addressed` and how many `still_present`: the latest disposition a review made after the last review that raised or repeated the finding. A finding no later review judged counts as neither, even when the review that repeated it also judged it still present. These are read from every review of the pull request, in range or not, so a finding raised in the range and fixed after it still counts as addressed. They measure whether findings are acted on without anyone flagging them. Report schema version 6 adds them; a row in an earlier report has `null` for both, shown as `-`, until the report is regenerated.

A flag is linked to a recommendation when it is open, names a repository, pull request, review version, and finding, and that finding, or the finding it repeats or one that repeats it, is among the recommendation's findings. Finding IDs restart at `F001` in every review, so a flag is matched only against the review it names, never a later re-review. Links are computed when the report is written and stored in `linked_flags`, so `decide` resolves exactly the flags the report listed. Report schema version 2 adds `decision_history` and `linked_flags`, and version 3 links each flag only to the review version it names. `decide` still reads version 1 and 2 reports and upgrades them when it records a decision, but drops their links: a version 2 report linked a flag to whatever finding had its ID in the latest review, so a decision on an earlier report resolves no flag until the report is regenerated.

The flag store is `CODE_REVIEW_FLAGS`, else `~/.coding-agent-skills/code-review/flags.json`, for both `review-insights` and `flag-review-finding`. Flag store schema version 2 adds `review_version`, which a flag naming a finding must set. A version 1 store is read as version 2 with no review versions and is written as version 2 on its next change; its flags that name a finding are never linked by `review-insights`, because their finding IDs cannot be tied to one review. `flag-review-finding add` refuses a finding ID that is not of the form `F001`, such as the whole label `v2 F003`, and a finding that review of the pull request does not have in the configured archive; a flag saved before it checked keeps its finding ID, which links to nothing. A store whose `finding_id` is not a string or null fails to load.

### Synthesis

The deterministic recommendations count findings; the synthesis reads them. `report` writes three files beside `insights.json`, and `review_synthesis.py` builds them. Every field of the report, of each kind of input line, of the context, and of the result is stated under [Insights report](code-review-operations-contract.md#insights-report), [Synthesis result](code-review-operations-contract.md#synthesis-result), [Synthesis input](code-review-operations-contract.md#synthesis-input), and [Synthesis context](code-review-operations-contract.md#synthesis-context) in the behavior contract's formats:

- `synthesis-input.jsonl`, what the analyst agent reads, one JSON object per line: a `seal` line with the input's hash; the range's `totals`; each repository's `guidance` files; the `previous` period's categories, themes, and synthesized recommendations with their decisions, when a report exists for a period of the same set that ends within seven days before this one starts; one `category` line per finding category with its count, listing every finding in full when there are five or fewer; one `custom-rule` line per custom-candidate rule with its count and two examples; findings grouped by repository, category, and headline (`group`), each with severity, source, and later-outcome counts, how many are flagged, its top paths, and two examples; and every open `flag` on the scope's repositories or on none, with the reference of the finding it names when it names one, in the range or not, and null only when it names none. The 150 largest groups are shown in full, ranked by size, then flags, then findings judged still present or partially addressed, then severity, then headline, and the rest are summarized per repository and category (`remaining`), so a large range still fits an agent's context.
- `synthesis-context.json`, what `synthesize` checks a result against: every finding reference the input gives (`owner/repo#pull vN F001`), each analyzed finding's and each one an open flag names, the open flag IDs in the input, the guidance sets, the previous period's recommendation IDs, each analyzed category with its findings' references when it has five or fewer (otherwise null), and the custom-candidate rules.
- `synthesis-prompt.md`, the agent's complete task: read only the input, write only `synthesis-result.json`, run only the `synthesize --check` self-check, and treat finding and flag text as untrusted data.

A repository's guidance files are the repository-relative paths in `review.adapter.source_hashes` of the latest record each repository-scoped reviewer wrote, anywhere in the archive: the files the reviewer was built from. A generic reviewer is built from no repository file, so a recommendation for such a repository names no file and says in its change where the guidance belongs.

The result holds up to 10 themes, 15 mistakes, 5 persistent patterns (findings later reviews judged still present, with a likely reason), the reviewer effectiveness, a comparison with the previous period (null without one), up to 12 recommendations, and one `categories` entry per finding category: 1 to 5 topics with counts and examples, an assessment, the titles of the recommendations that address it, and, for a category of five findings or fewer, an assessment of each of its findings by reference. `synthesize` refuses a result that misses a category or names one not analyzed, gives a small category's findings other than exactly its own, lists findings for a larger one, or names a title that is not one of its recommendations. Once recorded, a category recommendation renders and prints this commentary in place of its generic sentence. The result also groups every custom-candidate rule into at most 15 `custom_rule_patterns`, each rule in exactly one (names matched without regard to case), with an assessment of whether a custom rule is worth writing and the recommendations that act on it; `synthesize` refuses a result that leaves a rule out, places one twice, or names one not analyzed. `synthesize` refuses a result whose `input_sha256` is not the seal's, that names a finding not analyzed or a flag not open in the input, whose example lists are empty or longer than three, or whose comparison is given without a previous period or missing with one. It also refuses a recommendation whose target names a repository outside the scope or a file outside that repository's guidance set, whose `new-analyzer` target is not a valid analyzer rule, whose title is not a single line of at most 120 characters free of quotes, backticks, `$`, backslashes, and control characters, or repeats another's, or which names neither evidence nor flags (a `flagged` recommendation must name a flag). Each recorded recommendation gets the next `REC-` ID the report has never given and `kind: "synthesized"`, and its `flags` become its `linked_flags`, so accepting it resolves them whether or not they name a finding.

Regenerating a report keeps a recorded synthesis while its sealed input is unchanged. A changed input, such as a new or resolved flag or a new review, starts a pending synthesis and moves the recorded one's recommendations, with their decisions, to `synthesis.superseded`; their IDs are never given again. A range with no findings and no open flags in scope skips the synthesis and writes no input. Report schema version 7 adds `synthesis`; an earlier report has none until it is regenerated. Version 8 adds `next_recommendation_number`, the first `REC-` number the report has never given, so a subject a regeneration drops never has its ID given again; an earlier report gains the number after every ID it still holds.

## Configuration

Set `CODE_REVIEW_CONFIG` to an alternate file for fixtures or profiles. Otherwise the suite reads `~/.coding-agent-skills/code-review/config.json`. Every field, its type, and when it is required are listed under [Configuration](code-review-operations-contract.md#configuration) in the behavior contract's formats.

```json
{
  "schema_version": 1,
  "default_repository_set": "primary",
  "repository_sets": { "primary": ["example/example-repository"] },
  "repositories": {
    "example/example-repository": {
      "reviewer": {
        "id": "generic",
        "protocol_version": 1,
        "trusted_ref": null,
        "scope": "generic",
        "manifest_path": null
      },
      "checkout_path": null
    }
  },
  "archive_root": "D:\\AgentData\\Reviews",
  "local_mirror_root": null,
  "summary_root": "D:\\AgentData\\ReviewSummaries",
  "dashboard_file": "D:\\AgentData\\PullRequests.md",
  "github_login": null,
  "runtime": "auto",
  "verdict_policy": {
    "request_changes_for": ["MUST_FIX"],
    "should_fix_threshold": 3
  },
  "dashboard": {
    "start_marker": "<!-- code-review-pr-tracker:start -->",
    "end_marker": "<!-- code-review-pr-tracker:end -->",
    "status_overrides": {},
    "author_names": {}
  },
  "model_names": {}
}
```

`runtime` is the runtime that starts reviewers, which decides how they are dispatched: `ROLE` subagents under `claude-code` and `codex`; under `copilot-cli`, the Copilot CLI host for a repository entrypoint reviewer and an inline review (see "Inline reviews") for the generic reviewer and specialists. Naming one always wins. `auto`, the default, uses the runtime `prepare --host` states, which `review-prs` passes from the session it runs in, and only without a host falls back to the first of `claude`, `codex`, and `copilot` found on `PATH`. `PATH` says which CLIs are installed, not which one is orchestrating, so a Codex or Copilot session on a machine that also has `claude` would otherwise dispatch as Claude Code. Each run's `run.json` records the stated `host` (`null` without one) beside the resolved `runtime` and its `dispatch`.

`reviewer_effort` optionally sets the reasoning effort (`low`, `medium`, `high`, `xhigh`, or `max`) of every reviewer the Workflow tool starts; `null`, the default, keeps the session's effort. A specialist's own `effort` in its manifest wins over it. It exists to measure whether reviewers think more than a review needs, because thinking was about 80% of a profiled reviewer's output tokens and most of its wall time. Change it only alongside a before-and-after comparison of real reviews: lower effort can miss findings the way a smaller model did. An ordinary subagent cannot take a per-call effort, so it applies only on the Workflow path.

`re_review_scope` optionally sets when an `auto` re-review reviews the whole pull request: `full_share` (default `0.5`) is the share of the pull request's changed lines that changed since the last review, and `full_lines` (default `1000`) is a number of such lines; reaching either means a full pass. Tune them from the scope each record keeps, against what later full passes found.

`model_names` optionally maps the model identifier a reviewer reports to the name a report's **Reviewers** table shows, for example `{"arn:aws:bedrock:us-east-1:111122223333:application-inference-profile/abc123": "Opus 5.5"}`. An inference-profile ARN names no model, so this is the only way to see which model reviewed. Review Details still lists each mapped identifier beside its name, and an identifier with no entry shows as it is. Keys are trimmed single lines of at most 200 characters, and names are single lines of at most 100. A name is applied when a report is written, so changing it doesn't rewrite earlier reports.

`operation_repository_sets` optionally gives an operation its own default set, used when no repositories or set are named: for example `{"review-prs": "primary", "update-pr-tracker": "tracked"}`. Valid operations are `review-prs`, `update-pr-tracker`, and `review-insights`; without an entry the operation uses `default_repository_set`. A repository with no merged-pull watermark yet starts at the first run's date, so its first batch reviews only open pull requests.

A review's verdict is `CHANGES_REQUESTED` when its findings require it, otherwise `INCOMPLETE` when a changed file's source was unavailable to reviewers (excluded from the snapshot for size, an unsafe name, or the repository's `snapshot_exclude`; listed in the record's `review.coverage.unavailable_sources` and in the report), otherwise `APPROVED`. A coverage gap never hides a blocking finding. Changed files a reviewer manifest deliberately leaves unreviewed (`"uncovered": "ignore"`) are listed in `review.coverage.uncovered_files` and in the report's **Not reviewed** note, and do not change the verdict. A specialist or reviewer that produces no valid result is different: the result is `failed`, nothing is archived, and the pull request is retried on the next run.

`snapshot_exclude`, in a repository's entry beside `checkout_path`, optionally lists glob patterns of files to leave out of that repository's source snapshot: files a code reviewer has little reason to open, which every review would otherwise write and hash. Without a checkout, a review still downloads GitHub's whole tarball and hashes every entry to check it against the commit's tree, so there exclusion saves only the write. A pattern matches a whole path from the repository root, ignoring case. `*`, `?`, and `[...]` match within one folder or file name, and a `**` segment matches any number of folders, none included, so `*.resx` matches only a file at the root and `**/*.resx` one at any depth. For a .NET repository, resources, designer files, and generated reports might be:

```json
"snapshot_exclude": ["**/*.resx", "**/*.Designer.cs", "**/*.rdlc", "Reports/Generated/**"]
```

A matching file is recorded in the snapshot's manifest as a `configured` exclusion and never written, whether the snapshot is lazy, whole, or GitHub's tarball. A reviewer that asks for one with `source-file` gets `EXCLUDED <path> configured`, and `source-search` leaves it out. A changed file the patterns match still reaches its reviewers as diff, but its source is unavailable, so the review is `INCOMPLETE`: the author of a pull request cannot hide a change behind the maintainer's exclusion. Leave out of the list the generated files pull requests often change, and the analyzer settings (`.editorconfig`, project and `Directory.Build` files, and the like) that the analyzer inventory reads from the snapshot. `validate-reviewer` refuses a pattern that matches a file the reviewer's manifest declares, and its `SNAPSHOT` line counts the `configured` exclusions, so check a new list with it. The default, `[]`, leaves nothing out.

A migrated legacy review (`legacy-review.json`, written by the completed legacy migration) counts as a reviewed head for skip detection and the tracker's `current`/`stale` column. It has no structured findings, so `review-prs --re-review` of a legacy-only pull request runs an initial review that becomes version 1.

Validate or atomically replace configuration with:

```powershell
python -B skills/code-review-core/scripts/review_config.py validate D:\AgentData\config.json
python -B skills/code-review-core/scripts/review_config.py write candidate.json --output D:\AgentData\config.json
```

Without a path, both use `CODE_REVIEW_CONFIG` or the standard path. `validate` prints `VALID <config path>` and `write` prints `WROTE <config path>`, each exiting 0. An invalid or unreadable file prints `FAILED <reason>` on stdout and exits 1, and `write` then changes nothing. Exit 2 means the arguments themselves were wrong.

For a repository-provided reviewer, set `scope` to `repository`, give it a symbolic `id`, and configure an absolute checkout path. Then name the reviewer one of three ways:

| Fields | Reviewer | Use when |
| --- | --- | --- |
| `manifest_path` | A manifest committed to the repository, read from the trusted commit. | The repository maintains its own manifest. |
| `skill` | The repository's own review skill or agent file, run as one entrypoint reviewer with the repository files it names. | The skill does not start subagents of its own. |
| `skill` + `manifest` | The same skill's specialists, routed by a manifest kept outside the repository. | The skill starts specialist subagents and the repository should not change. |

`skill` is a safe repository-relative path. `manifest` is an absolute path, or `true` for `reviewers/<owner>/<repo>/manifest.json` beside the configuration file; it cannot be combined with `manifest_path`. `trusted_ref` may override the PR base commit, but pull refs and a ref resolving to the reviewed head are rejected.

The reviewer is read from `trusted_ref` when one is set, and otherwise from the pull request's base commit. A long-lived branch can start before the repository added its review skill, so its base has no `skill` file. Without a `trusted_ref`, `prepare` then reads the skill from the default branch's tip, as `git ls-remote origin HEAD` reports it now, fetching that commit if the checkout lacks it. When the tip lacks the skill too, or the tip is the pull request's own head, the suite's generic reviewer reviews that pull request instead. Either way `prepare` prints a `NOTE` naming the base, the tip, and the skill, and the record's `review.adapter.source` says where the reviewer came from: `base`, `trusted-ref`, `default-branch`, `generic` for a repository configured with the generic reviewer, or `generic-fallback`; the report's Review Details show it as **Reviewer source**. A skill file only the pull request's head holds is never used. The fallback applies to a `skill`, with or without a local `manifest`; a `manifest_path` the base lacks, or a `skill` its `trusted_ref` lacks, still fails the pull request, since those name the commit to read on purpose.

### Choosing and checking a repository reviewer

A review skill that starts its own subagents fails when it runs as a reviewer, because a subagent cannot start subagents. Two read-only commands tell you whether a skill needs a manifest, and whether a manifest works:

```powershell
python -B skills/code-review-core/scripts/review_pipeline.py inspect-reviewer --repository owner/repo
python -B skills/code-review-core/scripts/review_pipeline.py validate-reviewer --repository owner/repo --pull 123
```

`inspect-reviewer` reads the configured `skill` at the trusted ref (or `--ref`) and prints its `TOOLS`, `DELEGATES yes|no|unknown` with the reason and `EVIDENCE <line> <text>`, the repository files it names as `REFERENCES`, and a `VERDICT`:

- `entrypoint-ok`: its tool list rules out Agent and Task, or its text never asks for a subagent. `skill` alone is enough.
- `manifest-required`: it may start subagents and its text says it does, or it names another agent file. `skill` alone is refused at `prepare`; write a specialists manifest that routes those agents directly, pointing its profiles at the existing agent files.
- `undetermined`: its tool list grants Agent or Task but its text never says why. It runs as an entrypoint with a note; add a manifest if its review fails.
- `manifest-configured`: a manifest is set.

The tool list is the skill's frontmatter `tools`, or `allowed-tools` when it has no `tools`. It may be a YAML list, or text whose entries are separated by commas or spaces, with `Bash(git log:*)` kept as one entry. No list means every tool is inherited. The skill's frontmatter, like each specialist profile's, is read by the suite's shared frontmatter reader, the one that reads skill and agent frontmatter when the suite deploys. Keys are matched exactly, so `Tools:` is not `tools`. A block that reader cannot read fails the review with `FAILED`, naming the file and the reader's reason: one that is not closed, a line that is not `key: value`, a duplicated or nested `tools`, or an alias such as an unquoted `tools: *`. The review never guesses a grant. A tool list that grants neither Agent nor Task rules delegation out. Otherwise a line of the skill's body is evidence when it uses a delegation phrase (a subagent, `subagent_type`, the Agent or Task tool, or spawning) or names one of the repository's agents, an `.md` file under `.claude/agents/` or `.github/agents/`, by its file name. An agent named like `db-review` or `SecReview` counts wherever its name appears as a whole word, matched case-sensitively. An agent named after a plain word, like `review` or `Security`, counts only where the text names an agent: in a code span, followed by "agent" or "subagent", or on a line that also delegates (one of the phrases above, delegate, or start, launch, run, dispatch, or invoke with "agent" later on the line). So "review it and report findings" is ordinary prose, while "start the review agent" names the `review` agent. A named agent's files also become references, which the entrypoint reviewer receives.

`validate-reviewer` proves a reviewer setup without starting a reviewer or writing anything. It prints the reviewer and its source, `FILES <n> found` after reading every file the manifest names (profiles and resources at the trusted commit, condition scripts beside a local manifest), and `UNMATCHED <specialist> <pattern>` for an include pattern that matches no file in the repository. For each `--pull`, it reads the reviewer where `prepare` would: the trusted ref or the base, else, for a configured review skill the base predates, the default branch's tip, else the suite's generic reviewer (see "A review skill or reviewer file the pull request adds or rewrites" in the [contract](code-review-operations-contract.md#threat-model)). It prints `PULL <owner/repo#number> base=<commit> head=<commit> files=<n> reviewer=<source>`, where the source is the `review.adapter.source` the record would name, followed by `BODY characters=<n> given=<n>`, the length of the pull request's description and how much of it `prepare` would give reviewers, and `prepare`'s `NOTE` on a fallback, and, when the generic reviewer stands in, `GENERIC files=<n>` in place of the routing below. It measures the source snapshot `prepare` would write on the route `prepare` would take ("Source snapshots" below), with the same exclusions, and prints `SNAPSHOT <commit> source=<checkout-lazy|checkout> files=<n> fetchable=<n> bytes=<n> limit=<n> excluded=<reason>:<n>,...`: for the reviewer's commit without `--pull`, and for each pull's head (where a changed file keeps its 16 MiB allowance) with it. On the lazy route, `checkout-lazy`, `files` and `bytes` are the changed files, the analyzer settings, and the paths the routed conditions' `reads` match, which are written, and `fetchable` the other files, which are listed; the whole route, `checkout`, writes every file, for a routed condition that declares no `reads` and for an entrypoint reviewer on the Copilot CLI host. `--host`, as on `prepare`, names the runtime that decides an `auto` runtime, and only an entrypoint reviewer's route depends on it. A snapshot over the size limit by the files it writes, or over the file-count limit by the files it writes and lists, prints `FAILED` with the largest top-level directories, because `prepare` would refuse it. For each `--pull`, it prints which specialists would start (`ROUTE`), each condition script's real result against the pull's head, on the snapshot a review gives it (`CONDITION open|closed`), or `GENERIC` when none matches. When some specialists route, it prints `UNCOVERED <path>` for each changed file no specialist matches, then `GENERIC files=<n>` when the generic reviewer will review them or `UNREVIEWED files=<n>` when the manifest sets `uncovered` to `ignore`. A file matched only by a specialist whose condition is closed is skipped on purpose and is not listed. It ends with `VALID`; any missing file, invalid manifest, or failing condition script prints `FAILED`. Rerun it when the repository's own routing changes, since a local manifest is a hand-kept copy of that routing.

A local manifest supplies only its condition scripts, from its own folder. Every profile and resource it names is read from the repository's trusted commit, never from the pull-request head, and a condition script may not share a path with one of them.

## Re-review scope

Every review records a fingerprint of each changed file's patch in `review.patches`. A fingerprint hashes only the added and removed lines and the file's header lines (a binary file uses its new blob ID), never hunk positions, context, or the base side's blob, so a base merge or rebase that leaves a file's change alone leaves its fingerprint alone. A re-review compares the fingerprints at the new head with the latest record's; a file whose fingerprint differs, or that the record did not have, has changed since that review.

A re-review always names its scope; nothing picks one silently. `update-pr-tracker` asks once per run for its stale reviews, and `review-prs --re-review` asks when no `--scope` was given:

- `full` reviews the whole pull request again, as an initial review would, and gives every prior finding a disposition.
- `incremental` reviews in full only the files that changed. A specialist none of whose files changed only gives dispositions for its prior findings and comments, and is left out when it has none. A pass in which nothing changed still records the new head with a dispositions-only generic reviewer.
- `auto` runs `full` when the changed files' lines reach `re_review_scope.full_share` of the pull request's changed lines or `re_review_scope.full_lines` lines (counting files instead when nothing has changed lines), and `incremental` otherwise.

`incremental` and `auto` fall back to `full` when the latest record has no fingerprints (it was written before they were recorded) and for a repository entrypoint reviewer, which always reviews everything. `prepare` prints the scope used as `NOTE <selector> Scope <scope>, <files> of <total> files and <lines> of <total> changed lines differ from v<n> (requested <scope>: <reason>)`, and the record keeps the same facts in `review.scope`, which the report shows.

## Finding ledger

Finding IDs restart at `F001` in every review, so a problem's identity across versions is the chain of dispositions, which every record now makes explicit in its `ledger`. The ledger has one entry for every problem raised since the pull request's latest initial review. An entry is identified by the version and ID where it first appeared, written `v1:F001`, and records its severity and category, its state, the version that last judged it (`judged_in`), each later review's disposition, and the findings linked to it as repeats. `finalize` computes it, and the verdict, the report, `update-pr-tracker`, and `review-insights` read it.

- **State.** An entry is `open` when its latest judgment raised or repeated it, or found it `still_present` or `partially_addressed`. It is `closed` when the latest is `addressed` or `superseded`, and `unverified` when `unable_to_verify`.
- **Verdict.** `calculate_verdict` counts open entries, not the latest record's findings. A must-fix carried from an earlier review therefore requests changes until a review closes it, even when the review that judged it reported no findings, such as a dispositions-only pass of an incremental re-review. `request_changes_for` and `should_fix_threshold` apply to open entries as they did to findings. An `unverified` entry does not count, but is offered again.
- **What a re-review is given.** A re-review is given every open and unverified entry as a prior finding, with ID `v<n>:F<nnn>`, at the place it was last reported. That includes an entry the previous review only judged, so nothing drops out of the history unjudged. A record with a ledger names its prior dispositions by those IDs. An entry with a flag (see **Flags** below) is given with the flag's ID, category, and rationale.
- **Repeats.** A finding that reports the same problem as another one sets `repeats` and is counted with it, never twice. In a reviewer's result, `repeats` names another finding in the same result (a specialist gives its 0-based index; the adapter protocol a `candidate_key`) or a prior finding ID the reviewer judged `still_present` or `partially_addressed`. The record stores it as `{"version": <n>, "id": "F<nnn>"}`. The target must be at least as severe, must not be a repeat itself, and must exist; validation rejects anything else, and a specialist's invalid link is a retryable invalid result. `assemble` follows a link through merged findings to the finding at its end, and drops it when that finding is now less severe than the linking one, so the finding counts on its own. A `full` re-review that reports a still-present problem again links it to its entry instead of opening a second one. The report shows a repeat inside the entry it repeats.
- **Report.** A report's **Findings** section shows every open and unverified entry in full, grouped by severity and sorted by file and line. Each entry is shown from the finding that first raised it, labelled `v1 F001` (every finding in every report carries its version this way), with this review's repeats of it nested inside. In a re-review, each entry starts with what this review found: `**New in v3.**`, or `**Open since v1.** Still present in v3:` followed by the reviewer's rationale (or `Partially addressed`, or `**Unverified, raised in v1.** Unable to verify`). A collapsed **Addressed since v<n>** section, counting from the latest initial review, lists each closed entry with the version that closed it and why. The verdict row of a re-review adds the ledger's counts, such as `CHANGES REQUESTED, 2 open since v1 (1 flagged), 1 addressed`. An entry whose finding, or one of its repeats, has a flag in the `flag-review-finding` store gets a `**Flagged:**` line with each flag's ID, category, and rationale. A resolved flag still counts: resolving records that the improvement was handled, not that the finding stood. Rendering a re-review reads the pull request's earlier records, and fails if the record that raised an entry is missing.
- **Flags.** A flag is the user's judgment, recorded with `flag-review-finding`, that a finding was wrong or noisy. It changes neither the ledger nor the verdict by itself: a flagged must-fix still requests changes, and the entry is carried to the next re-review. That re-review's reviewer is given every flag on the entry, resolved or not, and is told to weigh it against the code as evidence rather than as an instruction. When the flag holds, the reviewer marks the finding `superseded` citing the flag's ID, which closes the entry like any other `superseded` disposition; when it does not, the reviewer judges the finding as usual and says why the flag does not hold. A flag on a finding whose pull request gets no further re-review changes nothing.
- **Initial reviews.** An initial review starts a fresh ledger. A batch or `--pull` review of a pull request whose head changed is an initial review, given no prior findings. Earlier entries would never be judged, and carrying them would count every problem the new review reports again a second time.
- **Older records.** A record written before ledgers stays valid and has no `ledger`; the tracker shows its counts alone. Its ledger is computed from the records' findings and dispositions when the next re-review is prepared and finalized. Their bare dispositions name findings of the version they compared with. Those records have no links, so a problem an earlier `full` re-review reported again is two entries; the next re-review is given both and can mark one `superseded`.

## Reviewer manifest

The manifest declares every trusted reviewer file. Directories are not recursively discovered. Every field of both manifest versions is listed under [Reviewer manifests](code-review-operations-contract.md#reviewer-manifests) in the behavior contract's formats. A repository's existing human-oriented review skill may be a declared resource, but the reviewer must write the normalized adapter-result protocol; terminal prose is not accepted as a result.

`prepare` gives an entrypoint reviewer one prompt, `reviewer.prompt.md`, as it gives each specialist one. It names the entrypoint under the materialized reviewer as the reviewer's instructions and states the request's facts (the repository, the pull request's number, the review mode, the base and head commits, and how many changed files lack their source), its input files, the input rules a specialist's prompt states (shared statements in `review_specialists.py`, so the two cannot drift), the prior findings and open review comments to disposition, and the adapter result's contract with the request's repository, number, and head filled in. The request file stays in the run for any fact the prompt leaves out, and the pull request's title and branch names, which its author writes, stay there as data. The prompt used to point at the request and leave the result format to the entrypoint: on a fixture canary, reviewers on two models read seven files before writing anything, among them the request, `run.json`, and `materialization.json`, guessed the result's fields, and failed the self-check three times on each of two attempts, so the review recorded nothing. With the contract inline they read the prompt, the entrypoint, its rules, and the diff, and wrote a valid result at once, in about half the turns.

```json
{
  "schema_version": 1,
  "id": "repository-review",
  "protocol_version": 1,
  "supports": ["initial", "re-review"],
  "required_capabilities": ["agent-delegation", "read-diff", "write-result"],
  "entrypoint": ".claude/skills/repository-review/SKILL.md",
  "resources": [".claude/skills/repository-review/references/rules.md"],
  "agent_profiles": [".claude/agents/repository-review.md"]
}
```

The core verifies the checkout's GitHub origin, resolves the trusted ref to a commit, rejects symlink entries and unsafe paths, materializes only declared blobs, and records the source commit and SHA-256 hash of every loaded file.

### Specialist reviewers

A repository whose review is split across specialist agents declares them instead of writing an orchestrating entrypoint. The suite routes changed files, starts one agent per matched specialist, and assembles their results; the repository supplies only data and trusted instruction files.

```json
{
  "schema_version": 2,
  "id": "repository-specialists",
  "protocol_version": 1,
  "kind": "specialists",
  "supports": ["initial", "re-review"],
  "required_capabilities": ["agent-delegation", "read-diff", "write-result"],
  "resources": ["docs/review/conventions.md"],
  "specialists": [
    {
      "id": "database-review",
      "category": "Database",
      "profile": ".claude/agents/database-review.md",
      "include": ["^db/.*\\.sql$"],
      "exclude": [],
      "resources": ["docs/review/database.md"],
      "when": null
    }
  ],
  "conditions": {
    "compatibility-window-open": {
      "script": "tools/review/compatibility_window.py",
      "reads": ["db/migrations/**", "global.json"]
    }
  }
}
```

- `include` and `exclude` are Python regular expressions searched against repository-relative paths. A specialist runs when at least one changed file matches an `include` pattern and no `exclude` pattern.
- `when` names a condition. Its script, materialized from the trusted commit, runs as `python <script> --source-root <snapshot>`; exit code 0 enables the specialist, 1 skips it, and anything else fails the review. Conditions are evaluated only for specialists that matched files.
- A condition may declare `reads`, the snapshot paths its script opens besides the changed files, as glob patterns matched as `snapshot_exclude` matches them: case-insensitive, `*`, `?`, and `[...]` within one segment, and a `**` segment for any number of segments. At most 100 distinct patterns of at most 200 characters, each repository-relative, without a backslash, a control character, or an empty, `.`, or `..` segment; `[]` says it reads nothing else. When every condition a review would run declares `reads`, the lazy snapshot (see "Source snapshots") also holds the paths they match and stays lazy, so declare them to keep a review from writing the whole snapshot. The script then sees only the changed files, the analyzer settings, and those paths: a path it opens without declaring is missing, and its result may change, so check it with `validate-reviewer`, which runs each condition on the snapshot a review gives it. A path `snapshot_exclude` matches is never written, declared or not. A condition without `reads` keeps the whole snapshot.
- `resources` are trusted files any specialist may read. A file has one role in a manifest, so a shared resource may not also be a profile, a specialist's own resource, or a condition script; two specialists may still name the same profile or the same guideline. Each specialist's own `resources` are materialized too: these are its guideline documents, so they are read from the pull request's base commit when that commit contains them (a pull request into a release branch is reviewed against that branch's rules) and from the trusted ref otherwise. Profiles, shared `resources`, and condition scripts always come from the trusted ref, which must hold the manifest. `materialization.json` records each guideline's source commit in `guideline_sources`. Specialist ids are slugs; `generic-review` is reserved.
- A specialist may set `model` (`inherit`, `sonnet`, `opus`, `haiku`, or `fable`) and `effort` (`low`, `medium`, `high`, `xhigh`, or `max`) in the manifest. Both are optional and are validated with the manifest, and either may be `null`, which means no setting, exactly as an absent key does, so the keys can stay in the manifest while their values are changed. The manifest's `model` wins over the profile's (`inherit` means the session's model, whatever the profile says; `null` leaves the profile's, else the session's), and its `effort` wins over the configuration's `reviewer_effort` (`null` leaves that, else the session's). A setting for one specialist beats a general one. Effort reaches only reviewers the Workflow tool starts: an ordinary subagent cannot take one, so the native path, including the Workflow fallback, drops it. `validate-reviewer` shows each route's resolved settings as `ROUTE <id> files=<n> model=<model> effort=<effort>`: the model it asks for and the effort a Workflow agent starts on, the specialist's or else the configuration's, each left out when the session's applies. Use these settings only alongside a before-and-after comparison of real reviews: a cheaper model or lower effort can miss findings.
- Otherwise, a profile's frontmatter `model` is applied when its reviewer starts: `prepare` and `check` print `MODEL <selector> <id> <model>` after that role's `ROLE` or `RETRY` line, the orchestrator passes it to the native subagent, and `workflow` passes it to the Workflow agent. Only the aliases `sonnet`, `opus`, `haiku`, and `fable` are applied, because the Agent tool accepts no other value and on Bedrock a bare model name can be silently ignored. The aliases are Claude Code's: Codex's native delegation takes only its own model identifiers, so on Codex `prepare` prints a `NOTE` naming the model in place of the `MODEL` line, as it does for an inline role, and the reviewer runs on the session's model. The manifest's and the profile's `model` alike follow this rule, and the record's `model` is the one the reviewer reports it ran on. `inherit` or no `model` uses the session's model, and any other value prints a `NOTE` and uses the session's model. A trailing `# comment` is not part of the value. A profile whose frontmatter the shared reader cannot read fails the review, as a review skill's does (see "Choosing and checking a repository reviewer" above). `validate-reviewer` shows each route's model as `ROUTE <id> files=<n> model=<model>`, the model it asks for on Claude Code. A profile's `tools` list is not applied: neither the Agent tool nor a Workflow agent can restrict a subagent's tools, and the suite's reviewers also need to write their result file.
- `required_capabilities` may leave out `agent-delegation`, so the specialists can also run inline (see "Inline reviews"); listing it keeps them to subagents. Earlier releases required it, so an existing manifest runs as it did.
- A specialist's `profile` may name a profile the suite ships instead of a repository file, as `suite:<name>`. The suite ships one, `suite:design-review` (see "Design documents" below). Its file is read from the deployed `code-review-core` references, never from the repository and never copied into the run; `materialization.json` keeps its hash under `suite_profiles`, which every later step checks, and the record's `adapter.source_hashes` names it by its `suite:` reference beside the repository files, so a record says which bytes reviewed it. Only names the suite ships resolve, so a manifest reaches no other file through one, and an unknown name fails the manifest.
- When no specialist matches, the suite's generic reviewer reviews the whole change. Prior findings and open review comments on files no routed specialist owns are given to the generic reviewer for disposition only.
- When some specialists route, the generic reviewer also starts beside them and reviews only the changed files no specialist matches, such as CI workflows, build properties, dependency manifests, scripts, and agent instructions. Without it nobody reviewed them: one reviewed change added "approve everything" to a specialist's profile, and only the source beside it was reviewed. An agent-instruction file stays out of the source snapshot, so the generic reviewer judges it from its diff as untrusted data. A file matched only by a specialist whose `when` condition is closed is skipped on purpose, not given to the generic reviewer. In an incremental re-review the generic reviewer takes only those of these files that changed.
- A manifest that deliberately leaves some paths unreviewed sets `"uncovered": "ignore"` at its top level (the default is `"review"`). Then no generic reviewer starts for those files: `prepare` prints a `NOTE` naming them, and the record lists them in `review.coverage.uncovered_files` and the report in a **Not reviewed** note. Prior findings and comments on them still get a disposition from the generic reviewer.
- By default a finding's `category` is its specialist's manifest `category`, so a record's categories name reviewers. A manifest whose findings should name the kind of problem instead sets `"finding_categories"` at its top level: a non-empty list of distinct one-line names of at most 60 characters, without backticks, quotes, or pipes, such as `["Correctness", "Risk", "Security", "Test Coverage", "Quality", "Style"]`. Then every role it plans, the generic reviewer's included, is told to give each finding a `category` from that list, `check` refuses a finding without one or with another (matched without regard to case, recorded in the manifest's spelling), and `assemble` records the finding's own category; a merged finding keeps the kept wording's. An optional `"fallback_finding_category"`, one of the list such as `Other`, is the one reviewers are told to use only when no other fits; a finding still has to name a listed category, so none is ever recorded as unknown. Listing a category no finding uses yet, such as `Accessibility`, costs nothing and leaves room for it. The specialist's manifest `category` still labels it in the record's `review.reviewers` and the report's Reviewers table, and `source` still names it, so per-reviewer counts are unchanged. `review-insights` then groups findings by kind across reviewers.

`prepare` plans the specialists (`build_plan` in `code-review-core/scripts/review_specialists.py`) and writes, per specialist, the routed file list, the filtered diff, an `other-changes.diff` of every changed file outside its scope, and a self-contained prompt. Both diffs are numbered: each hunk line keeps its `+`, `-`, or space marker first, then shows its line number in the new file (blank on removed lines), then ` | ` and the text. A separate table of added lines used to repeat every added line in each reviewer's context on every turn, about 25,000 tokens per turn for one specialist on a large pull request. The prompt maps the specialist's instructions onto those inputs: no `git` or `gh` commands, repository documents under the materialized root, source under the snapshot, finding lines only from the numbers on the diff's added lines, and independent reads made in the same turn. When the repository has a `checkout_path`, the prompt forbids reading it: one reviewer read half its context files from the local working copy, which may be on another branch, instead of the snapshot. `prepare` also prints a `NOTE` when the orchestrating session itself runs inside the checkout, because then the checkout's `CLAUDE.md` files and project memory load into every reviewer on every turn. It also names the other changes as read-only context, because the snapshot holds only the code after the change. They exclude the specialist's own files, which a whole-pull-request diff repeated for the rest of the review. The prompt lists the other changed files, up to 50 (an `other-files.txt` names them all), and tells the specialist not to read their diff unless its instructions need a caller, consumer, or contract outside its own files. When every reviewer read the other changes, the three smaller specialists on one large pull request roughly doubled their turns and their cache writes, investigating changes their checks did not need. A specialist judging what the previous version did, such as whether a caller that still runs during a rolling upgrade breaks, reads the removed lines there. Without it, a database reviewer cleared an in-place change to a stored procedure's result columns: it couldn't see that the same pull request had rewritten the procedure's C# consumer, and judged that consumer from the head source alone. Findings still come only from the specialist's own added lines. Each specialist writes `{model, summary, findings, prior_dispositions, comment_dispositions}`, where `model` is the model ID its system prompt says it runs on (or `unknown`), and every finding carries a one-line `title` of at most 120 characters that the report uses as its headline, and, when the manifest declares `finding_categories`, a `category` from them. A finding may also carry `repeats` (see "Finding ledger"). `check` validates every result; `assemble` drops findings that are not on an added line of that specialist's own files, merges two findings at the same path and line when one description contains the other, or when they come from different specialists and name mostly the same code (identifier overlap of at least half, three or more in common), keeping the most severe finding's title, wording, severity, and category, requires exactly one disposition for each prior finding and each open review comment, and writes the adapter result. Any missing or invalid specialist result yields status `failed`, which is never archived.

#### Design documents

The suite's `design-review` specialist reviews design documents as designs rather than as text: whether the requirements and constraints the design relies on are stated and met, whether each rejected alternative says why, which risks and failure modes have a path and no mitigation, which open questions decide the design and have no owner, whether the document agrees with itself (its prose with its tables and examples), with the architecture it states, with the repository's own design document such as `docs/design.md`, and with the other documents in the change, and how a change to stored data rolls out and back. Its instructions are `code-review-core/references/design-reviewer.md`. A repository routes its design documents to it in its specialists manifest, and lists its categories in `finding_categories` so each finding names the kind of gap:

```json
{
  "id": "design-review",
  "category": "Design",
  "profile": "suite:design-review",
  "include": ["^docs/design/.*\.md$"],
  "exclude": [],
  "resources": [],
  "when": null
}
```

The categories are `requirement-gap`, `alternative-unstated`, `risk`, `open-question`, `inconsistency`, and `rollout`, with `other` as the `fallback_finding_category`; a manifest whose other specialists review code lists its own categories beside them. Every other changed file keeps its own route, or the generic reviewer. Only Markdown routes today: a `.docx` or `.pdf` design document has no text a reviewer can anchor a finding to until the suite extracts it. The `design-gaps` and `design-clean` scenarios under `tests/fixtures/skill-evals/review-prs/` measure it ([Skill evaluations](skill-evaluations.md)).

### Analyzer coverage

A reviewer can mark a finding a diagnostic analyzer could catch with `analyzer: {coverage, tool, rule}`, and leaves it out when finding the issue needs judgment about intent or behavior. `coverage` is `available` (a rule in an analyzer the repository already has, left unenforced by its settings), `known` (a rule in an established analyzer the repository does not use), or `custom-candidate` (no existing rule; `rule` is a lowercase kebab-case pattern name of at most 60 characters, reused for every occurrence of the pattern). `tool` and `rule` are single tokens of at most 100 characters. The field is optional in the adapter protocol and in records, so records written before it existed stay valid, and the report adds an **Analyzer** line to the finding.

`plan` builds `analyzers.json` from the source snapshot with `code-review-core/scripts/review_analyzers.py` and names it in every prompt as `ANALYZERS_FILE`, so a reviewer needs no turns to find the repository's analyzers. It lists analyzer packages and `Analyzer` items referenced from MSBuild files, the SDK's own analyzers and code-style rules for SDK-style projects, and analyzers identified by their configuration files (ruff, flake8, pylint, mypy, pyright, ShellCheck, PSScriptAnalyzer, ESLint and its plugins, and others), plus the settings that decide which rules run and how severely: MSBuild analysis properties, `.editorconfig` and `.globalconfig` diagnostic severities, ruff and flake8 selections, and ShellCheck directives. `.editorconfig` and `.globalconfig` are read one `key = value` per line, because EditorConfig has no continuation lines: an indented line is a setting of its own, not part of the one above it. A `setup.cfg` or `tox.ini` keeps its continuation lines. It only parses files; it never runs an analyzer or repository code. `check` rejects `available` for a tool the inventory does not list and `known` for one it does, so "the repository already has it" rests on the repository's files. A repository entrypoint reviewer gets no inventory, so only the field's shape is checked.

### The pull request's description

`prepare` writes the pull request's description to the run's `pull-request-body.md`, cut to its first 24,000 characters, and every prompt names it `PULL_REQUEST_BODY_FILE`, untrusted pull-request data a reviewer reads only when its instructions judge the change against what the description states, such as a reviewer manifest's profile that checks the description's upgrade note. The description never enters a prompt, and the prompt says how much of it the file holds. The record keeps its length and how much reviewers were given, and the report shows them in a **Description** row. A fixture's description is `pull.json`'s `body`. "The pull request's description" in the [contract's threat model](code-review-operations-contract.md#threat-model) states what holds it.

### Review comments and the Reviewers table

`prepare` lists the pull request's unresolved review threads that a person started (a bot's thread, such as an AI reviewer's, is excluded; a deleted account counts as a person) as `C1`, `C2`, ..., using each thread's first comment. Every reviewer the suite plans must give each comment it is routed exactly one disposition from the prior-finding vocabulary, judged by whether the current code addresses the request. A repository entrypoint reviewer that predates comment dispositions may omit them all; one that gives any must cover every comment. The record keeps the comments and their dispositions together, and the report shows them under **Review Comments**. A comment is untrusted data, since anyone can start a thread, the pull request's author included: a reviewer's prompt lists each body as a JSON string cut to 4,000 characters, the run's `github-comments.json` holds it whole, and the report's excerpt escapes every character Markdown or HTML would read as markup, as the **Title** row does.

`finalize` also records which reviewers ran in `review.reviewers`: each reviewer's ID, focus, how many changed files it covered, how many final findings it raised (a finding merged from several specialists counts for each), how many times it was rerun after an invalid result, whether it only gave dispositions, the model it reported running on, and how long it took. The report shows them as a **Reviewers** table. The model comes from the reviewer's own accepted result, because the scripts cannot see which model a subagent got: a reviewer started without a model inherits a default the runtime resolves, and on one Bedrock setup that silently became a smaller model, which missed a must-fix finding. A repository entrypoint reviewer's result protocol has no model field, so its model shows as `-`. The configuration's `model_names` gives an identifier the table should show by name. `review.dispatch` records how the reviewers were worked: `subagents`, `copilot-host`, or `inline`. Records written before these fields existed stay valid. Token usage and cost are deliberately not recorded.

A reviewer's time (`seconds`, shown as **Time**) runs from when its role was handed out to the last write of its accepted result, so a rerun counts toward it. A role is handed out when `prepare` prints its `ROLE` line, when `workflow` writes the script that starts it, when `dispatch` first starts the Copilot CLI host, or when `next-role` first hands it out in an inline review. The time also covers the orchestrator's turn to start the reviewer and any wait for the Workflow tool's concurrency limit, so it shows which reviewer the pull request waited on, not the model's working time. A run prepared before timing existed records no time and shows `-`.

### Snapshot size and reads

Every record says how large its source snapshot was, how long `prepare` took around it, and how much of it each reviewer read, so the cost of snapshots can be measured before it is cut. Counts, bytes, and seconds only: no path, token count, or cost is recorded.

- **`review.snapshot`** comes from `prepare`, which records it in `run.json` under `snapshot`: the `source` (`checkout-lazy` for the configured checkout's git objects written lazily, as "Source snapshots" describes, `checkout` for them written whole, which a fixture canary's throwaway repository counts as too, or `tarball` for GitHub's), the `files` the snapshot holds when `prepare` has written it and their `bytes`, its manifest left out, the head's paths it left `excluded`, counted by reason (`configured` among them for a repository with `snapshot_exclude`), and the seconds of three phases to a tenth. `fetch` is checking the checkout's remote and fetching the head when it is not local, or downloading the tarball and checking it against the commit's tree; `materialize` is writing and hashing the snapshot; `prompts` is writing the request and every role's prompt. The report shows it as the **Snapshot** row of **Review Details**, which names the exclusion counts after the size.
- **`files_read` and `bytes_read`** of each reviewer come from the reviewer guard. When a `code-review-reviewer` claims its role, the guard creates that role's read log, `work/reads-<role>.log` in the run, and appends each allowed Read of a file, or Grep of one file, under the run's `source` folder as one JSON string, the path relative to the snapshot; `source-file` appends each file it fetches or finds there in the same way, so `files_read` counts fetches as well as reads. A Glob, a Grep of a folder, or a `source-search` reads no particular file and is not counted. `check` reduces the log of each role it accepts to the number of distinct files it names and their sizes, adds them to the role's counts in `run.json`'s `reads`, and deletes the log, so no path outlives `check`; a role set aside keeps its log, and its rerun adds to it, so a file both attempts read counts once. `finalize` reduces any log `check` did not reach. A file counts whole, whatever part of it was read, and a line that names no file of the snapshot counts for nothing. The report shows the counts as the **Files read** column of the Reviewers table.
- **Unknown, not zero.** A reviewer no guard held has no read log, and its record gives both counts as null, which the report shows as `unknown`: an inline reviewer, the Copilot CLI host, a Codex reviewer, and the general-purpose subagent `review-prs` falls back to. A guarded reviewer that read nothing of the snapshot has an empty log and records `0`.
- **Earlier records and runs.** A record written before these fields has neither, and its report shows no Snapshot row and `-` under Files read; a run prepared before them records neither. The record's schema version is unchanged, but an earlier release refuses a record that has them, and likewise one whose snapshot has `excluded`.

The read log changes nothing a reviewer may do: the guard writes it and only `check` and `finalize` read it, a reviewer may write nothing but its own result, and a reviewer can change its counts only by reading more or less, which the counts then report. A canary's `finalize` prints the same numbers after its `SHA256` lines, one `STATS <selector> snapshot source=<source> files=<n> bytes=<n> excluded=<reason>:<n>,... fetch=<s>s materialize=<s>s prompts=<s>s` line (`excluded=none` when nothing was left out, and no `excluded` for a record written before exclusions were counted) and one `STATS <selector> reviewer <id> files_read=<n> bytes_read=<n>` line per reviewer, with `unknown` for null.

## Source snapshots

Every adapter request includes a source snapshot materialized from the exact PR head commit. Snapshot files are hashed as they are written, and `prepare` then verifies the snapshot's structure once: its manifest, its exact file set, the size limits, and that no path is a reparse point or escapes its root. Nothing untrusted runs between the write and the request, so the request and the reviewer plan take the manifest that verification returned rather than checking the snapshot again. Verification walks the snapshot once, folder by folder: it enters a folder only when its directory entry is no reparse point and it resolves inside the root, and it judges each file from its directory entry, so its cost grows with the folders, not with each file's depth. The Copilot CLI host starts its reviewer in a process of its own, so `prepare` also stamps the snapshot for it, in `run.json`: one SHA-256 over the manifest's bytes and each written file's path, size, and modification time, as the snapshot's directory listing gives them. Before it starts Copilot, the host checks the structure again, which refuses a file added, removed, or replaced by a link, and takes the stamp again from that walk. While the two match, every file keeps the size and time it had when `prepare` hashed it, so the host re-reads only the files dated no earlier than the manifest, which a rewrite in the clock tick they were written in would leave with the same time, and each file a lazy snapshot has fetched, against its blob id. When they differ, or a run prepared before stamps has none, it re-reads and re-hashes every file, so a file changed since `prepare` is refused. Under real-time antivirus each file read costs milliseconds, so re-reading a large repository's snapshot takes minutes, where the stamped check reads a directory listing per folder. Files are written from a small thread pool for the same reason. Agent configuration and instruction paths—including `CLAUDE.md`, `AGENTS.md`, `.claude/`, `.agents/`, `.codex/`, and GitHub agent/skill/instruction paths—are excluded so a pull request cannot replace its own reviewer instructions. Repository-specific rules needed by a reviewer must instead be declared in its manifest and are materialized separately from the trusted base commit.

Reviewers may read the snapshot and write only their result: the reviewer guard holds a Claude Code reviewer to its role's result file, and the Copilot CLI host grants a write to its staging file only. A Codex reviewer, or the general-purpose subagent `review-prs` falls back to, has no such hook, so its prompt is its only boundary, and an inline reviewer has neither, so its run's seal stands in for part of it (see "Inline reviews"); the [threat model](code-review-operations-contract.md#threat-model) lists what a pull request's author controls and the test that holds each guarantee. The snapshot holds the head commit's exact blobs. With `checkout_path`, `prepare` lists the commit's tree with `git ls-tree` and reads each blob from the checkout's object store with `git cat-file`, with no worktree or branch change. Neither command consults `.gitattributes` or git configuration, so `export-ignore` cannot leave a changed file out, and `export-subst`, line-ending conversion, and filters cannot rewrite one. The snapshot used to come from `git archive`, which applies all of them, including the `core.autocrlf=true` that Git for Windows sets in its system configuration.

With `checkout_path`, the snapshot is lazy. Reviewers read a handful of the head's files besides the diff (a measured review read 6 of 11,685), so `prepare` writes only the changed files and the analyzer settings `analyzers.json` is built from, and lists every other file the snapshot would hold, with its blob id, in `source-snapshot.json` under `fetchable`. Every role's prompt then names two commands of `code-review-core/scripts/review_source.py`, which the reviewer guard allows for that role alone:

- `source-file --run "<run>" --role "<role>" --path="<path>"` writes the head file at `<path>` into the snapshot and prints `SOURCE_FILE <file>` for the reviewer to Read. It reads the blob from the checkout's object store by the id the manifest lists and refuses bytes that do not hash to it, so the exact-head guarantee holds without the file having been written up front. It prints `EXCLUDED <path> <reason>` for a path the snapshot leaves out, and decides `binary` only now, writing nothing for it. A path the manifest does not list, in any spelling, prints `FAILED`, with nothing written.
- `source-search --run "<run>" --role "<role>" --pattern="<pattern>"` runs `git grep` with an extended regular expression at the head commit, so the files nobody fetched are searched too, and prints `MATCH <path>:<line>: <text>` for each match in a path the snapshot can hold, at most 200, leaving out every file the snapshot's own test finds binary, whatever attributes the checkout sets: a file it lists to fetch is tested the first time it matches, read from the object store as `source-file` reads it, then `MATCHES <n>` or `MATCHES more than <n>; narrow the pattern`.

The path or pattern may hold no double quote, backtick, dollar sign, backslash, or line break, which the guard refuses, so it cannot leave its quotes in either shell. A fixture canary's throwaway repository moves into the run as `repository`, where the commands read it until `finalize` removes the run. The snapshot is written whole instead, recorded as `checkout`, where its reviewers could not fetch a file: for the Copilot CLI host, which runs no command, and for a specialists manifest whose routed specialist names a `when` condition that declares no `reads`, since that condition script reads the snapshot as it chooses. When every condition a review runs declares `reads`, the snapshot stays lazy, recorded as `checkout-lazy`, and also holds the paths they match, which the scripts read in place.

A repository without `checkout_path` is snapshotted from GitHub's tarball of the commit, which GitHub builds with `git archive`. `prepare` checks the tarball against the commit's tree from GitHub's trees API. A file missing from it, an extra one, a file with different bytes, or a listing GitHub truncated ends the pull request as `FAILED <selector> <reason>`, naming the paths. Set `checkout_path` for a repository whose attributes change its archives.

A file the repository's `snapshot_exclude` matches is a `configured` exclusion, as "Configuration" describes, and a coverage gap when the pull request changes it.

Binary files (a NUL byte within the first 8,000 bytes, the same test Git uses) and files over 1 MiB are recorded as explicit `binary` or `file-size-limit` exclusions in `source-snapshot.json` and do not count toward the 256 MiB snapshot total; reviewers still see their changes in the diff. Files the pull request changes are kept up to 16 MiB. A path Windows cannot hold as it is named is recorded as an `unsafe-path` exclusion and never written: a reserved or control character, a backslash, a segment ending in a dot or a space, a reserved device name such as `CON` or `nul.txt`, a segment over 255 UTF-16 code units, or a path longer than the room the run's folder leaves it (259 units for a file and 247 for its folder, the folder's own path included, or 32,507 where Windows has long paths enabled). So is a name that is not UTF-8, which the manifest names with U+FFFD for each undecodable byte, as `diff.patch` does. Such a file makes the verdict `INCOMPLETE` only for a pull request that changes it, every other pull request of the repository is reviewed in full, and `validate-reviewer` counts it among the exclusions. The "Threat model" section of the [contract](code-review-operations-contract.md#threat-model) lists every rule with its reason. A changed path that no reviewer prompt can carry safely (one with a control character below U+0020, U+007F, or a character Python treats as a line break, a backslash, or an absolute, empty, `.`, or `..` segment) is left out of every prompt, work file, and link: no reviewer is given the file, `prepare` notes it with the path escaped, and the request lists it among the unavailable sources, so the review is `INCOMPLETE`. A pull request that changes only such files fails. Two paths that differ only by case fail the snapshot, because a case-insensitive filesystem would merge them. Exceeding the file-count or total-size limit also fails closed.

A symbolic link is recorded as a `symbolic-link` exclusion, and any other entry that is not a regular file or a directory (a hard link, FIFO, or device entry) as `non-regular`. Nothing is written for either, and no link is ever created or followed, so the snapshot still holds only regular files. These entries used to fail the whole snapshot, so a pull request that committed a link to a machine-local path by mistake got no review at all, only a `FAILED` line. Yet that link is exactly what a review should report. For each link the pull request adds or changes, `prepare` prints `NOTE <selector> snapshot excludes symbolic link <path>`, and `finalize` repeats it. The prompt of the reviewer whose scope holds the link names it with the target from the diff's added line, quoted as untrusted text, and says that committing a symbolic link, above all one to an absolute path, is itself a finding to raise on that line. A link already in the repository is recorded without a note, so a repository that keeps links is not told about them on every review. Like `binary` and `agent-instruction`, these exclusions are deliberate and never make the verdict `INCOMPLETE`.

## Dashboard markers

Create exactly one marker pair in the configured dashboard before running `update-pr-tracker`:

```markdown
<!-- code-review-pr-tracker:start -->
<!-- code-review-pr-tracker:end -->
```

Missing or duplicate markers fail without modifying the file.

The tracker renders one section per state, each headed with its row count: `To Review`, `Awaiting Response`, `Drafts`, one section per pinned override, and `My PRs`. When there are rows, the Findings legend line comes first, above every section. Each section is a collapsible `<details>` block whose table groups rows by requestor (`Requestor | PR | AI Result | Findings | AI Review`; `My PRs` shows `PR | Status | ...` with GitHub's review decision). AI Result is the latest review's verdict, Findings its open findings and then what moved since your review, or what was addressed before you reviewed (see the **Findings** paragraph after the command table above), and AI Review a `vscode://file/` link to its report, marked `(stale)` or `(incomplete)` when applicable. Empty sections are omitted. Section placement depends only on the configured user's own latest GitHub review:

| User's latest review | PR changed since that review | Section |
|---|---|---|
| None or dismissed | — | `To review` |
| `CHANGES_REQUESTED` or `COMMENTED` | changed | `To review` |
| `CHANGES_REQUESTED` or `COMMENTED` | unchanged or unknown | `Awaiting response` |
| `APPROVED` | changed or unknown | `To review` |
| `APPROVED` | unchanged | omitted |

"Changed" is computed by the tracker, not judged by the agent, from GitHub's comparison of each commit with the current base branch (`base...sha`). A pull request is unchanged only when both commits change the same set of files, with the same status and previous name, and leave every one of them identical in both content and Git file mode (executable, symlink, or submodule), so a review of the earlier commit applies unchanged to the later one. Any difference, including a merge commit that resolves a conflict or brings in other work, is a change.

Each commit's fingerprint is the sorted list of the files its comparison changes, each as its path, status, previous path, blob ID (from the comparison), and Git mode (from the commit's recursive file tree, empty for a removed file). Two fingerprints are equal only when they list the same files with the same first four parts and the same modes, so commits whose comparisons already differ in a file's path, status, previous path, or blob have different fingerprints whatever the modes are: that is a change, decided without reading either tree. The trees are read only when the two comparisons list the same files, at least one of them not removed, because only a mode can then tell the commits apart, such as a script made executable or a file replaced by a symbolic link. The update reads every comparison it needs four at a time, then every tree those comparisons leave undecided, through the one GitHub client whose rate-limit backoff governs each call, and reads each commit's comparison and tree at most once.

Evidence it cannot obtain or that proves nothing, such as a reviewed commit or base branch GitHub reports missing (a force-push can remove a commit), a comparison listing GitHub's maximum of 300 files, a truncated file tree it needs, or commits that have already reached the base branch, is unknown, so uncertainty never moves a requested-changes review into `To review`. A tree it does not need cannot make the answer unknown: differing comparisons are a change even in a repository too large for GitHub to list its tree in full.

A GitHub call that fails for any other reason is not evidence, and never makes a review `stale`. Missing GitHub CLI, authentication, rate-limit, network, and timeout failures stop the run at once with `FAILED <reason>`, since every later call would fail alike. Any other failure, such as a refused request (HTTP 403), results an organization's SSO withheld, a server error, or a malformed response, fails the comparison of each pull request that needed the call: the update still compares the others, then prints `PULL_FAILED owner/repo#N <error>` for each pull request that failed and a last line `FAILED <n> of <m> pull requests could not be compared; the dashboard keeps its previous rows`, and exits 1. Nothing is written and no candidate is printed, so every row keeps the section and AI review status it had, and no review is offered again because a call failed. Rerun once GitHub answers; a pull request that fails every time can be left out of the run with `--remove`. `collect` treats the same failures alike: one while placing the user's review commit fails its repository with `REPOSITORY_FAILED`, and network and timeout failures stop the collection.

The `AI review` column is independent of section placement. It reports `missing`, `current`, `stale`, or `incomplete`, using the same change detection against the latest validated AI review's head commit, so base-branch merges do not make a review stale. `incomplete` is an unchanged head whose review could not read every changed file in full; it is not offered for review again until the head changes. Draft pull requests are offered like any other, so their AI review is ready before they leave draft.

Dashboard status overrides are for exceptional pinned states the normal classifier cannot derive, such as `on hold` or `delegated`. Do not add an override merely because a review finished or a pull request merged. Computed states are rejected as overrides. `update-pr-tracker` sets and clears them with `tracker_pipeline.py override` rather than editing the configuration by hand. An override lasts until the user asks to clear it: nothing compares overrides with closed pull requests, so one whose pull request has closed stays in the configuration, showing nowhere, until it is cleared, which works like clearing any other.

The Requestor column shows each author's GitHub profile name, or their login when the profile has none. `dashboard.author_names` optionally maps a login to the name to show instead, for example `{"octocat": "Mona Lisa"}`, for authors with no profile name or one you would rather not display. Logins match ignoring case, so two entries that differ only in case are rejected; names must be non-empty single lines. Rows within a section sort by the name shown. It applies only to rendering, so an edit takes effect on the next `update` without recollecting.

When the user directly says a pull request is approved, looks good, or can be removed, pass its full `owner/repo#number` key with `--remove`. This removes only its dashboard row and updates the generated counts; it never submits a GitHub review or records a persistent override.

After updating the tracker, `update-pr-tracker` lists pull requests whose AI review is missing or stale and asks whether to generate or refresh them. The prompt contains no cost estimate. Use `--no-review` to update the dashboard without that prompt. When any is stale, the same prompt asks once how to re-review them (`auto`, `full`, or `incremental`; see "Re-review scope"). It then makes one `review-prs` call for everything confirmed, with `--pull` for each missing review and `--re-review` for each stale one with that `--scope`, so the pull requests are reviewed in one pass rather than one after another.

The bundled generic reviewer prompt and result schema are loaded from the installed `code-review-core/references` directory. They do not depend on a repository checkout, its current branch, or a hard-coded local path.

## Legacy reviews

The one-time migration from the legacy local skills is complete, and its tools have been retired. Migrated pull requests keep a `legacy-review.json` index of the legacy review's head, verdict, and time beside the copied `legacy-review.md`; the findings and prior-finding statuses were never converted and stay readable only in that Markdown. When comparing a legacy report with a new one, read the legacy statuses as these dispositions:

| Legacy status | Disposition |
| --- | --- |
| ADDRESSED | `addressed` |
| PARTIALLY ADDRESSED | `partially_addressed` |
| NOT ADDRESSED | `still_present` |
| NO LONGER APPLICABLE | `superseded` |

The new `unable_to_verify` has no legacy equivalent. Legacy per-severity finding IDs (`M1`, `H1`, `S1`) are not carried over; new reports number findings `F001`, `F002`, ... so an ID survives a change of severity between reviews.
