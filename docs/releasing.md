# Releasing

How a release of this repository is cut. Every release is a tag on `main` created through a GitHub release; nothing is built or uploaded, because users install from a clone. Versions below `1.0.0` are tagged as pre-releases.

A release tag is `vMAJOR.MINOR.PATCH` in ASCII digits with nothing after the patch number, the `vX.Y.Z` this procedure tags. A pre-release is a GitHub release marked `--prerelease`, never a suffix on the tag, so a tag such as `vX.Y.Z-rc.1` is not a release, and neither is any other tag. Releases are ordered by their three numbers, each compared as a whole number, and the last release a commit holds is the highest release tag reachable from it, whatever tag of another name sits nearer to it. `release_tags.py` in skill-core is that one definition, and every reader of a release asks it: `tools/release_notes.py` starts a release's notes at the last release before it, the upgrade-notes check below compares the contract files with the last release on `origin/main`, and `update-coding-agent-skills` deploys the last release on `origin/main` by default and stops at one that raises the breaking component above the deployed commit's last release.

## Versioning

A version number tells a user what the update asks of them, because `update-coding-agent-skills` moves an installation to each release and the skills run from a clone rather than from a built artifact. The level of a release is set by the largest demand any change since the last tag makes on the user, judged against the contracts below.

**Contracts**, in the order a break hurts:

1. **Durable user data.** The code-review records, flags, and tracker state under the code-review state directory, and the ownership manifest under `~/.claude/skills`. A format change without an automatic migration is the most expensive break this project can ship.
2. **User-authored files.** Reviewer manifests and the code-review configuration file, which people write by hand.
3. **Skill invocation.** Skill names, their arguments, and the status lines an agent parses, such as `UP_TO_DATE` or `FAILED`.
4. **Deployer operation.** Commands and flags, configured variables, required tool floors, and supported platforms.
5. **Behavior.** Prompt wording, review heuristics, and output no script parses. Behavior is not a contract; the structured record is.

**Levels**, from `1.0.0` on:

- **Patch.** The user does nothing after updating: fixes, documentation, prompt wording, tests, internal refactoring.
- **Minor.** The update may ask for something optional or additive: a new skill or opt-in, a new configured variable that `configure` prompts for, a new platform, a new output line, a manifest version the previous release can still read (`OLDEST_READABLE_VERSION` in `deployer/manifest.py`).
- **Major.** The user must act or loses something: a removed or renamed skill, a renamed argument or status line, a record or configuration format that needs a migration, a dropped platform, a raised tool floor, or a manifest the previous release cannot read.

**Before `1.0.0`**, the minor level carries changes that would be major later, each with its migration or its stated manual step, and the patch level carries fixes only. `1.0.0` is tagged when the deployer runs on macOS and Linux as well as Windows, every contract above is pinned by a test against literal values, and a record or manifest migration has shipped and been exercised in a release.

A change to a contract file is what raises the level, and validation holds that rule. `tests/run_validation.py` finds the last tag, the last release on `origin/main`, and compares these contract values at that tag with the working tree: `MANIFEST_VERSION` and `OLDEST_READABLE_VERSION` in `deployer/manifest.py`, each `required_vars` list under `deploy-meta/`, each schema under `skills/code-review-core/references/`, the format tables under "Formats" in `docs/code-review-operations-contract.md`, the skill directory names under `skills/`, and the tool floors in `deployer/tools.py`. While one differs and no upgrade note since that tag names it, validation fails, naming the item and what the entry must say: its level in the words of the list above and the user action or none. An entry whose level is not one of those words fails too. A pull request writes its entry under `## Upgrade note` in its body, never in [upgrade-notes.md](upgrade-notes.md), and the repository squash-merges with the body as the commit message, so the notes since the tag are the entries in the commit messages since it. In a pull request, validation reads the body, which CI writes from the event payload to a file and passes with `--pr-body`, and the commits merged into `origin/main`, not the branch's own commits, since the body is what becomes the squash commit's message; a local run without `--pr-body` reads the commits on `HEAD`, the branch's included. Editing the body reruns the check. With no release tag reachable from `origin/main` nothing has been released and the check passes; a missing `origin/main` or a shallow clone fails it with the fetch command that fixes it. Skill arguments, status lines, exit codes, and deployer flags have no contract file, so the pull request that changes one writes its entry without being asked, naming it as the `Contract:` field in [upgrade-notes.md](upgrade-notes.md) says.

The provider-specific PDF tool floors in `skills/skill-core/scripts/pdf_tool.py`, referenced by the catalogue's `provider_minimum`, are tool-floor contracts too. The upgrade-notes guard compares them separately so changing a provider requirement cannot bypass the release obligation by leaving its catalogue reference unchanged.

The pull request body is author-controlled input. CI reads it as data from the event's JSON payload and writes it to a fixed file; it is never interpolated into executable workflow script text or executed by the upgrade-notes check. Validation checks the entries' structure and contract coverage, not the accuracy or suitability of their prose, links, or Markdown. The maintainer reviews the body before approving the squash merge, which carries it into the commit message. The release-note tool intentionally preserves authored Markdown from those entries rather than escaping it as literal text; reviewing the generated section before publishing remains the maintainer's responsibility.

## Milestones

Each release has a GitHub milestone, and its description holds these sections and nothing else:

- `## Scope`: one or two sentences saying what the release is and why it takes that version step, with the tag date once it is tagged.
- `## Order of work`: a numbered list of steps, each item an issue number and a few words, with sequencing notes in parentheses and `(done <date>)` on a step once its last item merges.

The other records live elsewhere. What shipped is the milestone's closed issues and the pull requests that closed them. An audit's record is the issues it filed, each naming in its body the audit, its scope, and its date. A release's by-hand obligations, such as a corrected generated entry, an upgrade note a pull request omitted, or the README's cells, are one preparation issue on the release's milestone, which the release pull request closes. A vulnerability follows [SECURITY.md](../SECURITY.md) and is never named on a milestone. A milestone is a GitHub record, so it carries dates; the documents still do not.

The [project board](../CONTRIBUTING.md#issues-and-pull-requests) groups its items by its `Release` field, not by milestone, so a new milestone needs its option there: when a release's milestone is created, add an option of the same name to the field in the board's settings, at its place in version order, then run `python tools/project_release_sync.py` once issues are filed on it.

## Before tagging

1. **Validation and the canary.** `main` is green by construction, since every change arrives through a validated pull request. That rests on the branch protection [CONTRIBUTING.md](../CONTRIBUTING.md#how-main-is-protected) states; run `python tools/branch_protection.py`, which reads it through `gh api`, and expect `PROTECTED`. For a release, also run the `runtime-canary` repository skill against every shipped skill `python -B tools/runtime_canary.py --changed-since` names, which reads the changes since the last tag, at most three to a run, so each runtime is seen finding and running them from a deployment, not only passing tests.
2. **Deployability on a fresh machine.** Dispatch the `deployable.yml` workflow against `main`:

   ```bash
   gh workflow run deployable.yml --ref main
   ```

   Or use **Actions > Deployment Smoke Test > Run workflow**. Its `claude-version`, `codex-version`, and `copilot-version` inputs default to the versions in the README's table; pass `latest` to try the newest release. The workflow installs the prerequisites and the three runtimes on a fresh GitHub-hosted Windows runner, writes the Codex sandbox setting and records where the Python app execution aliases stand, since no supported command turns them off, configures and deploys into the runner's profile, checks that Codex CLI and Copilot CLI find every adapter and that Claude Code is installed with every deployed skill and agent in place (it cannot list skills without a session, so this is a file-layout check), uninstalls, confirms that nothing the manifest owned or the deployment made, file or directory, is left beside the manifest and retained backups, deploys again, and checks again. Its Linux job does the same on a fresh GitHub-hosted Ubuntu runner, without the Codex settings, which exist only on Windows. It is never a required status check, and it starts no model, so it does not show a skill running. It also runs every Tuesday, the day after `validate.yml`'s weekly run, once on the README's versions and once on the latest release of every runtime, so a runtime release that breaks a fresh install shows within a week; a scheduled failure is a signal to read, not a gate. A release still dispatches its own run, because the README's fresh-runner column and date record the last dispatched release run, never a weekly one.

   Read the run's summary page: the tool versions, then one row per runtime and pass, each `PASSED`, `SKIPPED` with the reason (a runtime that will not list skills until it is signed in), or `FAILED`. A green run means every runtime that could list found every adapter and at least one could list. The **deployable-run-requested** artifact (a scheduled run's are `deployable-run-readme` and `deployable-run-latest`), and the Linux job's **deployable-run-linux-requested** beside it, hold each command's log, the verify results, and the manifest. Quote the versions and the date in the release notes, and update the README's fresh-runner column and date to match. Installing by hand on a clean Windows environment, one runtime at a time, is the stronger check and was not done for `v0.1.0`; do it when a machine and the time exist, and record the environment in the README's supported-runtimes section either way.
3. **Private-name scan.** Scan the tracked tree against the private list kept outside the repository, one term per line, and expect no hits:

   ```bash
   git grep -n -i -w -F -f '<list>' -- . | grep -v YourName
   ```

   `YourName` is the documented placeholder in test fixtures. The CI private-reference check matches only generic patterns, and adding a specific name to it would publish the name, so the list never enters the repository. Any hit is a prompt to read the line, not a verdict; fix a real one through a pull request before tagging.
4. **Statements that carry a version.** The README's supported-runtimes table names the versions tested and where they were tested; `SECURITY.md` says that an installation follows releases, that a fix lands on `main` and reaches users at the next tag, and that following `main` is the opt-in. Confirm both still describe the truth for this release.
5. **Security settings.** The `python tools/branch_protection.py` run in step 1 also confirms that secret scanning, push protection, private vulnerability reporting, and Dependabot security updates are enabled and that the default workflow token is read-only, and prints each setting as it found it; `PROTECTED` covers them.
6. **Validation legs.** In the release pull request, run `python -B tools/record_job_seconds.py`. It reads the logs of the latest successful `Validation` runs on `main` through `gh run view --log` and rewrites `tests/validation/job_seconds.json` with each job's median seconds across them and the runs it read, which is how `tests/run_validation.py` deals the jobs across the workflow's legs; the median keeps one run's slow or fast job from setting the legs for a release. The newest run decides which jobs the table names, and a job the older runs lack takes the median of the runs that have it. It reads a leg under its name or the one it had before the Linux job joined the required check, so the median spans that rename. Pass run IDs to read those runs instead, or `--count` to change how many of the latest it reads. A run that did not finish successfully, whose log names no job as a leg or lacks a leg, or whose log `gh` can no longer read refuses the whole record, and the refusal names its cause. Commit the table, and after the release pull request merges, confirm its `Validation` run's legs took about the same time.
7. **Upgrade notes.** In the release pull request, run `python tools/release_notes.py vX.Y.Z --write`. It writes the `## vX.Y.Z` section of [upgrade-notes.md](upgrade-notes.md) from the upgrade notes of the commits since the last tag, newest first, each naming its pull request from the squash commit's title. Read the section against the milestone's closed issues and the pull requests that closed them, review the authored Markdown and link targets as well as the stated upgrade obligations, add any obligation the release's preparation issue records as an entry, and commit it; the release audit in step 8 reads it, and the release notes open with it. A validated entry is not automatically approved for publication.
8. **Release audit.** Run the [`audit-repository`](../.claude/skills/audit-repository/SKILL.md) repository skill's `release` mode, which writes one brief per area changed since the last tag for a read-only reader. It asks whether the release keeps what it says: each change matches its issue and its upgrade note, no contract or document contradicts the code, every changed behavior has its test, and every grant a changed skill declares is used. A confirmed defect is fixed before the tag. Drift and polish are filed into the next milestone, and the release notes name each as deferred. A trust-boundary finding goes to a private security advisory, as [SECURITY.md](../SECURITY.md) says, never to a public issue.
9. **Project board.** Run `python tools/project_release_sync.py --check` and expect `IN_SYNC`: every item's `Release` matches its milestone, issues the release audit filed included, and the field's options are in version order. On `DRIFTED`, add any option it names to the field in the board's settings, then run the tool without `--check` to set the rest.

## Tagging

First run `git fetch origin main --tags`, then `python tools/release_notes.py vX.Y.Z --check`, and expect `CURRENT`. Step 7 of [Before tagging](#before-tagging) wrote the upgrade-notes section from the commits up to the release branch's head, and the tag is cut from `main`, so a pull request merged into `main` or into the release branch after the section was written would be in the tag and in no section: the next release's section starts at this tag. The check reads the `## vX.Y.Z` section as `origin/main` holds it and the upgrade notes of the commits from the last tag to `origin/main`, compares them by heading, and fetches nothing. When the section lacks an entry, it prints `BEHIND` with the count and each missing entry and exits 1: carry those entries into the committed section through a pull request, and tag once that merges and the check prints `CURRENT`. An entry the section holds that no commit carries, such as an obligation from the release's preparation issue, does not count against it.

Write the notes to a file and create the release from `main`:

```bash
gh release create vX.Y.Z --target main --prerelease --title "vX.Y.Z" --notes-file '<file>'
```

The notes open with the release's section of [upgrade-notes.md](upgrade-notes.md), which [Before tagging](#before-tagging) wrote. Just below the version heading, `Level: <level>.` states the largest leading level word any entry names, ordered by the **Levels** list in [Versioning](#versioning); an empty section instead says `Level: none (no upgrade-note entries).` The entries retain their explanations and the action, if any, each asks of the user, including when a minor carries a change that would be major after stability. The tool does not add summaries to published sections. The notes then say what the README says: what is included, the supported platform, the runtime versions tested and where, and what was deferred. Carry the release milestone's scope into them, with its closed issues and the pull requests that closed them. Drop `--prerelease` at `1.0.0`.

### Release notes

The GitHub release notes are the record of what changed between tags; the repository keeps no `CHANGELOG.md`. Since an installation follows releases unless its user opts into `main`, each update brings a release, and its notes are where a user reads what the update brought and what it asks of them, and `MAJOR_UPDATE` points the user at them.

A release-note obligation that a pull request records belongs in its body's `## Upgrade note`, and one no pull request carries is recorded in the release's preparation issue and added to the generated section in the release pull request, so each reaches [upgrade-notes.md](upgrade-notes.md) and the notes with the rest.

## After tagging

1. Deploy from the hub on `main` and confirm `python deploy.py verify` finds every adapter.
2. Start `update-coding-agent-skills --channel release` from a runtime and confirm it reports the new tag, as `UP_TO_DATE vX.Y.Z` or `UPDATED <old>..vX.Y.Z`, which exercises the rendered source path, the fetch, and the release lookup together. It pins the installation at the tag, so the hub's next deployment without `--at` needs `--unpin`, and the skill's `--channel main` replaces the pin too. A release that raised the breaking component makes the skill stop at `MAJOR_UPDATE` on every installation behind it until the user passes `--cross-major`, so its notes must say what the user has to do.
3. **Security advisories.** Apply [Disclosure](../SECURITY.md#disclosure) to each open draft advisory whose fix the new tag carries, whoever opened it (a reporter, the release audit, or a rotation audit): publish each whose defect a tagged release carried, with the new tag as its patched version, and close the rest without publication. A draft whose fix the new tag does not carry, such as a defect deferred to the next milestone, stays a draft for the release that carries it.
4. **Rotation audit.** Run the `audit-repository` skill's `rotation` mode, which names the area its rotation record shows read whole least recently (the deployer, the code review skills, the other skills, or the repository's infrastructure and documents) and writes that area's whole-area brief, so no area goes unread for more than four releases. Its findings, with the issues the new milestone carries, feed the next milestone; it holds nothing. Record the area for the new tag with `rotation --record`, through a pull request whose body names the areas both audits read; the milestone does not record them.
5. Retire any worktree the release work used.

The history of how the repository was prepared for its first release is in the Git history before the first tag.
