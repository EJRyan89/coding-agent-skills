# Releasing

How a release of this repository is cut. Every release is a tag on `main` created through a GitHub release. A deployment installs from a clone, so the one thing a release builds and uploads is the plugin archives the marketplace installs from ([After tagging](#after-tagging)). Versions below `1.0.0` are tagged as pre-releases.

A release tag is `vMAJOR.MINOR.PATCH` in ASCII digits with nothing after the patch number, the `vX.Y.Z` this procedure tags. A pre-release is a GitHub release marked `--prerelease`, never a suffix on the tag, so a tag such as `vX.Y.Z-rc.1` is not a release, and neither is any other tag. Releases are ordered by their three numbers, each compared as a whole number, and the last release a commit holds is the highest release tag reachable from it, whatever tag of another name sits nearer to it. `release_tags.py` in ejryan89-skill-core is that one definition, and every reader of a release asks it: `tools/release_notes.py` starts a release's notes at the last release before it, the upgrade-notes check below compares the contract files with the last release on `origin/main`, `update-coding-agent-skills` deploys the last release on `origin/main` by default and stops at one that raises the breaking component above the deployed commit's last release, and the deployer tells that skill's own pin at a release from yours by the last release the pinned commit holds.

## Versioning

A version number tells a user what the update asks of them, because `update-coding-agent-skills` moves an installation to each release and the skills run from a clone rather than from a built artifact. The level of a release is set by the largest demand any change since the last tag makes on the user, judged against the contracts below.

**Contracts**, in the order a break hurts:

1. **Durable user data.** The code-review records, flags, and tracker state under the code-review state directory, and the ownership manifest under `~/.claude/skills`. A format change without an automatic migration is the most expensive break this project can ship.
2. **User-authored files.** Reviewer manifests and the code-review configuration file, which people write by hand.
3. **Skill invocation.** Skill names, their arguments, and the status lines an agent parses, such as `UP_TO_DATE` or `FAILED`.
4. **Deployer operation.** Commands and flags, configured variables, required tool floors, and supported platforms.
5. **Behavior.** Prompt wording, review heuristics, and output no script parses. Behavior is not a contract; the structured record is.

**Levels**, from `1.0.0` on:

- **Patch.** The user does nothing after updating: fixes, documentation, prompt wording, tests, internal refactoring.
- **Minor.** The update may ask for something optional or additive: a new skill or opt-in, a new configured variable that `configure` prompts for, a new platform, a new output line, a manifest version the previous release can still read (`OLDEST_READABLE_VERSION` in `deployer/manifest.py`).
- **Major.** The user must act or loses something: a removed or renamed skill, a renamed argument or status line, a record or configuration format that needs a migration, a dropped platform, a raised tool floor, or a manifest the previous release cannot read.

**Before `1.0.0`**, the minor level carries changes that would be major later, each with its migration or its stated manual step, and the patch level carries fixes only. A fix that adds a refusal, or another stop that asks some users to act once, is a patch when the refusal only enforces a promise the documents already made and the action it asks is one the refusal itself names; otherwise it is a minor, and its upgrade note's `Level:` says which. `1.0.0` is tagged when the deployer runs on macOS and Linux as well as Windows, every contract above is pinned by a test against literal values, and a record or manifest migration has shipped and been exercised in a release.

A change to a contract file is what raises the level, and validation holds that rule. `tests/run_validation.py` finds the last tag, the last release on `origin/main`, and compares these contract values at that tag with the working tree: `MANIFEST_VERSION` and `OLDEST_READABLE_VERSION` in `deployer/manifest.py`, each `required_vars` list under `deploy-meta/`, each schema under `skills/ejryan89-code-review-core/references/`, the format tables under "Formats" in `docs/code-review-operations-contract.md`, the skill directory names under `skills/`, and the tool floors in `deployer/tools.py`. While one differs and no upgrade note since that tag names it, validation fails, naming the item and what the entry must say: its level in the words of the list above and the user action or none. An entry whose level is not one of those words fails too. A pull request writes its entry under `## Upgrade note` in its body, never in [upgrade-notes.md](upgrade-notes.md), and the repository squash-merges with the body as the commit message, so the notes since the tag are the entries in the commit messages since it. In a pull request, validation reads the body, which CI writes from the event payload to a file and passes with `--pr-body`, and the commits merged into `origin/main`, not the branch's own commits, since the body is what becomes the squash commit's message; a local run without `--pr-body` reads the commits on `HEAD`, the branch's included. Editing the body reruns the check. With no release tag reachable from `origin/main` nothing has been released and the check passes; a missing `origin/main` or a shallow clone fails it with the fetch command that fixes it. Skill arguments, status lines, exit codes, and deployer flags have no contract file, so the pull request that changes one writes its entry without being asked, naming it as the `Contract:` field in [upgrade-notes.md](upgrade-notes.md) says.

The provider-specific PDF tool floors in `skills/ejryan89-skill-core/scripts/pdf_tool.py`, referenced by the catalogue's `provider_minimum`, are tool-floor contracts too. The upgrade-notes guard compares them separately so changing a provider requirement cannot bypass the release obligation by leaving its catalogue reference unchanged.

The pull request body is author-controlled input. CI reads it as data from the event's JSON payload and writes it to a fixed file; it is never interpolated into executable workflow script text or executed by the upgrade-notes check. Validation checks the entries' structure and contract coverage, not the accuracy or suitability of their prose, links, or Markdown. The maintainer reviews the body before approving the squash merge, which carries it into the commit message. The release-note tool intentionally preserves authored Markdown from those entries rather than escaping it as literal text; reviewing the generated section before publishing remains the maintainer's responsibility.

## Milestones

Each release has a GitHub milestone, and its description holds these sections and nothing else:

- `## Scope`: one or two sentences saying what the release is and why it takes that version step, with the tag date once it is tagged.
- `## Order of work`: a numbered list of steps, each item an issue number and a few words, with sequencing notes in parentheses and `(done <date>)` on a step once its last item merges.

The other records live elsewhere. What shipped is the milestone's closed issues and the pull requests that closed them. An audit's record is the issues it filed, each naming in its body the audit, its scope, and its date. A release's by-hand obligations, such as a corrected generated entry, an upgrade note a pull request omitted, or the README's cells, are one preparation issue on the release's milestone, which the release pull request closes. A vulnerability follows [SECURITY.md](../SECURITY.md) and is never named on a milestone. A milestone is a GitHub record, so it carries dates; the documents still do not.

The [project board](../CONTRIBUTING.md#issues-and-pull-requests) groups its items by its `Release` field, not by milestone, so each milestone needs an option of the same name in that field, at its place in version order, added in the board's settings when the milestone is created. Step 4 of [After tagging](#after-tagging) confirms it for the next release.

## Before tagging

1. **Validation and the canary.** `main` is green by construction, since every change arrives through a validated pull request. That rests on the branch protection [CONTRIBUTING.md](../CONTRIBUTING.md#how-main-is-protected) states; run `python tools/branch_protection.py`, which reads it through `gh api`, and expect `PROTECTED`. For a release, also run the `runtime-canary` repository skill against every shipped skill `python -B tools/runtime_canary.py --changed-since` names, which reads the changes since the last tag, at most three to a run, so each runtime is seen finding and running them from a deployment, not only passing tests. Run `python -B tools/plugin_canary.py` too, which installs the plugins this checkout builds into a throwaway Claude Code configuration and checks that Claude Code lists them, runs the probe from the installed copy, guards the plugin's reviewer, and refuses that reviewer's result when every hook is off; each check starts a model session.
2. **Deployability on a fresh machine.** Dispatch the `deployable.yml` workflow against `main`:

   ```bash
   gh workflow run deployable.yml --ref main
   ```

   Or use **Actions > Deployment Smoke Test > Run workflow**. Its `claude-version`, `codex-version`, and `copilot-version` inputs default to the versions in the README's table; pass `latest` to try the newest release. The workflow installs the prerequisites and the three runtimes on a fresh GitHub-hosted Windows runner, writes the Codex sandbox setting and records where the Python app execution aliases stand, since no supported command turns them off, configures and deploys into the runner's profile, checks that Codex CLI and Copilot CLI find every adapter and that Claude Code is installed with every deployed skill and agent in place (it cannot list skills without a session, so this is a file-layout check), uninstalls, confirms that nothing the manifest owned or the deployment made, file or directory, is left beside the manifest and retained backups, deploys again, and checks again. Its Linux job does the same on a fresh GitHub-hosted Ubuntu runner, without the Codex settings, which exist only on Windows. It is never a required status check, and it starts no model, so it does not show a skill running. It also runs every Tuesday, the day after `validate.yml`'s weekly run, once on the README's versions and once on the latest release of every runtime, so a runtime release that breaks a fresh install shows within a week; a scheduled failure is a signal to read, not a gate. A release still dispatches its own run, because the README's fresh-runner column and date record the last dispatched release run, never a weekly one.

   Read the run's summary page: the tool versions, then one row per runtime and pass, each `PASSED`, `SKIPPED` with the reason (a runtime that will not list skills until it is signed in), or `FAILED`. A green run means every runtime that could list found every adapter and at least one could list. The **deployable-run-requested** artifact (a scheduled run's are `deployable-run-readme` and `deployable-run-latest`), and the Linux job's **deployable-run-linux-requested** beside it, hold each command's log, the verify results, and the manifest. Quote the versions and the date in the release notes, and update the README's fresh-runner column and date to match. Installing by hand on a clean Windows environment, one runtime at a time, is the stronger check; do it when a machine and the time exist, and record the environment in the README's supported-runtimes section either way.

   The workflow deploys into the runner's real profile, not a `--canary-home`, because Codex on Windows reads the real profile, and `HOME` on Linux, and each pass runs `deploy.py verify`. `tools/deployable_report.py` judges Codex and Copilot discovery, checks Claude Code's installed version and the deployed file layout, names every path the manifest owned or the deployment made, files included, that the uninstall left, and writes the step summary; `tests/tools/test_deployable_report.py` covers it. The workflow uses no secret. `tests/validation/workflows.py` holds that the Linux job is the Windows one in Bash without its Codex settings step, and pins the workflow's triggers, its cron, permissions, action pins, runtime versions, each verify report's `--deploy-verify-log` to the `verify-first.log` or `verify-second.log` its own step saves, and, in both jobs, the uninstall between the first deployment's layout check and the step that reports what was left.

   The `runtime-command-lines.yml` workflow is its companion for the command lines the repository starts. Every Wednesday, the day after `deployable.yml`'s run, and on dispatch, it installs the latest release of every runtime on a fresh Windows runner and a fresh Ubuntu one and runs `python tools/runtime_command_lines.py`. The tool builds each command line from the function that builds it for a real run: the Copilot CLI review host's, the runtime canary's, the skill evaluations', the plugin canary's, the deployer's skill listings, and `check`'s Codex sandbox probe. It looks for each flag in the runtime's help and starts each command line signed out, with a throwaway home, no credential, no GitHub CLI on its search path, and a proxy nothing listens on, so no model is reached. It prints one line per command line, `ACCEPTED`, `REMOVED` with the flag the runtime refused, `REFUSED` with another argument error, or `FAILED` with the runtime's own message, writes them to the step summary, and fails the job on a `REMOVED`, `REFUSED`, or `FAILED` line. `ACCEPTED ... UNLISTED` names a flag the runtime takes but its help does not list, a flag a later release may drop without notice. After each runtime's `VERSION` line, a `SAMPLE_BEHIND` line names each sample of that runtime's output captured under `tests/fixtures/captured-output/` whose recorded version is older than the one installed, which never fails the job: capture it again from the new release, as its `how` in `provenance.json` says, in the pull request that next touches its reader or one of its own. Before tagging, read its latest run, and dispatch one (`gh workflow run runtime-command-lines.yml --ref main`) when a runtime has released since. `tests/tools/test_runtime_command_lines.py` covers the tool with stub runtimes and each runtime's real refusals and signed-out starts captured under `tests/fixtures/captured-output/`, and `tests/validation/workflows.py` pins the workflow's triggers, its cron, permissions, action pins, and that each job installs the latest runtimes and then runs the check.
3. **Private-name scan.** Scan the tracked tree against the private list kept outside the repository, one term per line, and expect no hits:

   ```bash
   git grep -n -i -w -F -f '<list>' -- .
   ```

   The CI private-reference check matches only generic patterns, and adding a specific name to it would publish the name, so the list never enters the repository. Any hit is a prompt to read the line, not a verdict; fix a real one through a pull request before tagging.
4. **Statements that carry a version.** The README's supported-runtimes table names the versions tested and where they were tested; `SECURITY.md` says that an installation follows releases, that a fix lands on `main` and reaches users at the next tag, and that following `main` is the opt-in. Confirm both still describe the truth for this release.
5. **Security settings.** The `python tools/branch_protection.py` run in step 1 also confirms that secret scanning, push protection, private vulnerability reporting, and Dependabot security updates are enabled and that the default workflow token is read-only, and prints each setting as it found it; `PROTECTED` covers them.
6. **Validation legs.** In the release pull request, run `python -B tools/record_job_seconds.py`. It reads the logs of the latest successful `Validation` runs on `main` through `gh run view --log` and rewrites `tests/validation/job_seconds.json` with each job's median seconds on each platform across them and the runs it read, which is how `tests/run_validation.py` deals the jobs across each platform's legs; the median keeps one run's slow or fast job from setting the legs for a release. The newest run decides which jobs each platform's table names, and a job the older runs lack takes the median of the runs that have it. It reads a Windows leg under its name or the one it had before the Linux job joined the required check, and Linux under its legs' name, the one they had before they were named as the Windows legs are, or as the one leg of the job that ran it unsharded before Linux was dealt, so the median spans each rename. A job the pool retried after a termination is recorded under its own name, without the pool's note. Pass run IDs to read those runs instead, or `--count` to change how many of the latest it reads. A run that did not finish successfully, whose log names no job as a leg or lacks a platform or a leg, or whose log `gh` can no longer read refuses the whole record, and the refusal names its cause. Commit the table, and after the release pull request merges, confirm its `Validation` run's legs on each platform took about the same time.
7. **Upgrade notes.** In the release pull request, run `python tools/release_notes.py vX.Y.Z --write`. It writes the `## vX.Y.Z` section of [upgrade-notes.md](upgrade-notes.md) from the upgrade notes of the commits since the last tag, newest first, each naming its pull request from the squash commit's title. Read the section against the milestone's closed issues and the pull requests that closed them, review the authored Markdown and link targets as well as the stated upgrade obligations, add any obligation the release's preparation issue records as an entry, and commit it; the release audit in step 8 reads it, and the release notes open with it. A validated entry is not automatically approved for publication.
8. **Release audit.** Run the [`audit-repository`](../.claude/skills/audit-repository/SKILL.md) repository skill's `release` mode, which writes one brief per area changed since the last tag for a read-only reader. It asks whether the release keeps what it says: each change matches its issue and its upgrade note, no contract or document contradicts the code, every changed behavior has its test, and every grant a changed skill declares is used. A confirmed defect is fixed before the tag. Drift and polish are filed into the next milestone, and the release notes name each as deferred. A trust-boundary finding goes to a private security advisory, as [SECURITY.md](../SECURITY.md) says, never to a public issue.
9. **Project board.** Run `python tools/project_release_sync.py --check` and expect `IN_SYNC`: every item's `Release` matches its milestone, issues the release audit filed included, and the field's options are in version order. On `DRIFTED`, add any option it names to the field in the board's settings, then run the tool without `--check` to set the rest.

## Tagging

First run `git fetch origin main --tags`, then `python tools/release_notes.py vX.Y.Z --check`, and expect `CURRENT`. Step 7 of [Before tagging](#before-tagging) wrote the upgrade-notes section from the commits up to the release branch's head, and the tag is cut from `main`, so a pull request merged into `main` or into the release branch after the section was written would be in the tag and in no section: the next release's section starts at this tag. The check reads the `## vX.Y.Z` section as `origin/main` holds it and the upgrade notes of the commits from the last tag to `origin/main`, compares them by heading, and fetches nothing. When the section lacks an entry, it prints `BEHIND` with the count and each missing entry and exits 1: carry those entries into the committed section through a pull request, and tag once that merges and the check prints `CURRENT`. An entry the section holds that no commit carries, such as an obligation from the release's preparation issue, does not count against it.

Write the notes to a file and create the release from `main`:

```bash
gh release create vX.Y.Z --target main --prerelease --title "vX.Y.Z" --notes-file '<file>'
```

The notes open with the release's section of [upgrade-notes.md](upgrade-notes.md), which [Before tagging](#before-tagging) wrote. Just below the version heading, `Level: <level>.` states the largest leading level word any entry names, ordered by the **Levels** list in [Versioning](#versioning); an empty section instead says `Level: none (no upgrade-note entries).` The entries retain their explanations and the action, if any, each asks of the user, including when a minor carries a change that would be major after stability. The tool does not add summaries to published sections. The notes then say what the README says: what is included, the supported platform, the runtime versions tested and where, and what was deferred. Carry the release milestone's scope into them, with its closed issues and the pull requests that closed them. Drop `--prerelease` at `1.0.0`.

### Release notes

The GitHub release notes are the record of what changed between tags; the repository keeps no `CHANGELOG.md`. Since an installation follows releases unless its user opts into `main`, each update brings a release, and its notes are where a user reads what the update brought and what it asks of them, and `MAJOR_UPDATE` points the user at them.

A release-note obligation that a pull request records belongs in its body's `## Upgrade note`, and one no pull request carries is recorded in the release's preparation issue and added to the generated section in the release pull request, so each reaches [upgrade-notes.md](upgrade-notes.md) and the notes with the rest.

## After tagging

1. Deploy from the hub on `main` and confirm `python deploy.py verify` finds every adapter.
2. Start `update-coding-agent-skills --channel release` from a runtime and confirm it reports the new tag, as `UP_TO_DATE vX.Y.Z` or `UPDATED <old>..vX.Y.Z`, which exercises the rendered source path, the fetch, and the release lookup together. It pins the installation at the tag, so the hub's next deployment without `--at` needs `--unpin`, and the skill's `--channel main` replaces the pin too. A release that raised the breaking component makes the skill stop at `MAJOR_UPDATE` on every installation behind it until the user passes `--cross-major`, so its notes must say what the user has to do.
3. **Plugin archives.** The marketplace installs each plugin from its archive on the release, so build them from the tag, attach them, and pin their checksums. In a worktree on `origin/main`, never the hub:

   ```bash
   python -B tools/plugin_release.py build vX.Y.Z --output '<folder>'
   gh release upload vX.Y.Z '<folder>'/*.zip
   ```

   `build` exports the tag's own tree, so a commit on `main` after the tag changes nothing, and assembles each plugin from it at the tag's version. It writes the archives into the folder, printing `ARCHIVE <plugin> "<path>" <sha256>` for each, and rewrites `.claude-plugin/marketplace.json` so each entry names its release asset with that `sha256`, printing `PINNED <plugin> vX.Y.Z <sha256>`. Open a pull request with that change alone. Once it merges, run `python -B tools/plugin_release.py check` on `main`, which rebuilds each pinned archive from its tag, and expect `PIN_MATCHES` for every plugin. Until the pull request merges, the marketplace installs the previous release's plugins. A plugin with no pinned release yet, as every plugin had before the first release that attached archives, has nothing to fall back on: its entry names this release's asset with no `sha256`, so its install fails until the archive is attached and then installs an archive no digest checks, and `check` prints `UNPINNED` for it until the pins merge. So attach the archives and open the pull request as soon as the release is published. Then install from the published marketplace into a throwaway configuration, as `CLAUDE_CONFIG_DIR='<folder>' claude plugin marketplace add EJRyan89/coding-agent-skills` followed by `claude plugin install coding-agent-skills@ejryan89 --config "repos_root=<folder>"` with the same variable, giving each required option the plugin declares a folder of the throwaway configuration as `tools/plugin_canary.py` does, since a required option left unset stops the install, and expect `claude plugin list --json` there to name the new version.
4. **Security advisories.** Apply [Disclosure](../SECURITY.md#disclosure) to each open draft advisory whose fix the new tag carries, whoever opened it (a reporter, the release audit, or a rotation audit): publish each whose defect a tagged release carried, with the new tag as its patched version, and close the rest without publication. A draft whose fix the new tag does not carry, such as a defect deferred to the next milestone, stays a draft for the release that carries it.
5. **Milestones.** Close the released milestone, with the tag date in its `## Scope`. The next release's milestone usually exists already, since the release audit files into it before the tag; if it does not, create it now, holding only the sections [Milestones](#milestones) names. Run `python tools/project_release_sync.py` and expect `SYNCED`: a `DRIFTED` line naming the next milestone means its `Release` option is still missing, so add it in the board's settings, at its place in version order, and run the tool again.
6. **Rotation audit.** Run the `audit-repository` skill's `rotation` mode, which names the area its rotation record shows read whole least recently (the deployer, the code review skills, the other skills, or the repository's infrastructure and documents) and writes that area's whole-area brief, so no area goes unread for more than four releases. Its findings, with the issues the new milestone carries, feed the next milestone; it holds nothing. Record the area for the new tag with `rotation --record`, through a pull request whose body names the areas both audits read; the milestone does not record them.
7. **Guidance audit.** Run the `audit-repository` skill's `guidance` mode, which writes one brief per runtime the deployer supports and one for Python. Each names the pages of that runtime's published guidance the skill's `references/guidance.json` lists, the files of this repository that state facts about the runtime, the provenance files of `audit-skill` and `audit-ai-config` among them, and the questions a reader answers for each page against the live page. The mode refuses while the record names no page for a runtime the deployer supports. The maintainer runs it after every tag. Its findings feed the next milestone; it holds nothing. Record the tag with `guidance --record` in the pull request that records the rotation area, and give each page that moved its new address in the record there.

   The readers start from the latest run of the `runtime-changelogs.yml` workflow, which runs every Thursday, the day after `runtime-command-lines.yml`'s run, and on dispatch (`gh workflow run runtime-changelogs.yml --ref main`). It runs `python tools/runtime_changelogs.py`, which reads the changelogs of Claude Code, Codex CLI, and Copilot CLI that the record's `changelogs` name, keeps each entry of a release newer than that changelog's `read_through` that mentions a flag, environment variable, path, or frontmatter key the code uses, and requests every page of the record, listing each page that redirects, with its new address, or is gone. It reads the terms from the code at each run: the flags and environments of the command lines `tools/runtime_command_lines.py` builds, at the runtime version each changelog was read through and at each newer release, so a flag the code passes only before or after one of them is a term, the environment variables the Python reads or sets, the paths `deployer/paths.py` writes, and the keys of the skills' and agents' frontmatter. It also lists as `SAMPLE_BEHIND` each sample of a runtime's output captured under `tests/fixtures/captured-output/` whose recorded version is older than that runtime's latest release. It writes the findings to the step summary and fails only when the watch itself cannot run, never on a finding; it decides nothing, starts no model, and needs no secret. In the pull request that records the guidance audit, move each changelog's `read_through` to the latest release whose entries the readers read. `tests/tools/test_runtime_changelogs.py` covers the tool with fixture changelogs, stub responses, and real entries and a real Codex releases page captured under `tests/fixtures/captured-output/changelogs/` with their provenance, and `tests/validation/workflows.py` pins the workflow's triggers, its cron, permissions, action pins, and that its one job runs the watch so that the watch's own exit status is the job's.
8. Retire any worktree the release work used.

The history of how the repository was prepared for its first release is in the Git history before the first tag.
